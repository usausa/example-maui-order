# 文書 (docs/、README)

## 内容

- `docs/` は人向けの文書にし、現状 (何を・なぜ) を書く。どう書くべきかの規則は規則ファイルに置く
- 実装の計画 (`docs/plan.md`) は作っている間だけ置き、作り終えたら設計文書 (画面設計、構成) に移して、残った項目を `docs/backlog.md` に移す
- 設計文書には実装済みの内容だけを書き、作っていない機能と今後の検討事項は計画か `docs/backlog.md` に置く
- 業務の前提と流れ (前提、端末と業務、来店、業務の流れ、金額と税、扱わないもの) は `docs/business.md` に置く
- API の文書 (`docs/api-design.md`) には API のルール (共通仕様、リソース、通知、端末ごとの API、エラーコード) だけを書く
- API の文書は、まだ作っていない API を端末とこれから作るサーバが合わせる想定として書き、冒頭に想定であることを書く。作った API は構成 (`docs/architecture.md`) に挙げる
- データベースの文書 (`docs/database.md`) はスキーマ (`Schema.sql`) と同じ内容にし、スキーマを変えたら文書も直す
- 扱う業務は注文と店内の注文の業務に絞り、扱わないものは `docs/business.md` の「扱わないもの」の章に置き場所・連携と一緒に書く
- 本番の環境に使う AWS のサービス名 (Amazon ECS、Amazon RDS、AWS CDK など) は、文書・計画・規則に書いてよい
- 調べた結果は、実在の企業名・製品名・サービス名とその出典を書かずに、型や考え方で書く
- 公開しない情報 (企業名・製品名・出典、調査の生のメモ) は名前が `__` で始まるファイル (Git の管理の外。例: `docs/__research.md`) に置き、Git に載せる文書からリンクしない
- 実装が変わるたびに古くなる数 (クラスの数、テストの件数) は書かない。列挙するときは漏れのないようにするか、代表を挙げて「など」で結ぶ

## 形式

- 章 (`##`) の見出しだけ先頭に絵文字を付ける (`###` 以下には付けない)
- 見出しの絵文字は、標準で絵文字の形になるもの (U+FE0F の要らないもの) にする (アンカーに異体字セレクタが入らないように)
- 見出しを変えたら、その見出しへのリンクのアンカーも直す
- 表のチェックや可否は絵文字 (✅ など) で示す
- Markdown は 1 行 1 文にし、「。」の後に 2 スペースを置いて改行する (表、見出し、コードは除く)
- 箇条書きは最後の文に「。」を付けず、続きの行は本文の位置に字下げする
- 括弧の中の補足は「。」で区切って同じ行に続けてよい (箇条書きと段落のどちらも)
- 列挙、項目と値の組、条件ごとの扱いは、文で続けずに箇条書きか表にする
- 表のセルは短くし、長い説明は表の下の箇条書きに出す
