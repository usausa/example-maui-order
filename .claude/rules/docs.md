# 文書と規則

## 文書

- `docs/` は人間向けの文書にし、現状 (何を・なぜ) を書く。どう書くべきかの規則は規則ファイルに置く
- 実装の計画 (`docs/plan.md`) は作っている間だけ置き、作り終えたら設計文書 (画面設計、構成) に移して、残った項目を `docs/backlog.md` に移す
- 設計文書には実装済みの内容だけを書き、作っていない機能と今後の検討事項は計画か `docs/backlog.md` に置く
- サーバがない間は、`docs/api-design.md` (API) と `docs/database.md` (データベース) を、端末のモックとこれから作るサーバが合わせる想定として置き、冒頭に想定であることを書く。サーバを作ったら実装済みの仕様に直す
- API の想定は注文と店内の注文の業務に絞り、扱わないものは「扱わないもの」の章に置き場所・つなぎ方と一緒に書く
- 文書に経緯と日付は書かない (過去の形は git の履歴で追う)
- Git に載せる文書には実在の企業名・製品名・サービス名とその出典を書かず、調べた結果は型や考え方で書く
- 公開しない情報 (企業名・製品名・出典、調査の生のメモ) は名前が `__` で始まるファイル (Git の管理の外。例: `docs/__research.md`) に置き、Git に載せる文書からリンクしない
- 実装が変わるたびに古くなる数 (クラスの数、テストの件数) は書かない。列挙するときは漏れのないようにするか、代表を挙げて「など」で結ぶ
- README は概要 (数行)、主要な画面の画像と一言の説明、`docs/` の文書へのリンクだけにする (AI 向けの規則 (`AGENTS.md`、`.claude/`) は載せない)
- 人が読む文書 (README、`docs/`) は見てわかりやすくする。章 (`##`) の見出しは先頭に絵文字を付け、表のチェックや可否は絵文字 (✅ など) で示す
- 見出しの絵文字は、標準で絵文字の形になるもの (U+FE0F の要らないもの) にする (アンカーに異体字セレクタが入らないように)。見出しを変えたら、その見出しへのリンクのアンカーも直す
- `docs/` と README の Markdown は 1 行 1 文にし、「。」の後に 2 スペースを置いて改行する (表、見出し、コードは除く)
- 箇条書きは最後の文に「。」を付けず、続きの行は本文の位置に字下げする。括弧の中の補足は「。」で区切って同じ行に続けてよい
- 文の中の引用 (「…」と) には「。」を入れない

## 規則

- AI 向けの規則は `AGENTS.md` (すべてのエージェントが読む全体の書き方・検証・進め方) と `.claude/rules/` (領域別のコードの書き方) に置く
- AI が読むもの (`AGENTS.md`、`.claude/`) は AI にとっての読みやすさを優先し、人向けの飾り (見出しの絵文字など) は付けない
- 繰り返す手順 (検証、エミュレータでの確認) は `.claude/skills/` にスクリプトと一緒に置く。環境に固有の値 (機器、ポート) は skills に書かず、引数で受ける
- 規則ファイルは 1 項目 1 行 1 話題にする (表とコード例は除く)。文書の「。」+ 2 スペースの改行は適用しない
- 例の列挙は「、」、択一は「 / 」で区切る
