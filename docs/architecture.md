## 📦 1. プロジェクト

モノレポにし、区分ごとのフォルダの `src/` にプロジェクト、`tests/` にテストを置く。  
ソリューションはサーバと端末のアプリの区分ごとに分け、サーバは `server/TableOrder.Server.slnx`、端末のアプリはアプリごと (`table/TableOrder.TableApp.slnx`、`hall/TableOrder.HallApp.slnx`、`reception/TableOrder.ReceptionApp.slnx`)。

| 区分 | フォルダ | 内容 |
| --- | --- | --- |
| 共有 | `shared/` | サーバ・端末・Web アプリが共に使うもの (.NET の標準のライブラリのほかに依存しない) |
| サーバ | `server/` | 注文サーバと、サーバが配る Web アプリ |
| テーブル端末 | `table/` | お客様がテーブルで使う端末のアプリ (.NET MAUI、Android) |
| ホール端末 | `hall/` | スタッフが使う端末のアプリ (.NET MAUI、Android) |
| 受付機 | `reception/` | 店の入口に置く端末のアプリ (.NET MAUI、Android) |
| 端末に共通の部品 | `terminal/` | 端末のアプリが共に使う部品 (.NET MAUI の Android のライブラリ。画面は持たない) |

- 区分で分けるのは、ビルドに要るもの (端末は Android のワークロード) と設定が違うため。  
  サーバの区分は Android なしでビルドできる
- 端末のアプリは用途ごとに区分を分け、1 つの区分に用途の違うアプリを混ぜない。  
  端末に共通の部品 (端末の情報、鍵、専用端末、EMM の設定、異常終了の記録、端末の設定と状態、スタッフの PIN、登録と状態の報告、通知の受け口の土台、どの端末でも同じポップアップ、画面の土台、System の色と共通のスタイル、その文言) は `terminal/` の `TableOrder.Terminal` (画面 (`ViewId`) を持たないライブラリ) に置く
- 共有のプロジェクトと端末に共通の部品は単独のソリューションを持たず、使う区分のソリューションに入れて確かめる。  
  単独にすると、アプリだけが使う型を InspectCode が使われていないと指摘するため。  
  今は、共有のプロジェクトと共有のテストを、共有の型をいちばん使うテーブル端末のソリューションに入れている。  
  端末に共通の部品は、使っているテーブル端末、ホール端末、受付機のソリューションに入れている

| プロジェクト | 種類 | 内容 |
| --- | --- | --- |
| `shared/src/TableOrder.Domain` | .NET | 業務の値 (列挙型) と計算 (金額と内税、割り勘の目安、タグのルールの数え方、ラストオーダーの判定)。サーバと端末で同じ計算を使う |
| `shared/src/TableOrder.Contract` | .NET | 通信データ (`XxxRequest` / `XxxResponse`、`LocalizedText`) |
| `shared/src/TableOrder.Client` | .NET | 端末と Web アプリが使う API の窓口 (全端末に共通の `IDeviceApi`、端末の種類ごとの `ITableApi`・`IHallApi`・`IReceptionApi`・`IKitchenApi`、通知の `IOrderEvents`、`ApiResult`)、注文サーバの実装 (`Rest/` の要求、`SignalR/` の通知)、端末の鍵の値を API の形にする変換 (`DeviceCredentials`) |
| `terminal/src/TableOrder.Terminal` | .NET MAUI (Android のライブラリ) | 端末に共通の部品。端末の情報、鍵、専用端末、EMM の設定、異常終了の記録 (`Components/`、`Diagnostics/`)、端末の設定と状態、起動の準備 (`StartupState`)、スタッフの PIN (`State/`)、登録と状態の報告 (`Usecase/`、`Shell/`)、通知の受け口の土台 (`OrderEventReceiverBase`)、処理中の覆い (`ShellProperty`)、スタッフメニューの入口の長押しの時間 (`AppGestures`)、どの端末でも同じポップアップ (電卓、知らせ、確認) と入口 (`Modules/`。PIN の確かめを含む)、ポップアップと遷移のプラグイン (`Extender/`)、添付プロパティ (`Behaviors/`)、System の色と共通のスタイル (`Resources/Styles/` の `SystemColors`、`TerminalStyles`)、文言 (`TerminalResources`)、画面に収める幅 (`TerminalSizes`)、お客様の画面の端末 (テーブル端末、受付機) に共通の部品 (チェーンの色 `ThemeManager`、画像の保存 `ImageCache`、チェーンの印 `BrandMark`、言語 `LanguageState`)、登録 (`AddTerminalComponents`。端末の種類の `TerminalOptions` と、専用端末の型の `KioskOptions` を受ける。お客様の画面の部品は `AddCustomerComponents` で、アプリの文言のカルチャを替える `LanguageOptions` を受ける) |
| `table/src/TableOrder.TableApp` | .NET MAUI (Android) | テーブル端末のアプリ |
| `hall/src/TableOrder.HallApp` | .NET MAUI (Android) | ホール端末のアプリ |
| `reception/src/TableOrder.ReceptionApp` | .NET MAUI (Android) | 受付機のアプリ |
| `server/src/TableOrder.Server.Core` | .NET | 業務の処理 (端末の登録と認可、店舗、メニュー、品切れ) と DB の読み書き (Accessor と 2-way SQL) |
| `server/src/TableOrder.Server.Web` | ASP.NET Core | 入口 (REST)、端末の認証、管理画面 (Blazor Server)、キッチン端末の配信 |
| `server/src/TableOrder.Server.AppHost` | Aspire | 開発で動かす構成 (サーバとテレメトリ) |
| `server/src/TableOrder.KitchenApp` | Blazor WebAssembly | キッチン端末の Web アプリ |
| `shared/tests/TableOrder.Domain.Tests` | .NET (xunit) | `Domain` の計算のテストと、`Domain` が他の層に依存しないことの確認 |
| `shared/tests/TableOrder.Client.Tests` | .NET (xunit) | 端末の鍵の値の変換、通知の数え方 (つなぎ直しでためた通知と抜けた通知の合わせ方、接続の作り直し) と、`Client` が画面・端末・サーバに依存しないことのテスト (窓口の動きはサーバのテストで本物のサーバにつないで確かめる) |
| `server/tests/TableOrder.Server.Core.Tests` | .NET (xunit) | すべての SQL がテナントで絞っていることと、DB の型の変換のテスト |
| `server/tests/TableOrder.Server.Web.Tests` | .NET (xunit) | API と通知のハブのテスト (端末の登録とトークン、端末のアプリと同じ形の鍵での登録、端末の種類の範囲、テナントで分けられていること、来店から会計までの API、通知の送る先と抜けた通知) と、端末のアプリの窓口 (`TableOrder.Client` の REST と SignalR) をサーバにつないだテスト |

```
TableOrder.{Table|Hall|Reception}App ──> TableOrder.Terminal ──> TableOrder.Client ──> TableOrder.Contract ──> TableOrder.Domain
TableOrder.KitchenApp ──> TableOrder.Client
TableOrder.Server.Web ──> TableOrder.Server.Core ──> TableOrder.Contract
          └──> TableOrder.KitchenApp
```

### 名前の付け方

| 区分 | 名前 (アセンブリ、ルートの名前空間、フォルダ) |
| --- | --- |
| 共有 | `TableOrder.{Domain\|Contract\|Client}` |
| サーバ | `TableOrder.Server.{Core\|Web\|AppHost}` |
| アプリ (店の端末とブラウザで動く) | `TableOrder.{Table\|Hall\|Reception\|Kitchen}App` |
| 端末に共通の部品 (.NET MAUI のライブラリ) | `TableOrder.Terminal` |
| テスト | 区分の `tests/` に `{プロジェクト名}.Tests` |

- 店の端末とブラウザで動くアプリは `{用途}App` にし、サーバはプロジェクトの役割 (`Core`、`Web`、`AppHost`) で名前を分ける。  
  フォルダの区分はビルドの単位で決めるので、サーバが配る Web アプリ (`TableOrder.KitchenApp`) は `server/` に置く
- 名前空間はアセンブリの名前にフォルダの道を続ける (`TableOrder.TableApp.Modules.Menu` など)
- ファイルは 1 つの型を 1 つのファイルに置き、ファイル名を型の名前にする。  
  Android だけの部分は `Xxx.android.cs`、端末の画面は `Modules/{画面}/{画面}View.xaml` と `{画面}ViewModel.cs` にする
- 端末の窓口は端末の種類ごとに `I{種類}Api` (`ITableApi`。ホール端末は `IHallApi`、キッチン端末は `IKitchenApi`、受付機は `IReceptionApi`) にし、端末の登録と設定 (`IDeviceApi`) と通知 (`IOrderEvents`) は共通にする。  
  実装は通信の方式を前に付ける (`RestDeviceApi`、`Rest{種類}Api`、`SignalROrderEvents`)
- サーバのファイルの名前は template-maui-server に合わせる (入口は `Endpoints/{リソース}Endpoints.cs`、業務の処理は `Services/{リソース}Service.cs`、データは `Accessors/{リソース}Accessor.cs` と `Accessors/Sql/{リソース}Accessor.{メソッド}.sql`、行は `Models/Entity/{テーブル}Entity.cs`)
- MAUI の `MenuItem` とぶつかるので、メニューの品の型は `MenuProduct` などにする

## 🧱 2. テーブル端末の作り

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Modules/` | 画面とポップアップの View と ViewModel (`Startup`、`Setup`、`Staff`、`Standby`、`Menu`、`Checkout`、`Dialogs`) |
| `State/` | 画面をまたぐ状態 (`MenuState`、`VisitState`、`CartState`、`StoreState`) |
| `Usecase/` | 通信と状態の更新を組み合わせる手順 (`OrderUsecase`。来店の開始と終了、メニューのルールの判定、注文の送信) |
| `Models/` | 画面で使う形 (`MenuCategory`、`MenuProduct`、`CartLine`、`ItemSelection`、`OrderedLine`) |
| `Controls/` | 見た目の部品 (`QrCodeView`。QR コードの代わりの模様) |
| `Markup/` | 記号 (`AppIcons`)、画面 ID の拡張 |
| `Resources/` | 色 (`Colors.xaml`。Brand・Neutral・Status の役割)、テーブル端末の画面のスタイル (`Styles.xaml`)、画面の文言 (`Strings/AppResources.resx`、`.en.resx`)、記号のフォントとグリフの表、アイコン、スプラッシュ |
| `Shell/` | MainPage と通知の受け手 (`OrderEventReceiver`) から画面への知らせ (戻る、来店の開始・終了、店舗の変更、送れたかわからなかった注文の受け付け、起動からやり直す) |
| `Platforms/` | Activity と Device Owner の受け口とマニフェスト |

- 端末に共通の部品 (端末の情報、鍵、専用端末、EMM の設定、異常終了の記録、端末の設定 `Settings`、端末の状態、スタッフの PIN `StaffLock`、登録と状態の報告 `DeviceUsecase` / `StatusReporter`、電卓・知らせ・確認のポップアップ、プラグイン、添付プロパティ) と、お客様の画面の部品 (チェーンの色 `ThemeManager`、画像の保存 `ImageCache`、チェーンの印 `BrandMark`、言語 `LanguageState`) は `TableOrder.Terminal` のものを使う。  
  `MauiProgram` で `AddTerminalComponents` と `AddCustomerComponents` を呼んで登録し、登録で送る端末の種類は `TerminalOptions`、専用端末の制限に使う Device Owner の受け口とホームの画面は `KioskOptions`、言語を替えるときにテーブル端末の文言のカルチャを替える処理は `LanguageOptions` で渡す。  
  共通のポップアップの ID (`TerminalDialogId`) と View の組は、ポップアップの登録に `TerminalModules.DialogSource` を足して入れる
- 色とスタイルは、`App.xaml` でテーブル端末の色 (`Colors.xaml`)、`TableOrder.Terminal` の共通のスタイル (`TerminalStyles`。System の色 `SystemColors` を中に入れる)、テーブル端末のスタイル (`Styles.xaml`) の順に入れる。  
  共通のスタイルは、チェーンで替わる役割の色をテーブル端末の色から `DynamicResource` で引く

### 層

```
View (XAML) ──> ViewModel ──> Usecase ──> IDeviceApi / ITableApi (Client)
                    │            │
                    └────────────┴──> State (Settings / MenuState / VisitState / CartState / LanguageState / StoreState / StaffLock)

IOrderEvents / IDeviceApi.Denied (Client) ──> OrderEventReceiver (Shell) ──> State、表示中の画面への知らせ (ShellEvent)
StatusReporter (Terminal) ──> DeviceUsecase (Terminal) ──> IDeviceApi (1 分ごとの状態の報告)
```

- ViewModel は State を読み、いくつかの画面が使う手順 (来店の開始と終了、メニューのルールの判定、注文の送信) は Usecase に任せる。  
  読むだけの通信と、1 つの画面だけが使う手順 (お会計の会計の開始・取りやめと支払、注文履歴の食後の品のお願い) は、ViewModel から `ITableApi` を呼ぶ
- 通信の結果は `ApiResult<T>` で受け、例外にしない。  
  失敗は `ViewHelper.ErrorMessage` でお客様向けの文言にし、`Log.WarnApiFailed` で記録する
- ポップアップとの受け渡しは引数と戻り値で行い、ポップアップは閉じると ViewModel ごと破棄する
- 料理の写真とチェーンのロゴは `ImageCache` (`TableOrder.Terminal`) が端末に保存し、画面は保存したファイルを出す (写真を保存していない間は、面の色の上にチェーンのロゴか記号を出す)。  
  起動のときに足りない画像をまとめて受け取り (同時に 4 つまで)、今のメニューで使わなくなった画像は消す。  
  受け取れなかった画像は待受に戻ったときに取り直し、保存は登録ごとのフォルダに分けて、登録し直したら前のフォルダを消す
- サーバの通知は `OrderEventReceiver` が受けて状態を替え、操作の途中 (Busy) と遷移の間を待ってから、表示中の画面に `ShellEvent` で知らせる。  
  受け方 (重複を接続ごとの seq で捨てる、操作と遷移の間を待つ、起動からやり直す知らせ) は `TableOrder.Terminal` の `OrderEventReceiverBase` が持ち、`OrderEventReceiver` は来店・店舗・品切れ・注文の通知の扱いだけを持つ。  
  扱いは各画面が決める (待受は注文の画面へ、注文は待受へ、お会計はお礼へ。人数・会計中・売り切れは表示を替える)
- 来店が終わってから画面が来店を終えるまで (お礼の間、スタッフメニューの間) に同じテーブルで開いた次の来店 (移ってきた来店も) は、`VisitState.Next` に残す。  
  来店を終えたら続けて次の来店を開き、待受に戻さずに注文の画面にする (お礼の間に受付機やスタッフが次のお客様を案内したとき)
- 端末が使えなくなったとき (無効化、テナントの停止)、管理画面で端末を替えたとき (`device.updated`)、EMM が接続先を替えたとき、通知を追いかけられなくなったときは、`OrderEventReceiver` が開いているポップアップを閉じて `ShellEvent.Restart` を出し、表示中の画面が起動からやり直す。  
  起動と端末の設定の画面は自分で確かめるので受けず、ポップアップ (PIN や登録の入力) も閉じない。  
  受けない画面の間に届いた知らせは残し、受ける画面に移ってから起動からやり直す (起動の途中に届いた端末の変更を捨てない)
- 管理画面でチェーンや店舗の設定を替えると、設定の版 (`settingsVersion`) が上がって `store.updated` が届く。  
  待受は版が起動のときに読んだ端末の設定と違えば起動からやり直して読み直し (来店の途中の画面では替えない)、待受に入ったときにも版を確かめる

## 📱 3. 画面

### 画面とポップアップ

| 画面 | ViewId | 内容 |
| --- | --- | --- |
| 起動 | `Startup` | システムのロゴ、準備の進み具合 (登録、トークン、端末と店舗の設定 (チェーンの色、スタッフの PIN、言語を入れる)、メニュー、品切れ、料理の写真とロゴ、今の来店)、失敗のときの再試行と設定 (設定は PIN を確かめて開く。失敗の間は 30 秒ごとに自動でもやり直す)。テーブルの割り当て待ちとテナントの停止もここに出す |
| 端末の設定 | `Setup` | 接続先 (注文サーバの URL)、今の接続先での登録、ペアリングコード (電卓) |
| スタッフメニュー | `Staff` | 端末の情報 (テーブル、端末の名前、端末の id、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリの版)、端末の設定、専用端末の一時的な解除。5 分操作しなければ、専用端末に戻してお客様の画面に戻る |
| 待受 | `Standby` | チェーンの名前とロゴ、いらっしゃいませ、来店の開き方 (店舗の設定) で替わる文言 (スタッフの案内を待つ、受付機で受け付ける、タブレットから注文できる)、言語 (今の言語を出し、押すと選ぶ。店舗の言語が 1 つなら出さない)、テーブル。来店の開き方が席の店は「ご注文をはじめる」から人数を入れて始め、ほかの店はスタッフか受付機が開いた知らせで注文の画面に進む |
| 注文 | `Menu` | ヘッダ (チェーンの名前とロゴ、テーブル、人数、言語)、カテゴリのタブ、メニューのカード、注文リスト (1 回の注文の明細の上限を知らせる)、注文の知らせ (ほかの端末で始めた会計、注文の一時停止、ラストオーダー。注文できない間は確定を止める)、下部の操作 (注文履歴、店員呼出 (呼び出しの用件がなければ出さない)、お会計) |
| お会計 | `Checkout` | 明細、内税、割り勘の目安、まだ出していない品 (お支払いのあともお持ちする) の知らせ、支払方法 (QR コード決済、カード、レジ。店舗の設定にあるものだけ)、割り勘 (店舗の設定で使うとき。人数で割った 1 人分ずつ払い、残りがなくなるまで支払方法の選び直しに戻る。払い終えた人数は、明細を読み直せるまでやり直してから減らした人数で割り直す)、QR の表示と待ち (期限を過ぎたら取り消して選び直しに戻る)、お礼と電子レシートの QR |

| ポップアップ | DialogId | 内容 |
| --- | --- | --- |
| 電卓 | `InputNumber` (`TerminalDialogId`) | ペアリングコード、スタッフの PIN (入れた桁数だけ見せる) |
| 知らせ / 確認 | `Message` / `Confirm` (`TerminalDialogId`) | 上限、失敗、年齢などの確認 (受ける / 断るは同じ大きさ) |
| 言語 | `Language` | 言語をその言語の名前で並べ、今の言語に印を付ける (待受と注文の画面の言語のボタンから開く) |
| 人数 | `GuestCount` | 大人と子ども (小学生以下) を増減のボタンで入れ、合わせて 1 人以上で始める (来店の開き方が席の店の待受から開く) |
| 商品の詳細 | `ItemDetail` | 大きな写真 (ないときはチェーンのロゴ)、説明、アレルギー、カロリー、オプション (必須 / お好みで。品切れのものは選べない)、出す時機、数量、入れる (合計つき)。注文リストの行から開くと内容を直せる |
| 注文の確認 | `OrderConfirm` | 明細と合計、提案 (1 枠。上限に当たったら理由を出す)、注文する、受け付けの知らせ (数秒で閉じる)、失敗と送り直し |
| 注文履歴 | `OrderHistory` | 注文と明細の状態、食後の品をお願いする (通らなければ失敗を出す)、これまでの合計 |
| 店員呼出 | `StaffCall` | 用件のタイル、呼び出しの状態 (呼んでいます / 向かっています) |

### 遷移

```
起動 ──(登録なし、登録トークンなし)──> 端末の設定 ──登録 / 保存──> 起動
起動 ──(登録なし、登録トークンあり)──> 登録して続ける
起動 ──(来店なし)──> 待受
起動 ──(来店あり)──> 注文
注文 ──お会計──> お会計 ──支払の完了──> (お礼) ──閉じる / 時間 (店舗の設定)──> 待受
                    ├──割り勘の 1 人分の完了──> 支払方法の選び直し (残りがなくなるまで)
                    └──メニューに戻る (払う前だけ)──> 注文
待受 ──(来店が開いた知らせ)──> 注文
待受 ──ご注文をはじめる (来店の開き方が席の店)──> [人数] ──> 注文
注文 ──(レジで払い終えた知らせ)──> 待受
お会計 ──(レジで払い終えた知らせ)──> (お礼) ──閉じる / 時間 (店舗の設定)──> 待受
(お礼) ──閉じる / 時間 (お礼の間に次の来店が開いた)──> 注文
注文 ──カード──> [商品の詳細] ──(確認のルール)──> [確認]
     ──注文を確定する──> [注文の確認]
     ──注文履歴──> [注文履歴]
     ──店員呼出──> [店員呼出]
待受 / 注文 / お会計 ──ブランドの印の長押し──> [PIN] ──> スタッフメニュー ──閉じる──> 注文 (来店中) / 待受
待受 ──(チェーンと店舗の設定の変更)──> 起動
どの画面 ──(端末の無効化、テナントの停止、接続先の変更の知らせ)──> 起動
```

- MainPage は画面を切り替える入れ物と処理中の覆いだけを持ち、帯 (ヘッダ、タブ、下部の操作) は各 View が持つ
- 来店が閉じたときと起動からやり直すときは、開いているポップアップを `PopupClosePlugin` が閉じる (来店が閉じたときはお客様の画面 (注文、お会計) のものだけ)。  
  ポップアップの処理の途中 (注文の送信など) は終わってから閉じ、閉じるのはそのポップアップだけにする
- 端末の戻るは表示中の画面に渡す。  
  お客様の画面 (待受、注文) では何もせず、お会計では支払方法の選び直しかメニューへ戻る (一部を払ったあとは画面の戻ると同じく何もしない)
- カートに入れる前に、1 回の注文の明細の数、1 明細の数量 (同じ内容の行にまとめた数)、メニューのルールの上限、残りの数 (商品とオプション) を確かめる (提案の追加も同じ)。  
  端末で確かめられる上限は、お客様に確認のルールを尋ねる前に見る
- 注文が送れたかわからない (通信できない) ときは注文の Id を残し、届いたか断られたかがわかるまでカートを直させずに、同じ内容を同じ Id で送り直してもらう。  
  注文の通知 (`order.created`) で届いていたとわかったら、カートを空にして受け付けたことを知らせる
- 支払も、結果のわからない支払 (作る要求の結果がわからない、取り消しが通らなかった) の Id・方法・額を残し、同じ方法と額で払うときは同じ Id で送り直す。  
  ほかの払い方にするときは先に取り消し、取り消す前に払い終わっていたら払い終えたものとして進める
- スタッフメニューは、ブランドの印を 3 秒押して PIN (店舗の設定) を入れると開く。  
  閉じると、品切れなどの表示を合わせるために注文の画面か待受を作り直す
- PIN は店舗の設定で受け取ったハッシュ (登録と一緒に保存する) で確かめるので、サーバにつながらないときも確かめられる。  
  5 回続けて間違えると 5 分入れない (アプリを起動し直すと数え直す)。  
  起動に失敗したときの端末の設定も PIN で守る (登録していない端末は PIN なしで入れる)
- 全画面 (システムバーを隠す) は専用端末の扱い ([6. 専用端末](#-6-専用端末)) に含める。  
  ポップアップは Activity と別の窓に出るので、`FullscreenPopupPlugin` でポップアップの窓のシステムバーも隠す

## 🔗 4. 状態と通信

### 状態

| 状態 | 持つもの |
| --- | --- |
| `Settings` | 接続先、登録した端末の id (登録した接続先と組で持つ)、スタッフの PIN のハッシュ (登録と一緒に持つ)。`IPreferences` に置き、API の実装は `IDeviceContext` として読む |
| `MenuState` | 端末と店舗の設定 (端末を置いたテーブル、チェーンの名前とロゴ、機能の有無と来店の開き方、言語、設定の版を含む)、メニュー、品切れ。画面には選んでいる言語に直して渡す |
| `VisitState` | 今の来店 (人数、状態、答えた確認のルール、注文した品) |
| `CartState` | 注文する前の行。送ったが結果のわからない注文の Id (送り直しで同じ Id を使う。ある間はカートを直さない) |
| `LanguageState` | 画面の言語と、店舗で選べる言語 |
| `StoreState` | 店舗の今の状態 (タイムゾーン、注文の一時停止、ラストオーダー、設定の版)。起動で読み、通知で替える |
| `StaffLock` | スタッフの PIN の確かめと、間違いが続いたときに止める時間 |

### メニューのルール

ドリンクバー・お酒・数量限定などの特例はコードで分けず、メニューのタグとルール (`MenuResponseRule`) で表す。  
数え方は `TableOrder.Domain.TagRules` に置き、端末は案内に、サーバは注文の確認に使う。

| ルール | 端末の動き | サンプルのメニューの例 |
| --- | --- | --- |
| 確認 (`Confirmation`) | タグの品を入れる前に確かめ、答えを来店に記録する (`Visit` は来店で 1 回) | お酒の年齢の確認 |
| 上限 (`Limit`) | 来店の注文とカートを合わせて上限を超えたら入れない (`Guest` は 1 人あたり × 人数) | サーロインステーキはお一人様 1 点まで |
| 提案 (`Suggestion`) | 注文の確認で、タグの品を誰かが頼んでいて人数より少なければ 1 枠だけ提案する | ドリンクバー (単品とセットのオプション) を人数分に |

### 通信の窓口

- `ITableApi` はテーブル端末が使う要求 ([api-design.md](api-design.md)) を 1 つずつメソッドにしたもの。  
  REST と gRPC のどちらで実装しても、端末は `ITableApi` だけを見る
- `IHallApi` はホール端末が使う要求 (席、来店の操作、代わりの注文、提供、呼び出し、品切れと注文の一時停止、会計の手伝い) を 1 つずつメソッドにしたもの
- `IReceptionApi` は受付機が使う要求 (店舗、空席、来店の開始) を 1 つずつメソッドにしたもの
- `IKitchenApi` はキッチン端末が使う要求 (店舗、メニュー、品切れ、チケットの一覧と作り始め・できあがり・下げる・戻す) を 1 つずつメソッドにしたもの
- `IDeviceApi` は全端末に共通の要求 (登録、トークン、状態の報告、端末の設定) の窓口。  
  アクセストークンは窓口の中で持って画面に渡さず、トークンの要求が断られたとき (無効化、テナントの停止) は `Denied` で端末の id と理由を知らせる
- API の実装が読む端末の側の値 (接続先、登録した端末の id、端末の鍵) は `IDeviceContext` で受ける (テーブル端末は `Settings` が持つ)
- `IOrderEvents` はサーバの通知 (来店の開始・変更・移動・終了、店舗の変更、品切れ、注文と明細の変化) を受ける窓口。  
  起動で今の状態を読む前につなぎ (`ConnectAsync`)、通知は `seq` の順に届く。  
  同じ通知が 2 回届くことがあるので、受け手は最後に受けた `seq` 以前の通知を捨てる
- ラストオーダーを過ぎたかは `TableOrder.Domain.StoreHours` で決める (開店の時刻を営業日の区切りにし、日をまたぐ営業も扱う)。  
  端末は知らせに、サーバは注文の受け付けに使う
- DI では `IDeviceApi`、`ITableApi`、`IOrderEvents` に注文サーバの実装 (`RestDeviceApi`、`RestTableApi`、`SignalROrderEvents`) を登録する。  
  接続先は要求のたびに読むので、端末の設定で替えると次の要求から新しい接続先に送る (通知は起動でつなぎ直す)

### 注文サーバの実装

| 実装 | 中身 |
| --- | --- |
| `RestConnection` | 要求の送り方。接続先の下の `api/v1/` に送り、アクセストークンを期限の 2 分前と `401` を受けたときに取り直す (送り直しは 1 回だけ)。結果は `4xx` を `Rejected` (`errorCode` と文言)、`401` を `Unauthorized`、`5xx`・時間切れ (15 秒)・通信できないを `Unavailable` にする |
| `RestDeviceApi` / `RestTableApi` / `RestHallApi` / `RestReceptionApi` / `RestKitchenApi` | 端末の種類ごとの窓口。要求の形を決めて `RestConnection` で送る。メニューは版が同じなら `304` を受けて前に読んだものを使う (`RestMenuCache`。窓口ごとに持つ) |
| `SignalROrderEvents` | 通知 (`/hubs/store`)。`ready` で受けた番号から数え、切れたら間をおいてつなぎ直して、抜けた通知を `GET /events` で読んでから続ける。切れてから抜けた通知を読み終えるまでに届いた通知 (`ready` より前のものも) はためておき、抜けた通知と合わせて seq の順に渡す (`EventSequencer`)。通知には接続を付け (`OrderEventArgs.Connection`)、`ConnectAsync` で作り直したら前の接続の通知と読み込みは渡さない。つなぐ前の問い合わせは 15 秒で打ち切り、`401` で断られたらトークンを取り直す。抜けた通知を読めないとき (追いかけられない `410` など) は `Expired` で知らせ、端末は起動からやり直す。受け手が例外を投げても配り続け、渡しそこねた通知の代わりに `Expired` で知らせる |

- JSON はソース生成 (`ClientJsonContext`) で読み書きし、リフレクションに頼らない (端末のトリミングで型の情報が消えないように)
- 端末が受ける通知は、来店 (`visit.opened` / `updated` / `moved` / `closed`)、店舗 (`store.updated`)、品切れ (`stock.updated`)、注文 (`order.created`、`order.lines.updated`。上限のルールの数え方)、呼び出し (`call.created` / `call.updated`。ホール端末の呼び出しの一覧)、チケット (`ticket.created` / `ticket.updated`。キッチン端末は一覧を読み直すので中身を渡さない) にする。  
  テーブル端末は、注文履歴・呼び出し・支払の状態を開いている間に読み直して出す
- Android の端末は Debug だけ平文の HTTP につなげる (開発のサーバ。Release は HTTPS だけで、端末の設定と EMM の構成も https の接続先だけを受ける)
- 落ちたときの例外は記録し (`CrashReport`)、次の起動でログに残す (お客様の画面には出さず、起動を待たせない)。  
  観測されなかったタスクの例外は落ちていないので、ログにだけ残す

### 端末の登録

端末は自分の鍵 (`Components/DeviceKey`。Android の Keystore の P-256 で、秘密鍵は取り出せない) で登録し、サーバの端末の設定でテーブルを受け取る。  
鍵は Keystore の形 (公開鍵は SubjectPublicKeyInfo、署名は DER) で返し、API の形 (JWK、ES256 の JWT) には `DeviceCredentials` で直す。  
鍵の窓口 (`IDeviceKey`) の公開鍵と署名は非同期にし (ブラウザの鍵は非同期でしか使えない)、Android の鍵は Keystore の操作を画面のスレッドの外で行う。

| 場面 | 端末の動き |
| --- | --- |
| 登録 | 端末の設定でペアリングコードを入れて登録する。EMM が登録トークンを配っていれば、登録していない端末は起動したときに自分で登録する |
| 起動 | トークンを取り直し、端末の設定でテーブル端末として登録されていることとテーブルを確かめる。テーブルを割り当てるまでは起動の画面で待つ |
| 表示 | テーブルの名前は端末の設定 (`device.tableName`) のものを出す (端末ではテーブルを入れない) |
| 状態の報告 | 登録している間、1 分ごとにアプリの版と電池を送る (`StatusReporter`) |
| 無効化 | トークンの要求が `DEVICE_REVOKED` で断られたら、登録と鍵を消して端末の設定に戻る (無効にされたことを覚え、EMM の登録トークンでは自分で登録し直さない) |
| テナントの停止 | 起動の画面で止まっていることを出し、30 秒ごとにやり直す |
| 接続先の変更 | 登録は接続先ごとなので、登録した接続先と今の接続先が違えば登録していないものとする。登録は送った接続先の登録として覚え、送る間に接続先が替わったら覚えない。EMM が接続先を替えたら起動からやり直す |

- 鍵は登録し直しても使い回し、無効にされたときに消す (次の登録で作り直す)。  
  前の登録は、新しい登録でトークンを受け取ったときにサーバが無効にする (登録の応答が届かなければ、前の登録のまま使い続けられる)
- 登録の要求にアプリの端末の種類 (`TerminalOptions`) を入れ、違う種類のコード (テーブル端末にホール端末のコードなど) はサーバが登録せずに断る (`DEVICE_KIND_MISMATCH`。コードは使わない)。  
  断られた登録トークン (種類の違い、期限切れや取り消し) は待っても通らないので、起動の失敗でも自動ではやり直さない (配り直してから、もう一度試す)

## 🌐 5. 多言語と色

### 多言語

- 画面の文言は `Resources/Strings/AppResources.resx` (日本語、既定) と `AppResources.en.resx` (英語) に置き、XAML は `{x:Static strings:AppResources.Xxx}` で引く
- 言語を選ぶと `LanguageState` が UI のカルチャを替え、表示中の画面を作り直して文言を引き直す (注文リストは状態に残る)
- メニューの名前と説明、呼び出しの用件、チェーンの名前はサーバの `LocalizedText` から選んだ言語で出す
- 選べる言語は店舗の設定 (`languages`) の言語だけにし、1 つなら言語のボタンを出さない
- 起動して来店がないときと来店が終わったときは、端末の言語の設定によらず店舗の初めの言語に戻す (店舗の設定を読むまでは日本語)
- 金額と時刻の書式は言語で変えない。  
  時刻は店舗のタイムゾーンで出す (端末のタイムゾーンの設定によらない)
- サーバの失敗は errorCode ごとに端末の文言 (日本語と英語) で出し、割り当てのないものは共通の文言にする (サーバの文言は担当者向けの日本語なので出さない)

### 色

- 色は `Colors.xaml` の役割の名前で定義し、スタイル・画面・記号は役割の名前だけを使う
- Brand (主色、補助色)・Neutral・Status の役割は、起動のときにチェーンの設定の色 (`brand.theme`) で替える (`ThemeManager`)。  
  `Colors.xaml` の値は既定の色で、設定にない役割は既定の色にする。  
  スタイルはこれらの色を `DynamicResource` で引き、アプリの資源の一番上に置いたチェーンの色を使う
- System は起動・端末の設定・電卓の色で、チェーンの色に替えない。  
  スプラッシュとアプリのアイコンの色に揃えている
- チェーンの名前とロゴはチェーンの設定から受け取り、ヘッダと待受の印に出す (ロゴを保存していなければ名前の頭の文字を出す)。  
  店舗の名前 `storeName` とは分ける

## 🔒 6. 専用端末

`Components/KioskManager` が、端末に合わせて専用端末にする。  
画面が前に出るたびに全画面をかけ直し、方式を読み直して、変わっていれば掛け直す。  
動いている間に EMM がロックタスクを許したり外したりするので、スタッフメニューに出すときも方式を読み直す。

| 方式 | 見分け方 | 行うこと |
| --- | --- | --- |
| Device Owner | アプリ自身が Device Owner | 下の端末の制限を掛けて、ロックタスクに入る |
| 外部の管理 (EMM) | EMM がロックタスクを許している | ロックタスクに入る (端末の制限は EMM が掛ける) |
| なし | どちらでもない (開発中の端末など) | 全画面にするだけ (ロックタスクに入ろうとすると画面の固定の確認が出るため) |

Device Owner のときに掛ける端末の制限:

| 対象 | 設定 |
| --- | --- |
| ロックタスク | このアプリだけを許し、ホーム・履歴・通知・電源のメニュー・ステータスバーの情報を出さない |
| ホームアプリ | 注文の画面 (`MainActivity`) を常に使うホームにする。電源を入れたときと、落ちたときに起動し直す |
| ロック画面とステータスバー | 止める |
| 画面 | 充電中は点けたままにする |
| OS の更新 | 夜間 (2:00〜4:00) に入れる |
| 端末の操作 | 工場出荷時へのリセット、安全モード、利用者の追加を禁止する |

- 注文の画面は `lockTaskMode="if_whitelisted"` にして、ロックタスクを許されていれば起動したときにシステムがロックタスクに入れる (落ちて起動し直したときも)
- 注文の画面はホームの候補にもなるが、ホームの役割 (Android 10 以降) は替わらないので、Device Owner でない端末のホームはそのまま
- スタッフメニューの「一時的に解除する」でロックタスクを抜けてシステムバーを出し、Android の設定を開ける。  
  「専用端末に戻す」かアプリを起動し直すと元に戻る
- Device Owner の受け口 (`AdminReceiver`) は、adb から指せるように Java の名前を固定している (`tableorder.terminal.table/.AdminReceiver`)
- Debug は `testOnly` にして、adb から Device Owner を外せるようにしている。  
  Release は外せない (端末の初期化が要る)

エミュレータで確かめた動き:

| 操作 | 結果 |
| --- | --- |
| ステータスバーを引き下ろす | 通知とクイック設定を開けない |
| ホーム・履歴のキー | 注文の画面のまま |
| 電源ボタンの長押し | 電源のメニューが出ない |
| 通知 | 割り込みの通知が出ない |
| 再起動 | 注文の画面がホームとして起動し、ロックタスクに入る。ロック画面は出ない |
| プロセスを止める | ホームとして起動し直し、ロックタスクに入る。ホームアプリにしていないと (ランチャーから起動しただけでは)、ランチャーに戻ってしまう |
| Device Owner のアプリを止める | `am force-stop` と `am crash` が効かない (Debug は `run-as` で止める) |

### 管理対象の構成

接続先と端末の登録トークンは、外部の EMM が管理対象の構成で配れる (`Components/ManagedConfiguration`)。  
配られた値は端末の設定より優先し (`Settings` が読む)、端末の値は書き換えないので、配られなくなると端末の値に戻る。  
起動したときに読み、EMM が値を替えた知らせと、画面が前に出たときに読み直す。

- 配られた値は画面で変えられないようにする (端末の設定の画面は入力の代わりに値を出す)
- スタッフの PIN は配らず、管理画面の店舗の設定で決める
- 登録トークンは、登録していない端末が起動したときに使う (テーブルは管理画面で割り当てる)
- 接続先が替わったら起動からやり直してつなぎ直す (登録は接続先ごとなので、登録トークンがあれば登録し直す)
- スタッフメニューの端末の情報に、配られている設定を出す
- 配り方と値は [device-management.md](device-management.md) に書いた

### 状態と通知

- 起動で店舗の設定と今の状態、メニューと品切れ、席・呼び出し・提供の一覧を読み、`OrderEventReceiver` が通知で替える
- 店舗と品切れは通知の中身で替える。  
  店舗の設定の版が替わったら (PIN、呼び出しの用件、注文のルール、店舗の名前)、タブの画面で起動からやり直して読み直す (来店の詳細と代わりの注文の画面では替えず、タブの画面に戻ったときにやり直す)。  
  席・呼び出し・提供は、変わる通知 (来店、注文、明細、呼び出し) を受けたら一覧を読み直す (持ち場のない品は注文を受けたときにできあがるので、提供は注文の通知でも読み直す)
- 読み直す一覧の印は届いたとき (`OrderEventReceiverBase.OnReceived`) に付け、まとめて届いた通知を扱い終えたあと (`OnDrainedAsync`) に一覧を 1 回だけ読み直す。  
  印は読み直す前に下ろし (読み直しを待つ間に届いた通知の印を消さない)、読み直せなかった一覧は印を戻して次の通知のあとに読み直す
- 替えたら表示中の画面に `ShellEvent` (`StoreChanged`、`StockChanged`、`TablesChanged`、`CallsChanged`、`ServingChanged`) で知らせる。  
  起動からやり直す知らせ (`Restart`) はテーブル端末と同じ
- 来店の詳細は、席の一覧を読み直した知らせ (`TablesChanged`) で来店と注文を読み直し、来店が終わっていたら席のタブに戻る
- 品切れのタブは、品切れの知らせ (`StockChanged`。注文で残りの数が減ったときも届く) で品を出し直す
- 代わりの注文の画面は、席の一覧を読み直した知らせで来店を読み直し、終わっていたら席のタブ、会計中なら来店の詳細に戻る。  
  品切れの知らせで品の状態を替え、店舗の知らせで注文の一時停止の帯を出し直す
- 代わりの注文は、入れる前に上限のルール (来店の注文 (取消を除く) とカートを合わせて数える) と確認のルール (文言でお客様に確かめたかをスタッフに聞き、確かめたら来店に記録する。来店で 1 回のルールは記録したら聞かない) を `ProxyOrderUsecase` で確かめる (数え方はテーブル端末とサーバと同じ `TagRules`)。  
  送れたかわからない (通信できない) ときは、同じ来店で同じカートを送るときだけ同じ注文の id を送り直す (カートを替えたら新しい注文にする)
- 来店・明細・呼び出し・提供・品切れ・注文の一時停止・会計の操作は `HallUsecase` が送り、終えたら替わったもの (席、呼び出し、提供、品切れ、店舗の今の状態) を読み直す (通知でも読み直すが、操作した画面がすぐ替わるように)。  
  断られたとき (ほかで替えられていた、席が埋まっていた、会計中、来店が終わっていた) は知らせて読み直す。  
  来店を直す・終える操作は、読んだ来店の版を付けて送る
- 案内が送れたかわからない (通信できない) ときは、同じテーブルと人数の次の案内で同じ来店の id を送り直す (サーバは同じ id の送り直しに、開いた来店を返す)。  
  返った来店が終わっていたら (開いたあとに閉じた) 使わずに新しく開き、席の一覧にその来店が出たら送り直さない
- 呼び出しの向かう・対応したと提供は、ほかの端末が先に進めていても失敗にならない (サーバは今の呼び出しを返し、提供済みの明細は飛ばす)
- 一覧 (席のタイル、呼び出し、提供) は、読み直した並びに合わせて残る項目の中身を替え、作り直さない (`ItemsHelper.Sync`。スクロールの位置を保つ)。  
  残る項目も、出している値 (提供の数量とできあがりの時刻など) はすべて替える (一部の取消は同じ明細の数量を減らす)
- 払い終えた支払のある会計は取りやめられないので (サーバは会計中のまま返す)、明細のポップアップは取りやめを出さずに理由を出す。  
  明細を出したあとに払われて取りやめが効かなかったときも知らせる
- 新しい呼び出し (`call.created`) は、届いたとき (`OnReceived`) に `CallAlert` が端末の通知の音 (通知の音量) と振動 (通知の用途) で知らせる (操作の途中とポップアップを開いている間も待たない)。  
  続けて届いたときは 3 秒の間を空けて 1 回にまとめる
- 画面が消えている間も知らせるため、画面が前に出たときに前景サービス (`CallWatchService`。種類は `specialUse`) を始め、部分ウェイクロックで CPU を止めない。  
  前景サービスのアプリは Doze でも通信でき、通知の接続を保つ。  
  前景サービスの知らせは音のないチャネルに出す (通知の許可は求めない。許可がなくても前景サービスは動く)

### 色と言語

- 色の辞書 (`Colors.xaml`) の Brand・Neutral・Status の役割に System の色に揃えた値を持ち、チェーンの色に替えない (`ThemeManager` を持たない)
- 文言とサーバの文字 (店舗の名前) は、端末の言語で選ぶ (英語の端末は英語、ほかは日本語)

### 専用端末

テーブル端末と同じ仕組みを使う ([6. 専用端末](#-6-専用端末))。  
アプリの画面 (`MainActivity`) をロックタスクとホームの候補にし、Device Owner の受け口 (`tableorder.terminal.hall/.AdminReceiver`) と管理対象の構成の定義を置く。  
専用端末の一時的な解除は、端末の画面で PIN を確かめて行う。

## 🙋 8. 受付機の作り

| スタッフメニュー | `Staff` | 端末の情報 (店舗、端末の名前、端末の id、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリの版)、端末の設定、専用端末の一時的な解除。情報と操作を 1 列に並べる。5 分操作しなければ、専用端末に戻して待受に戻る |
| 待受 | `Standby` | 上の帯にチェーンの名前とロゴ、店舗の名前、言語 (今の言語を出し、押すと選ぶ。店舗の言語が 1 つなら出さない)。いらっしゃいませ、受付の文言、受付の流れ (人数を入れる、席が決まる、お席へ)、空席の状態 (すぐに案内できる / 満席 / 受付を止めている / 本日の受付の終了 / 開店前は受付の始まる時刻。記号と状態の色)、受付する。受け付けないとき (来店の開き方が受付機でない店、ラストオーダーの後) と、空いているテーブルがひとつもないときは、状態だけを出して受付の流れと受付するを出さない。注文を一時停止している間も受け付け、空席の状態に一時停止の文言 (店舗の文言。なければ既定の文言) を注意の色で添える。言語を選んで受付せずに 60 秒たったら、店舗の初めの言語に戻す |
| 人数 | `Guests` | 受付の段階 (人数)、大人と子ども (小学生以下) を大きな増減のボタンで入れ (はじめは大人 2 人。合わせて 1 人以上)、合計を出す。席を決めるで来店を開いて案内に進む (ラストオーダーを過ぎていたら送らずに、受付の終わりを知らせて待受に戻る)。戻るか、60 秒触らなければ待受に戻る (戻るまでの時間を添える) |
| 案内 | `Guide` | 受付の段階 (ご案内)、決まったテーブルを主色の札にして大きく出し、お席へお進みくださいと人数を添える。人数の入る空席がなかったときは、満席とスタッフが案内することを出す。注文を一時停止している間は、人数の下に一時停止の文言を添える (店舗の通知で出し直す)。閉じるか、15 秒たつと待受に戻る (残りの秒を、減っていく帯と文字で出す)。起動からやり直す知らせを受けたら、案内を消さずに、閉じたときに起動に移る |

- お客様の画面 (待受、人数、案内) は、入口に縦に置いたタブレット (1200x1920) を立って使う受付機に固有の組み方にし、テーブル端末の画面を流用しない。  
  上にチェーンの帯 (印、名前、店舗の名前) を通し、人数と案内の画面はその下に受付の段階の帯を置き、主な操作は画面の幅いっぱいのボタンにして下に置く
- 起動と端末の設定は、テーブル端末と同じ列の組み方のまま縦置きに収める

| ポップアップ | DialogId | 内容 |
| --- | --- | --- |
| 電卓 / 知らせ | `InputNumber` / `Message` (`TerminalDialogId`) | ペアリングコード、スタッフの PIN、失敗の知らせ、受付を止めた知らせ |
| 言語 | `Language` | 言語をその言語の名前で並べ、今の言語に印を付ける (待受の言語のボタンから開く) |

### 遷移

```
起動 ──(登録なし、登録トークンなし)──> 端末の設定 ──登録 / 保存──> 起動
起動 ──(用意ができた)──> 待受
待受 ──受付する──> 人数 ──席を決める──> 案内 (テーブル / 満席) ──閉じる / 15 秒──> 待受
人数 ──戻る / 60 秒触らない──> 待受
人数 ──(受付を止めていた)──> [知らせ] ──> 起動
待受 ──ブランドの印の長押し──> [PIN] ──> スタッフメニュー ──閉じる──> 待受
待受 ──(チェーンと店舗の設定の変更)──> 起動
どの画面 ──(端末の無効化、テナントの停止、接続先の変更の知らせ)──> 起動
```

- 端末の戻るは、待受では何もせず、人数・案内・スタッフメニューでは待受に戻る (アプリの外へ出さない)
- 案内を閉じたときと、人数の画面で触らずに待受に戻ったとき、待受で言語を選んで受付せずに離れたときは、言語を店舗の初めの言語に戻す (次のお客様が初めの言語から始められるように)。  
  人数の画面の戻るでは、選んだ言語のままにする (同じお客様が人数を入れ直すため)
- 待受に戻す時間は、操作の途中 (`BusyState`) なら次の機会に延ばす。  
  人数の画面は、人数を替えるたびに触らなかった時間を数え直す。  
  失敗の知らせを開いたまま時間が来たら、知らせを閉じてから待受に戻す (お客様が知らせを開いたまま離れたとき)
- スタッフメニューは、テーブル端末と同じく、ブランドの印を 3 秒押して PIN (店舗の設定) を入れると開く

### 状態と通知

- 起動で端末の設定 (チェーンと店舗の設定)、店舗の今の状態、空いているテーブルを読み、`OrderEventReceiver` が通知で替える
- 空いているテーブルは、来店の通知 (`visit.opened`、`visit.moved`、`visit.closed`) を受けたら読み直す (`GET /tables?status=Vacant`)。  
  読み直す印は届いたとき (`OnReceived`) に付け、まとめて届いた通知を扱い終えたあと (`OnDrainedAsync`) に、印を下ろしてから 1 回だけ読み直して、表示中の画面に `ShellEvent.VacancyChanged` で知らせる。  
  読み直せなかったときは、待受が入ったときと 30 秒ごとに読み直す (次の来店の通知まで満席のままにしない)
- 空いているテーブルがひとつもなければ、待受を満席にする。  
  人数が定員に入るかは、席を決めるときにサーバが確かめる (入る空席がなければ `NO_VACANT_TABLE` を返し、案内の画面に満席を出す)
- 店舗は通知 (`store.updated`) の中身で替え、表示中の画面に `ShellEvent.StoreUpdated` で知らせる。  
  待受は、設定の版が起動のときに読んだ端末の設定と違えば起動からやり直し (来店の開き方の変更もこれで反映する)、ほかの変化 (ラストオーダーの時刻) は文言を出し直す
- ラストオーダーの時刻を過ぎたかは、待受が 30 秒ごとに店舗のタイムゾーンの時刻で見直す (来店を開いても注文できないので受け付けない。受付機だけで止め、サーバは止めない)
- 来店を開く要求が送れたかわからない (通信できない) ときは、同じお客様が同じ人数で送り直すときに同じ来店の id を送り直す (人数が替われば新しく開く)。  
  残した id は人数の画面に入るとき (次のお客様) に捨て、送り直しで返った来店が開いていなければ (スタッフが閉じたなど) 使わずに新しく開く
- 来店の開き方が替わっていた (`VISIT_OPENING_DISABLED`) ときは、知らせてから起動からやり直す
- 起動からやり直す知らせ (`Restart`) はテーブル端末と同じ

### 色と言語

- チェーンの色は、テーブル端末と同じく起動のときに `ThemeManager` が Brand・Neutral・Status の役割を替える。  
  お客様の画面は、上の帯を補助色、本文を地の色、主な操作と案内のテーブルの札を主色にし、空席の状態は状態の色 (すぐに案内できるは成功、満席は注意) で示す。  
  起動・端末の設定・スタッフメニューは System の役割の色で組む
- 文言とサーバの文字 (チェーンの名前、店舗の名前) は、待受で選んだ言語で出す (選べる言語は店舗の設定の言語)。  
  起動のときは、端末の言語の設定によらず店舗の初めの言語から始める
- 言語を替えたら、待受を作り直して文言を引き直す

### 専用端末

テーブル端末と同じ仕組みを使う ([6. 専用端末](#-6-専用端末))。  
アプリの画面 (`MainActivity`) をロックタスクとホームの候補にし、Device Owner の受け口 (`tableorder.terminal.reception/.AdminReceiver`) と管理対象の構成の定義を置く。  
専用端末の一時的な解除は、スタッフメニューで行う。

## 🍳 9. キッチン端末の作り

厨房・デザート・ドリンクの持ち場に置くタブレット (横向き) のブラウザで開く、Web アプリ (Blazor WebAssembly)。  
サーバが `/kitchen` で配り、接続先はアプリを配ったサーバにする。  
内容で名前の替わらないファイル (index.html、JavaScript の部品、スタイル) は、更新がすぐ届くようにブラウザに毎回確かめさせる (`Cache-Control: no-cache`)。  
起動、端末の設定と登録、端末の画面、チケット (持ち場のタブ、明細の作り始めとできあがり、下げる、下げたチケットと戻す、遅れの色)、品切れと、通知の受け口、新しいチケットの音を作った。  
窓口 (`TableOrder.Client`) は端末のアプリと同じもの (`IDeviceApi`、`IKitchenApi`、`IOrderEvents`) を使う。

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Components/Pages/` | 画面 (`StartupPage`、`SetupPage`、`DevicePage`、`TicketsPage`、`DonePage`、`StockPage`) |
| `Components/Controls/` | 部品 (チケットのカード `TicketCard`、数を入れる `NumberPad`、品の状態を選ぶ `StockEditDialog`、知らせ `MessageDialog`) |
| `Components/Helpers/` | 画面に出す文字の組み立て (`ViewHelper`) |
| `Browser/` | ブラウザの機能を使う部品 (端末の鍵 `BrowserDeviceKey`、`localStorage` の `BrowserStorage`、画面を消さないことと音の `KioskScreen`)。JavaScript の部品は `wwwroot/js/` に置く |
| `State/` | 端末の設定 (`Settings`。`IDeviceContext`)、店舗とメニュー (`StoreState`)、チケット (`TicketState`)、品切れ (`StockState`) |
| `Usecase/` | 登録、チケットの読み直しと操作、品切れの設定 (`KitchenUsecase`) |
| `Shell/` | 通知の受け手 (`KitchenEventReceiver`) と状態の報告 (`StatusReporter`) |
| `Resources/` | 画面の文言 (`Strings/AppResources.resx`、`.en.resx`) |
| `wwwroot/` | 色の役割とスタイル (`css/app.css`)、記号のフォント、JavaScript の部品 |

### 画面

| 画面 | 経路 | 内容 |
| --- | --- | --- |
| 起動 | `/` | 鍵を作れるブラウザか (HTTPS か localhost) を確かめ、トークン、端末の設定、通知の接続のあと、店舗、メニュー (持ち場と品)、品切れ、チケットを読む。キッチン端末として登録されていなければ進まない。失敗したら 30 秒ごとにやり直す |
| 端末の設定 | `/setup` | 接続先 (アプリを配ったサーバ)、今の登録、ペアリングコード (画面の数のボタンで入れる) |
| チケット | `/tickets` | 持ち場のタブ (受け持つ持ち場が 2 つ以上のとき。「すべて」と持ち場ごとに、まだ作り始めていない明細のあるチケットの数を添える) と、チケットを古い順に左から並べる (入らなければ横にスクロールする)。チケットはテーブル、何回目の注文、経過時間、持ち場 (「すべて」のとき)、明細 (数量、名前、オプション、状態)、下げる。下の帯から下げたチケット、品切れ、端末を開く |
| 下げたチケット | `/done` | 直近に下げたチケットを新しい順に並べ、戻す (押し間違い) を置く |
| 品切れ | `/stock` | カテゴリの帯 (品切れ・残り、メニューのカテゴリ、オプション) と品の一覧 (名前、品切れと残りの数)。品を押すと状態を選ぶポップアップ (売れる、残りの数を決める、品切れ) を開き、残りの数は数のボタンで入れる |
| 端末 | `/device` | 端末の情報 (店舗、端末の名前、受け持つ持ち場、端末の id、接続先、音の知らせ、アプリの版) と、端末の設定への入口 |

- 明細を押すと作り始め、もう一度押すとできあがりにする (できあがり・提供済み・取消の明細は押せない)。  
  下げると残りの明細もできあがりになる
- 経過時間は 15 秒ごとに出し直し、店舗の設定の遅れの時間 (`kitchenAlertMinutes`) を過ぎたチケットは見出しを注意の色にする
- 操作を送っている間はボタンを押せなくする。  
  ほかの端末で先に進めていた (`LINE_STATUS_INVALID`、`NOT_FOUND`) ときは、読み直した一覧を出すだけにする
- 選んだ持ち場のタブは、ほかの画面から戻っても保つ (`TicketState`)
- 起動を終える前に途中の画面の URL を開いたとき (読み込み直したときなど) は、その画面を作らずに起動からやり直す (`MainLayout`。画面は起動で読んだメニューなどを使う)
- 物理キーボードを前提にしない (バンプバーは扱わない)。  
  数は画面の数のボタンで入れる

### 状態と通知

- 起動で端末の設定、店舗、メニュー、品切れ、まだ下げていないチケットを読み、`KitchenEventReceiver` が通知で替える。  
  起動で読み終えるまでに届いた通知は、読んだ状態に入っていないこともあるのでためておき、読み終えたあとに届いた順に扱う (起動からやり直す知らせだけはすぐに扱う)
- 通知の重複は接続ごとの seq で捨て、つなぎ直したら数え直す
- チケットの通知 (`ticket.created` / `ticket.updated`) は中身を持たず、届いたら受け持つすべての持ち場のチケットを読み直す (読み直している間に届いた通知は、読み終えたあとに 1 回だけ読み直す)。  
  読み直せなかったら 10 秒後に読み直し、操作のあとの読み直しと重なっても、あとに頼んだ読み直しの応答を古い応答で上書きしない
- 新しいチケット (`ticket.created`) は音で知らせる (続けて届いたときは 3 秒の間を空けて 1 回にまとめる)
- 品切れ (`stock.updated`) は通知の中身で替える
- 設定の版が替わった (`store.updated`)、この端末を替えた (`device.updated`)、通知を追いかけられない (`Expired`)、トークンを断られた (無効化、テナントの停止)、端末の設定で登録し直したときは、アプリを読み込み直して起動からやり直す
- 操作が通ったら、替わった一覧を読み直す (通知でも読み直すが、操作した画面がすぐ替わるように)
- 状態の報告は 1 分ごとに送る (ブラウザは電池を読めないので、アプリの版だけ)

### 端末の鍵と設定

- 端末の鍵は、WebCrypto で取り出せない P-256 の鍵を作り、鍵の組のまま IndexedDB に持つ (`wwwroot/js/device-key.js`)。  
  WebCrypto は安全な接続 (HTTPS か localhost) でしか使えないので、起動で確かめ、使えなければ知らせて止まる
- WebCrypto の署名は r と s を並べた形なので、`DeviceCredentials.ToDerSignature` で窓口の約束の DER にして返す
- 鍵を消すときは IndexedDB の操作を順に並べ、消したあとの操作が消す前の鍵を読まないようにする
- 登録した端末の id は、登録した接続先と組で `localStorage` に持ち、今の接続先と違えば登録していないものとする。  
  端末の名前には、管理画面で見分けられるようにブラウザごとの値を付ける (`Browser XXXX`)

### 色と言語

- スタッフ向けなので、ホール端末と同じく System の色にそろえ、チェーンの色に替えない。  
  色の値は `wwwroot/css/app.css` の `:root` に役割の名前の CSS の変数で持ち、ほかの場所は役割の名前で使う
- 文言はブラウザの言語で選ぶ (英語のブラウザは英語、ほかは日本語)。  
  メニューの名前 (料理、オプション、カテゴリ) と持ち場の名前は、サーバが返す日本語のまま出す (チケットと品切れの画面で同じ名前にする)
- 状態の色はホール端末と同じ使い分けにする (品切れは失敗の色、残りの数と遅れたチケットは注意の色)
- 角丸・影・グラデーションを使わず、記号は Material Icons のグリフにする (端末のアプリと同じ)

### 専用端末

- EMM のキオスクのブラウザで `/kitchen` を開く想定にする (全画面と URL の固定はブラウザに任せる)
- キオスクのブラウザでない (URL の帯が出る) ときは、画面に触れたときに全画面にする (戻るや通知で外れたら、次に触れたときに戻す)
- 画面の Wake Lock を、画面が前に出るたびに取り直して、画面を消さない
- 新しいチケットの音は、ブラウザが許すまで (画面に触れるまで) 出せないので、チケットの画面に知らせの帯を出し、触れたら消す (自動再生を許したブラウザでは出ない)
- 全画面と音は、画面に触れて指を離したとき (`pointerup`) に求める (ブラウザは、タッチの触れ始めを人の操作と認めない)

## 🏭 10. サーバの作り

サーバは、端末が使う API (端末の登録とトークン、店舗・メニュー・品切れ・端末の設定、来店・テーブル・注文・キッチン・提供・呼び出し・会計・支払) と、通知 (SignalR) を作った。  
外部の連携 (OAuth のクライアント、メニューの公開、Webhook) と本物の決済サービスは、これから作る ([plan.md](plan.md))。

### 層

```
端末 ──REST────> Server.Web (Endpoints) ──> Server.Core (Services ──> Accessors ──> SQLite)
端末 <──SignalR── Server.Web (StoreHub <── EventDispatcher) ──> Server.Core (EventService)
                   ├─ 管理画面 (Blazor Server) ──> Server.Core
                   └─ キッチン端末 (KitchenApp、WebAssembly) を /kitchen で配る
```

- 入口 (`Endpoints/`) は要求の形を確かめて Service に渡し、結果を応答にするだけにする
- Service は `TableOrder.Contract` の Request を受けて Response を返し、Accessor は 2-way SQL (`Accessors/Sql/`) で DB を読み書きする
- 入力の誤りと業務の失敗は、Service が `ServiceError` (`errorCode` と項目ごとの理由) で返し、入口が `ApiProblems` で HTTP の状態と Problem Details にする
- データベースは SQLite で、`Assets/Data/Schema.sql` を起動のたびに実行して [database.md](database.md) のすべての表を作る

### テナントの文脈

- 認証のあと、アクセストークンのクレーム (`tenant_id`、`store_id`、`device_kind`、`table_id`、`station_ids`) から要求の文脈 (`ServiceContext`) を作り、Service はそこからテナントと店舗を受け取る
- Accessor はテナントを持つ表を引数の `tenantId` で絞り、すべての SQL がテナントで絞っていることをテスト (`SqlTenantConditionTests`) で確かめる
- テナントのわからない要求 (端末の登録、トークンの要求) で引くのは `DirectoryAccessor` だけで、引いた行のテナントで続ける
- テナントをまたぐ裏の処理 (通知の送り手の見回り、古いデータの消去、すぐに拒む一覧の読み直し) は `BackgroundAccessor` に置き、店舗の通知を読むときは店舗の文脈を始めてから Service を呼ぶ
- ログの全行に、テナント・店舗・主体 (端末) を付ける。  
  要求の外 (裏の処理、管理画面の回線) は、始めている業務の文脈からテナントと店舗を付け、店舗ごとの裏の処理の失敗はテナントと店舗を入れて記録する
- HTTP のログに本文を出す設定 (`Log:HttpDump`) でも、秘密を運ぶ API (登録、トークン、端末の設定) の本文は出さない。  
  利用者はメールアドレスではなく Id で記録する

### 端末の認証

| 段階 | API | 作り |
| --- | --- | --- |
| 登録 | `POST /api/v1/devices/pair` | ペアリングコード (か登録トークンのハッシュ) で受け口を引いてアプリの端末の種類と比べ、店舗の書き込みの中で台数を数えてから端末と公開鍵 (P-256 の JWK。座標は読み直した値で書く) を記録する。使わなくした店舗には登録せず、使わなくしたテーブルには置かない。接続元ごと (IPv6 は /64 ごと) に 1 分の回数を限り、超えたら `429` に `Retry-After` を付ける |
| トークン | `POST /api/v1/devices/token` | 端末の鍵で署名した使い捨ての JWT を確かめ (期限 5 分以内、jti は使い捨て)、端末の記録からアクセストークン (ES256、30 分) を作る。同じ鍵の前の登録 (登録し直す前の端末) は、ここで無効にして前の店舗に `device.updated` を送る |
| 要求 | `Authorization: Bearer` | JwtBearer で署名と期限を確かめ、端末の種類のポリシーで使える API を絞る (範囲の外は `403` `DEVICE_SCOPE`)。`401` には失敗の理由 (期限切れ、署名の誤り) を付けない |

- 署名の鍵は設定 (`Token:SigningKey`。P-256 の秘密鍵の PEM) から読み、開発の環境で空なら起動のたびに作る
- 端末を無効にしたときとテナントを止めたときは、次のトークンを出さない (`DEVICE_REVOKED`、`TENANT_SUSPENDED`)
- 出したトークンも、すぐに拒む一覧 (`RevocationList`。無効にしてからトークンの期限を過ぎるまでの端末と、止めたテナント) で断る (`401`)。  
  JwtBearer がトークンを確かめたあとに一覧を引き (要求ごとにデータベースは引かない)、通知のハブはつないだ端末を覚えて (`StoreHubConnections`) 一覧に入った接続を切る。  
  端末はトークンを取り直して断られ、無効にした端末は登録からやり直し、止めたテナントの端末は再開を待つ
- 一覧は、端末を無効にする・テナントを止める・戻す Service が替えたあとに読み直させ (`IRevocationList`)、裏の処理 (`RevocationWorker`) も一定の間隔 (`Token:RevocationSweepSeconds`) で読み直す (ほかのサーバで替えたものも数秒で断る)
- ハブはトークンの期限が来た接続も切り、端末は新しいトークンでつなぎ直す

### 書き込みと通知

- 店舗の状態を変える書き込みは `EventService.WriteAsync` の中で行う。  
  最初に店舗の通し番号の行 (`EventSequences`) をとって店舗の書き込みを 1 つずつにし、変えた内容の通知を同じトランザクションで `Events` に書く (コミットしなければ通知も捨てる)
- コミットしたら、Core は通知の増えた店舗だけを `IEventPublisher` で知らせ、Web の送り手 (`EventDispatcher`) が店舗ごとに `seq` の順で読んでハブ (`StoreHub`) のグループに送る
- 送り手は一定の間隔 (`Event:SweepSeconds`) ですべての店舗の通し番号も見て、ほかのサーバが書いた通知を送る (サーバを並べても、どのサーバにつながる端末にも届く)。  
  見回りは知らせの合間ではなく前の見回りから間隔ごとに行い (知らせが続くサーバでも止まらない)、1 つの店舗で送れなくてもほかの店舗には送る (送れなかった店舗は次の見回りで送り直す)。  
  起動より前の通知は送らず、端末がつなぎ直したときに `GET /events` で受け取る
- ハブのグループは端末の種類と置き場所 (テーブル、持ち場) ごとに作り、名前にテナントと店舗を入れる (持ち場の `id` はメニューごとなので、ほかの店舗と重なりうる)。  
  通知の種類ごとの送る先 (`EventRoutes`) は、ハブの送り分けと `GET /events` の絞り込みで同じものを使う
- ハブは端末をグループに入れ終えたら `ready` で店舗の今の通し番号を送る。  
  端末ははじめはその番号から数え (このあとに今の状態を読む)、つなぎ直したときは抜けた通知を読む (グループに入る前に届いた通知を取りこぼさない)。  
  つなぎ直したときに `ready` より前に届いた通知では番号を進めず、抜けた通知と合わせて渡す
- 管理画面で端末の置き場所・名前を替えたときと無効にしたときは、店舗のすべての端末に `device.updated` を送り、その端末だけが起動からやり直す
- 送り手は店舗の通知を送ったら、サーバの中でその店舗を見ている画面 (`StoreActivity`。管理画面の店内の今) にも知らせる (ほかのサーバが書いた通知も送るので、どのサーバで開いた画面にも届く)
- 古いデータ (残す時間 (24 時間) を過ぎた通知、期限を過ぎたペアリングコード、期限を過ぎるか取り消してから 1 日たった登録トークン) は、掃除の裏の処理 (`CleanupWorker`) が `Event:CleanupMinutes` ごとに消す

### 管理画面

管理画面 (Blazor Server) は、サインインしてから、上の帯でテナントと店舗を選んで使う。  
選んだテナントと店舗 (`StoreSelection`。回線の間だけ覚える) は、画面から Service を呼ぶときの文脈 (`BlazorServiceScope`) に入れ、API と同じ Service をその店舗の文脈で呼ぶ。

| 項目 | 作り |
| --- | --- |
| サインイン | 利用者 (`AdminUsers`) をデータベースに持ち、ASP.NET Core Identity の部品 (`UserManager`、`SignInManager`、パスワードのハッシュ、ロックアウト、認証アプリのコード) を、自前の置き場 (`AdminUserStore` から `AccountService`) で使う。パスワードは 12 文字以上、5 回続けて間違えたら 15 分止める。間違えた回数と止める時刻は、資格情報の版を見ずに 1 文で書く (同時に間違えても数え漏らさない)。サインインと多要素のコードの送信は、接続元ごとに 1 分の回数を限る (`RateLimit:SignInPerMinute`) |
| 確かめ方 | 既定の確かめ方を経路で選び (`/api` と `/hubs` は端末のアクセストークン、ほかは Cookie)、端末の API に Cookie を通さない。Cookie は 8 時間 (使えば延ばす) で、ほかのサイトからの遷移では送らない |
| 役割 | 運営者・テナントの管理者・店舗の担当。クレーム (役割、テナント、受け持つ店舗) から回線ごとの範囲 (`AdminScope`) を作り、選べるテナントと店舗を絞る (範囲の外は選んでも文脈にしない)。開ける画面はポリシー (`AdminPolicies`) で絞る |
| やり直させる | 資格の印 (`SecurityStamp`) を Cookie と開いている回線のどちらも 1 分ごとに確かめ、替わっていたか止めた利用者・止めたテナントならサインインからやり直させる。止めた利用者・止めたテナントの利用者には Cookie を出し直さず (パスワードの変更など)、止めた利用者の資格情報は書かない。資格の印は扱える範囲と資格情報 (役割、受け持つ店舗、パスワード、多要素、止める) を替えたときに替え、名前だけなら替えない。回線は Cookie を延ばさないので、始めてから Cookie の期限 (8 時間) を過ぎたらやり直させる |
| 多要素 | 認証アプリのワンタイムコード。鍵は文字で出し、データ保護で暗号にして持つ。回復用のコードも鍵と同じくデータ保護で暗号にして持つ (DB だけが漏れても使えない)。使い始めは回復用のコードを書いてから、外すときは鍵とコードを捨てるのと 1 回で書き、書けなかったら Cookie を出し直さずに知らせる |
| 仮のパスワード | 管理者が利用者を足すときと出し直すときに、管理画面で作ってハッシュにし (Service には平文を渡さない)、平文は一度だけ見せる。仮のパスワードでサインインしたら、パスワードを替えるまでほかの画面 (アカウントと多要素の画面も) を開かず、今のパスワードと同じものには替えさせない |
| 利用者の管理 | テナントの利用者は `AdminUserService` (選んだテナントで絞る)、運営者は `OperatorService` で替える。メールアドレスはすべてのテナントで一意にし、足すときに形を確かめる (利用者名に使うので、Identity の文字の制限は使わない)。自分の役割は替えず、自分は止めない |
| テナントの管理 | 登録と止める・戻すは `TenantService`。止めると、テナントの利用者の資格の印を替えて開いている管理画面をやり直させ、端末の登録とトークンを断る |
| 店舗の管理 | `StoreSetupService`。新しい店舗の設定 (言語、支払方法、電子レシート、機能、呼び出しの用件、今のメニュー) は選んだ店舗から写し、写さないときは既定の設定 (電子レシートは出さない) とサンプルのメニュー (外部の連携でメニューを公開するまでの仮) にする。基本を替えたら設定の版を上げて `store.updated` を送る。使わなくするのは使っている端末と開いている来店がないときだけで、使わなくした店舗には端末を登録しない |
| テーブルの管理 | `TableSetupService`。追加・変更・並べ替え・使わなくするたびに店舗の設定の版を上げて `store.updated` を送り、端末は起動からやり直してテーブルを読み直す。使わなくするのは来店中でなく、端末を置いていないときだけ |
| 登録トークン | `DeviceEnrollmentService`。店舗と端末の種類に限り、台数 (1~1000) と期限 (1~30 日) を決めて出す。トークン (32 バイトの乱数) は、出した画面で接続先と並べて一度だけ見せ、ハッシュだけを持つ。取り消すと、それからの登録を断る (登録した端末はそのまま)。登録した端末は、置き場所を割り当てるまで待つ |
| すぐに拒む一覧 | 端末を無効にしたとき (`DeviceService`) とテナントを止めた・戻したとき (`TenantService`) に読み直し、端末の今のトークンと通知の接続を断つ ([端末の認証](#端末の認証)) |
| 初めの運営者 | 運営者がいなければ、起動のときに設定 (`Admin:InitialOperatorEmail`、`Admin:InitialOperatorPassword`) で作る (仮のパスワード) |

サインイン・多要素のコード・パスワード・多要素の登録の画面は Cookie を書くので、対話しない静的な画面 (`[ExcludeFromInteractiveRouting]`) にし、サインアウトはフォームの POST (`/account/sign-out`。偽造防止の値を確かめる) で受ける。

| 画面 | できること |
| --- | --- |
| サインイン (`/account/sign-in`) | メールアドレスとパスワード。多要素を使う利用者は、続けて認証アプリのコードか回復用のコード (`/account/sign-in-2fa`)。どこを間違えたかは分けて出さない |
| アカウント (`/account`) | 名前、役割、多要素の状態と、パスワードの変更 (`/account/password`)、多要素の登録と外す・回復用のコードの出し直し (`/account/two-factor`)、サインアウト |
| ダッシュボード (`/`) | 扱えるテナント (運営者) か店舗 (テナントの利用者) の一覧 |
| 端末 (`/devices`) | 店舗の端末の一覧 (種類、置き場所、最後の通信、電池、アプリの版、有効か。置き場所の割り当てを待つ端末を先に出す)、ペアリングコードの発行 (種類と置き場所を決める。10 分、1 台)、登録トークンの発行 (種類、台数、期限。管理対象の構成のキー (`apiEndPoint`、`enrollmentToken`) と値を一度だけ見せる) と一覧・取り消し、置き場所の割り当てと名前の変更、無効化 |
| チェーン (`/brand`) | チェーンの名前 (日本語、英語)、ロゴ (置いた画像から選ぶ)、色 (役割ごと。空なら端末の既定の色)。運営者とテナントの管理者だけが開ける |
| 利用者 (`/users`) | 選んだテナントの利用者 (テナントの管理者と店舗の担当) の一覧、追加 (仮のパスワードを一度だけ出す)、名前・役割・受け持つ店舗の変更、仮のパスワードの出し直し、多要素を外す、止める・戻す。運営者とテナントの管理者だけが開ける |
| 店舗 (`/stores`) | 選んだテナントの店舗の一覧、追加 (店舗コード、名前、タイムゾーン、営業時間、ラストオーダー、税の丸め、注文の上限、スタッフの PIN、設定を写す店舗)、基本の変更、使わなくする・使う。運営者とテナントの管理者だけが開ける |
| テーブル (`/tables`) | 選んだ店舗のテーブルの一覧 (並び、名前、エリア、席の数、置いた端末、状態)、追加、変更、並べ替え (前後と入れ替える)、使わなくする・使う |
| テナント (`/tenants`) | テナントの一覧 (コード、会社の名前、チェーンの名前、使っている店舗の数、状態)、登録、止める・戻す (確かめてから)。運営者だけが開ける |
| 運営者 (`/operators`) | 運営者の一覧、追加、名前の変更、仮のパスワードの出し直し、多要素を外す、止める・戻す。運営者だけが開ける |
| 店舗の設定 (`/store-settings`) | 来店の開き方 (スタッフ、受付機、席)、機能の有無 (レジで払う、割り勘、ラストオーダーの知らせ、お礼の時間、キッチンの遅れの時間)、言語、支払方法、電子レシート (テーブルで払い終えた来店に作り、お礼の画面に QR を出す)、呼び出しの用件 (使うものを選ぶ)、スタッフの PIN (入れたときだけ替える) |
| 店内の今 (`/floor`) | テーブルの一覧 (空き・来店中・会計中、人数、経過時間、まだ出していない品、呼び出し)、押したテーブルの来店 (人数、注文と明細の状態、注文の額)、終わっていない呼び出し (用件の名前)、品切れと残りの数 (メニューの名前)、通知の記録 (直近の通知の種類と時刻)。空いているテーブルは来店を開き (人数)、来店は閉じる (レジで払った。お願いしていない食後の品があれば、閉じると作らないことを確認で知らせる)・取りやめ (注文のないまま帰った) |

- 店内の今は、ホール端末が使えないときに来店を開き・閉じる画面を兼ね、ホール端末の API と同じ `VisitService` を呼ぶ (テーブル端末には同じ通知が届く)
- 店内の今は、選んだ店舗の通知を送るたびに (`StoreActivity`) 少し待ってから読み直し、読み直しても選んだテーブルと入れている人数は替えない
- チェーンと店舗の設定を替えると、設定の版 (`Stores.SettingsVersion`。チェーンの設定はテナントのすべての店舗) を上げて `store.updated` を送る。  
  テーブル端末は待受で起動からやり直して反映する
- どの環境でも開き、サインインの画面のほかはサインインを求める (API の説明 (Swagger UI) は開発の環境だけ)

| `POST /api/v1/payments/callbacks/fake` | 匿名 (開発の環境だけ) | 仮の決済サービスの結果の通知 |
| `GET /api/v1/events?after=` | すべて | 抜けた通知 (端末の種類と置き場所に合うもの) |
| `/hubs/store` (SignalR) | すべて | 通知 (`event`) と、グループに入れ終えた知らせ (`ready`。店舗の今の通し番号) |

### 画像

- 画像 (料理の写真、チェーンのロゴ) はテナントごとの置き場 (`IImageStore`) に名前で置き、`ImageService` が名前を確かめて返す。  
  開発とテストはファイル (`FileImageStore`。実行のフォルダの `images/{テナント}/`。設定 `Image:Directory`)、本番は Amazon S3 にする
- 名前は内容が変わると変わる (内容のハッシュを入れる) ので、置いた画像は替えない。  
  名前の決まり (英小文字・数字・`-`・`_`・`.`、拡張子) は `TableOrder.Domain.ImageNames` にあり、端末も保存の前に同じもので確かめる

### 決済と開発の環境の自動の進行

- 決済サービスは `IPaymentProvider` の実装で替える。  
  今は仮の決済サービス (`FakePaymentProvider`) で、QR の内容を作り、結果は開発の環境の通知 (`POST /api/v1/payments/callbacks/fake`) か自動の進行で受ける
- 開発の環境では、スタッフ (キッチン、ホール) と決済サービスの代わりに、サーバが時間で進める (`Simulation` の設定。テストでは止める)。  
  明細は注文 (食後の品はお願い) からの時間で作り始め・できあがり・提供と進め、明細がそろったチケットは下げる。  
  払い終えて閉じた来店の品も進める (キッチンは作り続け、ホールはお席に運ぶ)。  
  呼び出しには向かってから対応を終え、待っている支払は払い終える
- ホール端末で提供と呼び出しを確かめるときは、サーバが先に進めないように、提供と向かうまでの秒 (`Simulation:ServedSeconds`、`Simulation:AcknowledgeSeconds`) を長くして起動する
- 進めるもののある店舗をテナントをまたいで探し (`BackgroundAccessor`)、店舗ごとに文脈を始めて `SimulationService` を呼ぶ (業務の処理と同じ書き込みと通知で進める)

### 動かし方

- `dotnet run --project server/src/TableOrder.Server.Web` で、8080 番で受ける (開発の環境は Swagger UI を `/swagger` に出す)。  
  テレメトリと一緒に動かすときは、Aspire の `server/src/TableOrder.Server.AppHost` を起動する
- スキーマは `CREATE TABLE IF NOT EXISTS` で作るので、表に列を足したときは開発の DB (実行のフォルダの `data.db`) を消して作り直す
- 開発の環境ではサーバが調理・提供・呼び出し・支払を時間で進めるので、テーブル端末だけで注文から会計までを確かめられる
- テーブル端末をつなぐときは、端末の設定で接続先を開発のサーバ (エミュレータからは `http://10.0.2.2:8080`) にし、ペアリングコード (`100001`) で登録する
- 受付機で受け付けるときは、管理画面の店舗の設定で来店の開き方を受付機にする (サンプルのデモの店舗はスタッフなので、そのままでは受付機の待受に受付を止めている文言が出る)
- 管理画面 (`/`) は、サンプルの利用者 (`operator@example.com` などと `tableorder-dev`) でサインインして開く。  
  端末の画面 (`/devices`) でペアリングコードを出せば、サンプルの決まったコードのほかにも端末を登録できる
- 本番の環境では、初めの運営者のメールアドレスと仮のパスワード (`Admin:InitialOperatorEmail`、`Admin:InitialOperatorPassword`) を秘密の値で渡して起動する
- キッチン端末は `/kitchen` を開き、ペアリングコード (`100201`) で登録する (端末の鍵に WebCrypto を使うので、HTTPS か localhost で開く)
