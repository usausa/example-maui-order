## 📦 1. プロジェクト

モノレポにし、区分ごとのフォルダの `src/` にプロジェクト、`tests/` にテストを置く。  
ソリューションは区分ごとに分ける。

| 区分 | フォルダ | 内容 | ソリューション |
| --- | --- | --- | --- |
| 共有 | `shared/` | サーバ・端末・Web アプリが共に使うもの | なし |
| サーバ | `server/` | 注文サーバと、サーバが配信する Web アプリ | `server/TableOrder.Server.slnx` |
| テーブル端末 | `table/` | お客様がテーブルで使う端末のアプリ (.NET MAUI、Android) | `table/TableOrder.TableApp.slnx` |
| ホール端末 | `hall/` | スタッフが使う端末のアプリ (.NET MAUI、Android) | `hall/TableOrder.HallApp.slnx` |
| 受付機 | `reception/` | 店の入口に置く端末のアプリ (.NET MAUI、Android) | `reception/TableOrder.ReceptionApp.slnx` |
| 端末に共通の部品 | `terminal/` | 端末のアプリが共に使う部品。.NET MAUI の Android のライブラリで、画面 (`ViewId`) は持たない | なし |

- 区分で分けるのは、ビルドに要るもの (端末は Android のワークロード) と設定が違うため。  
  サーバの区分は Android なしでビルドできる
- 端末のアプリは用途ごとに区分を分け、1 つの区分に用途の違うアプリを混ぜない
- 共有のプロジェクトは、画面・端末・サーバに依存しない。  
  業務のルールと通信データは .NET の標準のライブラリだけを使い、API クライアントは SignalR のクライアントも使う
- 共有と端末に共通の部品は、単独のソリューションを持たず、使う区分のソリューションに入れて検証する。  
  単独にすると、アプリだけが使う型を InspectCode が使われていないと指摘するため
- 共有のプロジェクトと共有のテストは、共有の型をいちばん使うテーブル端末のソリューションに入れる
- 端末に共通の部品は、使っているテーブル端末、ホール端末、受付機のソリューションに入れる

| プロジェクト | 種類 | 内容 |
| --- | --- | --- |
| `shared/src/TableOrder.Domain` | .NET | 業務の値 (列挙型) と計算。サーバと端末で同じ計算を使う |
| `shared/src/TableOrder.Contract` | .NET | 通信データ (`XxxRequest` / `XxxResponse`、`LocalizedText`) |
| `shared/src/TableOrder.Client` | .NET | 端末と Web アプリが使う API クライアントと、注文サーバの実装 |
| `terminal/src/TableOrder.Terminal` | .NET MAUI (Android のライブラリ) | 端末に共通の部品 |
| `table/src/TableOrder.TableApp` | .NET MAUI (Android) | テーブル端末のアプリ |
| `hall/src/TableOrder.HallApp` | .NET MAUI (Android) | ホール端末のアプリ |
| `reception/src/TableOrder.ReceptionApp` | .NET MAUI (Android) | 受付機のアプリ |
| `server/src/TableOrder.Server.Core` | .NET | 業務の処理 (端末の登録と認可、店舗、メニュー、品切れ) と DB の読み書き (Accessor と 2-way SQL) |
| `server/src/TableOrder.Server.Web` | ASP.NET Core | エンドポイント (REST)、端末の認証、管理画面 (Blazor Server)、キッチン端末の配信 |
| `server/src/TableOrder.Server.AppHost` | Aspire | 開発で動かす構成 (サーバとテレメトリ) |
| `server/src/TableOrder.KitchenApp` | Blazor WebAssembly | キッチン端末の Web アプリ |
| `shared/tests/TableOrder.Domain.Tests` | .NET (xunit) | `Domain` の計算と、`Domain` がほかの層に依存しないことのテスト |
| `shared/tests/TableOrder.Client.Tests` | .NET (xunit) | 端末の鍵の値の変換、通知の数え方、`Client` が画面・端末・サーバに依存しないことのテスト |
| `server/tests/TableOrder.Server.Core.Tests` | .NET (xunit) | すべての SQL がテナントで絞っていることと、DB の型の変換のテスト |
| `server/tests/TableOrder.Server.Web.Tests` | .NET (xunit) | API と通知のハブのテストと、端末のアプリの API クライアント (`TableOrder.Client` の REST と SignalR) をサーバにつないだテスト |

```
TableOrder.{Table|Hall|Reception}App ──> TableOrder.Terminal ──> TableOrder.Client ──> TableOrder.Contract ──> TableOrder.Domain
TableOrder.KitchenApp ──> TableOrder.Client
TableOrder.Server.Web ──> TableOrder.Server.Core ──> TableOrder.Contract
          └──> TableOrder.KitchenApp
```

- `TableOrder.Domain` の計算: 金額と内税、割り勘の目安、タグのルールの数え方、ラストオーダーの判定
- `TableOrder.Client` の内容
  - API クライアント: 全端末に共通の `IDeviceApi`、端末の種類ごとの `ITableApi`・`IHallApi`・`IReceptionApi`・`IKitchenApi`、通知の `IOrderEvents`、`ApiResult`
  - 注文サーバの実装: `Rest/` のリクエスト、`SignalR/` の通知
  - 端末の鍵の値を API の形にする変換 (`DeviceCredentials`)
- `TableOrder.Client.Tests` の通知の数え方: 再接続でためた通知と欠落した通知の合わせ方、接続の作り直し。  
  API クライアントの動きは、サーバのテストで実際のサーバにつないで確認する
- `TableOrder.Server.Web.Tests` の API と通知のハブのテスト: 端末の登録とトークン、端末のアプリと同じ形の鍵での登録、端末の種類の範囲、テナントで分けられていること、来店から会計までの API、通知の送信先と欠落した通知

`TableOrder.Terminal` の部品:

| 部品 | 場所・型 |
| --- | --- |
| 端末の情報、鍵、専用端末、EMM の設定、クラッシュレポート | `Components/`、`Diagnostics/` |
| 端末の設定と状態、起動の準備 (`StartupState`)、スタッフの PIN | `State/` |
| 登録と状態の報告 | `Usecase/` の `DeviceUsecase`、`Shell/` の `StatusReporter` |
| 通知のレシーバの基底クラス | `OrderEventReceiverBase` |
| ビジーオーバーレイ | `ShellProperty` |
| スタッフメニューを開く長押しの時間 | `AppGestures` |
| どの端末でも同じポップアップ (電卓、メッセージ、確認) と、それを開くメソッド (PIN の確認を含む) | `Modules/` |
| ポップアップと遷移のプラグイン | `Extender/` |
| 添付プロパティ (タップできる行とタイルのリップルとクリックの `TouchOption` など) | `Behaviors/` |
| System の色と共通のスタイル | `Resources/Styles/` の `SystemColors`、`TerminalStyles` |
| 文言 | `TerminalResources` |
| 画面に収める幅 | `TerminalSizes` |
| お客様の画面の端末 (テーブル端末、受付機) に共通の部品 | チェーンの色 `ThemeManager`、画像の保存 `ImageCache`、チェーンの印 `BrandMark`、言語 `LanguageState` |
| DI の登録 | `AddTerminalComponents`、`AddCustomerComponents` |

- `AddTerminalComponents` は、端末の種類の `TerminalOptions` と、専用端末の型の `KioskOptions` を受ける
- お客様の画面の部品は `AddCustomerComponents` で登録し、アプリの文言のカルチャを切り替える `LanguageOptions` を受ける

### 名前の付け方

| 区分 | 名前 (アセンブリ、ルートの名前空間、フォルダ) |
| --- | --- |
| 共有 | `TableOrder.{Domain\|Contract\|Client}` |
| サーバ | `TableOrder.Server.{Core\|Web\|AppHost}` |
| アプリ (店の端末とブラウザで動く) | `TableOrder.{Table\|Hall\|Reception\|Kitchen}App` |
| 端末に共通の部品 (.NET MAUI のライブラリ) | `TableOrder.Terminal` |
| テスト | 区分の `tests/` に `{プロジェクト名}.Tests` |

- 店の端末とブラウザで動くアプリは `{用途}App` にし、サーバはプロジェクトの役割 (`Core`、`Web`、`AppHost`) で名前を分ける
- フォルダの区分はビルドの単位で決める。  
  サーバが配信する Web アプリ (`TableOrder.KitchenApp`) は `server/` に置く
- 名前空間は、アセンブリの名前にフォルダのパスを続ける (`TableOrder.TableApp.Modules.Menu` など)
- 1 つの型を 1 つのファイルに置き、ファイル名を型の名前にする
- Android だけの部分は `Xxx.android.cs` にする
- 端末の画面は `Modules/{画面}/{画面}View.xaml` と `{画面}ViewModel.cs` にする
- 端末の API クライアントは、端末の種類ごとに `I{種類}Api` にする (テーブル端末は `ITableApi`、ホール端末は `IHallApi`、キッチン端末は `IKitchenApi`、受付機は `IReceptionApi`)。  
  端末の登録と設定 (`IDeviceApi`) と通知 (`IOrderEvents`) は共通にする
- 実装は、通信の方式を名前の前に付ける (`RestDeviceApi`、`Rest{種類}Api`、`SignalROrderEvents`)
- MAUI の `MenuItem` とぶつかるので、メニューの品の型は `MenuProduct` などにする

サーバのファイルの名前は、template-maui-server に合わせる。

| 対象 | ファイル |
| --- | --- |
| エンドポイント | `Endpoints/{リソース}Endpoints.cs` |
| 業務の処理 | `Services/{リソース}Service.cs` |
| データ | `Accessors/{リソース}Accessor.cs`、`Accessors/Sql/{リソース}Accessor.{メソッド}.sql` |
| 行 | `Models/Entity/{テーブル}Entity.cs` |

## 🧱 2. テーブル端末の実装

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Modules/` | 画面とポップアップの View と ViewModel (`Startup`、`Setup`、`Staff`、`Standby`、`Menu`、`Checkout`、`Dialogs`) |
| `State/` | 画面をまたぐ状態 (`MenuState`、`VisitState`、`CartState`、`StoreState`) |
| `Usecase/` | 通信と状態の更新を組み合わせる手順 (`OrderUsecase`。来店の開始と終了、メニューのルールの判定、注文の送信) |
| `Models/` | 画面で使う形 (`MenuCategory`、`MenuProduct`、`CartLine`、`ItemSelection`、`OrderedLine`) |
| `Controls/` | 表示の部品 (`QrCodeView`。QR コードの代わりのパターン) |
| `Markup/` | アイコン (`AppIcons`) |
| `Resources/` | 色 (`Colors.xaml`。Brand・Neutral・Status の役割)、テーブル端末のスタイル (`Styles.xaml`)、画面の文言 (`Strings/AppResources.resx`、`.en.resx`)、アイコンのフォントとグリフの表、アプリのアイコン、スプラッシュ |
| `Shell/` | 通知のレシーバ (`OrderEventReceiver`) と、画面へのイベント (`ShellEvent`) |
| `Platforms/` | Activity、Device Owner のレシーバ、マニフェスト |

- 画面へのイベントは、MainPage と通知のレシーバが出す。  
  種類は、戻る、来店の開始・終了、店舗の変更、送れたかわからなかった注文の受け付け、起動からやり直す
- 端末に共通の部品とお客様の画面の部品は、`TableOrder.Terminal` のものを使う ([1. プロジェクト](#-1-プロジェクト))
- `MauiProgram` で `AddTerminalComponents` と `AddCustomerComponents` を呼んで登録し、次のものを渡す
  - `TerminalOptions`: 登録で送る端末の種類
  - `KioskOptions`: 専用端末の制限に使う Device Owner のレシーバとホームの画面
  - `LanguageOptions`: 言語を切り替えるときに、テーブル端末の文言のカルチャを切り替える処理
- 共通のポップアップの ID (`TerminalDialogId`) と View の組は、ポップアップの登録に `TerminalModules.DialogSource` を足して入れる
- `App.xaml` には、色とスタイルを次の順に入れる
  1. テーブル端末の色 (`Colors.xaml`)
  2. `TableOrder.Terminal` の共通のスタイル (`TerminalStyles`。System の色 `SystemColors` を中に入れる)
  3. テーブル端末のスタイル (`Styles.xaml`)
- 共通のスタイルは、チェーンで変わる役割の色を、テーブル端末の色から `DynamicResource` で引く

### 層

```
View (XAML) ──> ViewModel ──> Usecase ──> IDeviceApi / ITableApi (Client)
                    │            │
                    └────────────┴──> State (Settings / MenuState / VisitState / CartState / LanguageState / StoreState / StaffLock)

IOrderEvents / IDeviceApi.Denied・Authorized (Client) ──> OrderEventReceiver (Shell) ──> State、表示中の画面への知らせ (ShellEvent)
StatusReporter (Terminal) ──> DeviceUsecase (Terminal) ──> IDeviceApi (1 分ごとの状態の報告)
```

- ViewModel は State を読む。  
  いくつかの画面が使う手順 (来店の開始と終了、メニューのルールの判定、注文の送信) は、Usecase に任せる
- 読むだけの通信と、1 つの画面だけが使う手順は、ViewModel から `ITableApi` を呼ぶ (お会計の会計の開始・取りやめと支払、注文履歴の食後の品のお願い)
- 通信の結果は `ApiResult<T>` で受け、例外にしない。  
  失敗は `ViewHelper.ErrorMessage` でお客様向けの文言にし、`Log.WarnApiFailed` で記録する
- ポップアップとの受け渡しは、引数と戻り値で行う。  
  ポップアップは、閉じると ViewModel ごと破棄する
- ポップアップを開いている間は、下の画面を非アクティブにする (コマンドを受けない)。  
  重ねたポップアップがすべて閉じたら戻す (`PopupActivationPlugin`)
- ポップアップの ViewModel も、閉じ始めたらコマンドを受けない
- 料理の写真とチェーンのロゴは、`ImageCache` (`TableOrder.Terminal`) が端末に保存し、画面は保存したファイルを出す
  - 写真を保存していない間は、面の色の上にチェーンのロゴかアイコンを出す
  - 起動のときに、足りない画像をまとめてダウンロードする (同時に 4 つまで)
  - 今のメニューで使わなくなった画像は削除する
  - ダウンロードできなかった画像は、待受に戻ったときに再取得する
  - 保存先は登録ごとのフォルダに分け、再登録したら前のフォルダを削除する
- サーバの通知は `OrderEventReceiver` が受けて状態を更新し、表示中の画面に `ShellEvent` で伝える。  
  操作の途中 (Busy) と遷移の間は、終わるまで待つ
- 受け方は、`TableOrder.Terminal` の `OrderEventReceiverBase` が持つ (接続ごとの seq で重複を捨てる、操作と遷移の間を待つ、起動からやり直すイベント)。  
  `OrderEventReceiver` は、来店・店舗・品切れ・注文の通知の扱いだけを持つ
- 通知への対応は、各画面が決める
  - 待受: 注文の画面へ
  - 注文: 待受へ
  - お会計: お礼へ
  - 人数・会計中・売り切れ: 表示を更新する
- 来店が終わってから画面が来店を終えるまで (お礼の間、スタッフメニューの間) に、同じテーブルで開いた次の来店は `VisitState.Next` に残す (移ってきた来店も)。  
  来店を終えたら続けて次の来店を開き、待受に戻さずに注文の画面にする (お礼の間に、受付機やスタッフが次のお客様を案内したとき)
- 次のときは、`OrderEventReceiver` が開いているポップアップを閉じて `ShellEvent.Restart` を出し、表示中の画面が起動からやり直す
  - 端末が使えなくなった (無効化、テナントの停止)
  - 管理画面で端末を変更した (`device.updated`)
  - EMM が接続先を変更した
  - 通知を追跡できなくなった
- 起動と端末の設定の画面は、自分で確認するので `Restart` を受けない。  
  ポップアップ (PIN や登録の入力) も閉じない
- 受けない画面の間に届いたイベントは残し、受ける画面に移ってから起動からやり直す (起動の途中に届いた端末の変更を捨てない)
- ただし拒否の通知 (無効化、テナントの停止) は、そのあとにトークンを受け取れたら (起動の画面で回復したら) やり直さない。  
  回復したあとに、もう一度起動しないため
- 管理画面でチェーンや店舗の設定を変更すると、設定のバージョン (`settingsVersion`) が上がって `store.updated` が届く
- 待受は、バージョンが起動のときに読んだ端末の設定と違えば、起動からやり直して再読み込みする (来店の途中の画面では切り替えない)。  
  待受に入ったときにも、バージョンを確認する

## 📱 3. 画面

### 画面とポップアップ

| 画面 | ViewId | 内容 |
| --- | --- | --- |
| 起動 | `Startup` | システムのロゴ、準備の進捗、失敗のときの再試行と設定。テーブルの割り当て待ちとテナントの停止もここに出す |
| 端末の設定 | `Setup` | 接続先 (注文サーバの URL)、今の接続先での登録、ペアリングコード (電卓) |
| スタッフメニュー | `Staff` | 端末の情報、端末の設定、専用端末の一時的な解除。5 分操作しなければ、専用端末に戻してお客様の画面に戻る |
| 待受 | `Standby` | チェーンの名前とロゴ、いらっしゃいませ、来店の開き方で変わる文言、言語、テーブル |
| 注文 | `Menu` | ヘッダ、カテゴリのタブ、メニューのカード、注文リスト、注文のメッセージ、下部の操作 |
| お会計 | `Checkout` | 明細、内税、割り勘の目安、未提供の品のメッセージ、支払方法、割り勘、QR の表示と待ち、お礼と電子レシートの QR |

起動:

- 準備の進捗: 登録、トークン、端末と店舗の設定 (チェーンの色、スタッフの PIN、言語を入れる)、メニュー、品切れ、料理の写真とロゴ、今の来店
- 設定は、PIN を確認して開く
- 失敗の間は 30 秒ごと、テナントの停止は 5 分ごとに、自動でもリトライする。  
  間隔は案内に出す

スタッフメニュー:

- 端末の情報: テーブル、端末の名前、端末の ID、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリのバージョン

待受:

- 来店の開き方 (店舗の設定) で変わる文言: スタッフの案内を待つ、受付機で受け付ける、タブレットから注文できる
- 言語は今の言語を出し、押すと選ぶ。  
  店舗の言語が 1 つなら出さない
- 来店の開き方が席の店は、「ご注文をはじめる」から人数を入れて始める。  
  ほかの店は、スタッフか受付機が来店を開いた通知で、注文の画面に進む

注文:

- ヘッダ: チェーンの名前とロゴ、テーブル、人数、言語
- メニューのカード: 出せる条件を満たさない品と、出せる品のないカテゴリは隠す
- 注文リスト: 1 回の注文の明細の上限を表示する。  
  出せる条件を満たさなくなった行に、時間外 / お子様のみの印を付ける
- 注文のメッセージ: ほかの端末で始めた会計、注文の一時停止、ラストオーダー、今は注文できない品、時間帯の終わり。  
  注文できない間は確定を止める
- 下部の操作: 注文履歴、店員呼出 (呼び出しの用件がなければ出さない)、お会計

お会計:

- 未提供の品は、お支払いのあともお持ちすることを表示する
- 支払方法: QR コード決済、カード、レジ (店舗の設定にあるものだけ)
- 割り勘 (店舗の設定で使うとき): 人数で割った 1 人分ずつ払い、残りがなくなるまで支払方法の選び直しに戻る。  
  払い終えた人数は、明細を再取得できるまでリトライしてから、減らした人数で割り直す
- QR の表示と待ち: 期限を過ぎたら取り消して、選び直しに戻る

| ポップアップ | DialogId | 内容 |
| --- | --- | --- |
| 電卓 | `InputNumber` (`TerminalDialogId`) | ペアリングコード、スタッフの PIN (入れた桁数だけ見せる) |
| メッセージ / 確認 | `Message` / `Confirm` (`TerminalDialogId`) | 上限、失敗、年齢などの確認 (受ける / 断るのボタンは同じ大きさ) |
| 言語 | `Language` | 言語をその言語の名前で並べ、今の言語に印を付ける (待受と注文の画面の言語のボタンから開く) |
| 人数 | `GuestCount` | 大人と子ども (小学生以下) を増減のボタンで入れ、合わせて 1 人以上で始める (来店の開き方が席の店の待受から開く) |
| 商品の詳細 | `ItemDetail` | 大きな写真、説明、アレルギー、カロリー、オプション、出す時機、数量、入れる (合計つき)。注文リストの行から開くと内容を直せる |
| 注文の確認 | `OrderConfirm` | 明細と合計、提案、「注文する」、受け付けのメッセージ (数秒で閉じる)、失敗と再送 |
| 注文履歴 | `OrderHistory` | 注文と明細の状態、食後の品をお願いする (通らなければ失敗を出す)、これまでの合計 |
| 店員呼出 | `StaffCall` | 用件のタイル、呼び出しの状態 (呼んでいます / 向かっています) |

- 商品の詳細の写真は、ないときはチェーンのロゴを出す。  
  入れられない品は、理由を重ねる
- 商品の詳細のオプションは、必須 / お好みで。  
  品切れと、出せる条件を満たさないものは選べない
- 注文の確認の提案は 1 枠で、出せる条件を満たす品だけを出す。  
  上限に当たったら理由を出す
- 注文の確認の「注文する」は、再送でなければ、送る前に出せる条件を確認する

### 遷移

```
起動 ──(登録なし、登録トークンなし)──> 端末の設定 ──登録 / 保存──> 起動
起動 ──(登録なし、登録トークンあり)──> 登録して続ける
起動 ──(来店なし)──> 待受
起動 ──(来店あり)──> 注文
注文 ──お会計──> お会計 ──支払の完了──> (お礼) ──閉じる / 時間 (店舗の設定)──> 待受
                    ├──割り勘の 1 人分の完了──> 支払方法の選び直し (残りがなくなるまで)
                    └──メニューに戻る (払う前だけ)──> 注文
待受 ──(来店が開いた知らせ)──> 注文
待受 ──ご注文をはじめる (来店の開き方が席の店)──> [人数] ──> 注文
注文 ──(レジで払い終えた知らせ)──> 待受
お会計 ──(レジで払い終えた知らせ)──> (お礼) ──閉じる / 時間 (店舗の設定)──> 待受
(お礼) ──閉じる / 時間 (お礼の間に次の来店が開いた)──> 注文
注文 ──カード──> [商品の詳細] ──(確認のルール)──> [確認]
     ──注文を確定する──> [注文の確認]
     ──注文履歴──> [注文履歴]
     ──店員呼出──> [店員呼出]
待受 / 注文 / お会計 ──ブランドの印の長押し──> [PIN] ──> スタッフメニュー ──閉じる──> 注文 (来店中) / 待受
待受 ──(チェーンと店舗の設定の変更)──> 起動
どの画面 ──(端末の無効化、テナントの停止、接続先の変更の知らせ)──> 起動
```

- MainPage は、画面を切り替える入れ物とビジーオーバーレイだけを持つ。  
  バー (ヘッダ、タブ、下部の操作) は各 View が持つ
- 来店が閉じたときと起動からやり直すときは、開いているポップアップを `PopupClosePlugin` が閉じる。  
  来店が閉じたときに閉じるのは、お客様の画面 (注文、お会計) のポップアップだけ
- ポップアップの処理の途中 (注文の送信など) は、終わってから閉じる。  
  閉じるのは、そのポップアップだけにする
- 端末の戻るは、表示中の画面に渡す
  - お客様の画面 (待受、注文): 何もしない
  - お会計: 支払方法の選び直しかメニューへ戻る。  
    一部を払ったあとは、画面の戻ると同じく何もしない
- カートに入れる前に、次を確認する (提案の追加も同じ)
  - 1 回の注文の明細の数
  - 1 明細の数量 (同じ内容の行にまとめた数)
  - メニューのルールの上限
  - 残りの数 (商品とオプション)
- 端末で確認できる上限は、お客様に確認のルールを尋ねる前に見る
- 注文が送れたかわからない (通信できない) ときは、注文の ID を残す。  
  届いたか拒否されたかがわかるまでカートを直させず、同じ内容を同じ ID で再送してもらう
- 注文の通知 (`order.created`) で届いていたとわかったら、カートを空にして、受け付けたことを表示する
- 支払も、結果のわからない支払の ID・方法・額を残す (作るリクエストの結果がわからない、取り消しが通らなかった)。  
  同じ方法と額で払うときは、同じ ID で再送する
- ほかの払い方にするときは、先に取り消す。  
  取り消す前に払い終わっていたら、払い終えたものとして進める
- スタッフメニューは、ブランドの印を 3 秒押して PIN (店舗の設定) を入れると開く。  
  閉じると、品切れなどの表示を合わせるために、注文の画面か待受を作り直す
- PIN は、店舗の設定で受け取ったハッシュ (登録と一緒に保存する) で確認する。  
  サーバにつながらないときも確認できる
- PIN を 5 回続けて間違えると、5 分入れない (アプリを再起動すると回数をリセットする)
- 起動に失敗したときの端末の設定も、PIN で守る (登録していない端末は PIN なしで入れる)
- 全画面 (システムバーを隠す) は、専用端末の扱いに含める ([6. 専用端末](#-6-専用端末))。  
  ポップアップは Activity と別のウィンドウに出るので、`FullscreenPopupPlugin` でポップアップのウィンドウのシステムバーも隠す

## 🔗 4. 状態と通信

### 状態

| 状態 | 持つもの |
| --- | --- |
| `Settings` | 接続先、登録した端末の ID (登録した接続先と組で持つ)、スタッフの PIN のハッシュ (登録と一緒に持つ)。`IPreferences` に置き、API の実装は `IDeviceContext` として読む |
| `MenuState` | 端末と店舗の設定、メニュー、品切れ。画面には、選んでいる言語に直して渡す |
| `VisitState` | 今の来店 (人数、状態、答えた確認のルール、注文した品) |
| `CartState` | 注文する前の行と、送ったが結果のわからない注文の ID (再送で同じ ID を使う。ある間はカートを直さない) |
| `LanguageState` | 画面の言語と、店舗で選べる言語 |
| `StoreState` | 店舗の今の状態 (タイムゾーン、注文の一時停止、ラストオーダー、設定のバージョン)。起動で読み、通知で更新する |
| `StaffLock` | スタッフの PIN の確認と、間違いが続いたときにロックする時間 |

- `MenuState` の端末と店舗の設定には、端末を置いたテーブル、チェーンの名前とロゴ、機能の有無と来店の開き方、言語、設定のバージョンを含む

### メニューのルール

ドリンクバー・お酒・数量限定などの特例はコードで分けず、メニューのタグとルール (`MenuResponseRule`) で表す。  
数え方は `TableOrder.Domain.TagRules` に置き、端末は案内に、サーバは注文の検証に使う。

| ルール | 端末の動き | サンプルのメニューの例 |
| --- | --- | --- |
| 確認 (`Confirmation`) | タグの品を入れる前に確認し、答えを来店に記録する (`Visit` は来店で 1 回) | お酒の年齢の確認 |
| 上限 (`Limit`) | 来店の注文とカートを合わせて上限を超えたら入れない (`Guest` は 1 人あたり × 人数) | サーロインステーキはお一人様 1 点まで |
| 提案 (`Suggestion`) | 注文の確認で、タグの品を誰かが頼んでいて人数より少なければ、1 枠だけ提案する | ドリンクバー (単品とセットのオプション) を人数分に |
| 出せる条件 (`Availability`) | 時間帯 (メニューの `dayparts`) の外の品と、子どものいない来店のキッズの品を隠す | キッズはお子様のいる来店だけ (デモ)、朝定食とランチは時間帯だけ (検証用) |

- 出せる条件は、30 秒ごとの見直しと人数の変更で表示を更新する (タブとカードの並べ替えは、操作の途中を避ける)
- 出せる条件は、カートに入れるときと確定するときにも確認する。  
  カートの品が満たさなくなったら、外すまで確定を止める
- 出せる条件の判定は、`TableOrder.Terminal` の `MenuAvailability` でホール端末と共通にする

### API クライアント

| API クライアント | 端末 | 持つリクエスト |
| --- | --- | --- |
| `ITableApi` | テーブル端末 | テーブル端末が使うリクエスト ([api-design.md](api-design.md)) |
| `IHallApi` | ホール端末 | 席、来店の操作、代理注文、提供、呼び出し、品切れと注文の一時停止、会計の補助 |
| `IReceptionApi` | 受付機 | 店舗、空席、来店の開始 |
| `IKitchenApi` | キッチン端末 | 店舗、メニュー、品切れ、チケットの一覧と作り始め・できあがり・下げる・戻す |
| `IDeviceApi` | 全端末 | 登録、トークン、状態の報告、端末の設定 |
| `IOrderEvents` | 全端末 | サーバの通知 (来店の開始・変更・移動・終了、店舗の変更、品切れ、注文と明細の変化) の受信 |

- 端末の種類ごとの API クライアントは、端末が使うリクエストを 1 つずつメソッドにしたもの
- REST と gRPC のどちらで実装しても、端末は `ITableApi` だけを見る
- `IDeviceApi` はアクセストークンを中で持ち、画面に渡さない
- トークンのリクエストが拒否されたとき (無効化、テナントの停止) は、`Denied` で端末の ID と理由を通知する。  
  受け取れたときは、`Authorized` で端末の ID を通知する
- API の実装が読む端末の側の値 (接続先、登録した端末の ID、端末の鍵) は、`IDeviceContext` で受ける (テーブル端末は `Settings` が持つ)
- `IOrderEvents` は、起動で今の状態を読む前に接続する (`ConnectAsync`)。  
  通知は `seq` の順に届く
- 同じ通知が 2 回届くことがあるので、レシーバは最後に受けた `seq` 以前の通知を捨てる
- ラストオーダーを過ぎたかは、`TableOrder.Domain.StoreHours` で決める (開店の時刻を営業日の区切りにし、日をまたぐ営業も扱う)。  
  端末は表示に、サーバは注文の受け付けに使う
- DI では、`IDeviceApi`、`ITableApi`、`IOrderEvents` に注文サーバの実装 (`RestDeviceApi`、`RestTableApi`、`SignalROrderEvents`) を登録する
- 接続先はリクエストのたびに読む。  
  端末の設定で変更すると、次のリクエストから新しい接続先に送る (通知は起動で再接続する)

### 注文サーバの実装

| 実装 | 内容 |
| --- | --- |
| `RestConnection` | リクエストの送信。接続先の下の `api/v1/` に送る |
| `RestDeviceApi` / `RestTableApi` / `RestHallApi` / `RestReceptionApi` / `RestKitchenApi` | 端末の種類ごとの API クライアント。リクエストの形を決めて `RestConnection` で送る |
| `SignalROrderEvents` | 通知の受信 (`/hubs/store`) |

`RestConnection`:

- アクセストークンは、期限の 2 分前と `401` を受けたときに再取得する (再送は 1 回だけ)
- テナントの停止で拒否されたら、起動の再取得 (`AuthenticateAsync`) がトークンを受け取るまで、ほかのリクエストはトークンを求めずに同じ拒否を返す。  
  停止の間に、通知の再接続と状態の報告がリクエストを送り続けないため

| レスポンス | 結果 |
| --- | --- |
| `4xx` | `Rejected` (`errorCode` と文言) |
| `401` | `Unauthorized` |
| `5xx`、タイムアウト (15 秒)、通信できない | `Unavailable` |

`Rest{種類}Api`:

- メニューは、バージョンが同じなら `304` を受けて、前に読んだものを使う (`RestMenuCache`。API クライアントごとに持つ)

`SignalROrderEvents`:

- `ready` で受けた番号から数える
- 切れたら間をおいて再接続し、欠落した通知を `GET /events` で読んでから続ける
- 切れてから欠落した通知を読み終えるまでに届いた通知 (`ready` より前のものも) は、ためておく。  
  欠落した通知と合わせて、seq の順に渡す (`EventSequencer`)
- 通知には接続を付ける (`OrderEventArgs.Connection`)。  
  `ConnectAsync` で作り直したら、前の接続の通知と読み込みは渡さない
- 接続前のネゴシエーションは、15 秒でタイムアウトする。  
  `401` で拒否されたら、トークンを再取得する
- 欠落した通知を読めないとき (追跡できない `410` など) は `Expired` で通知し、端末は起動からやり直す
- レシーバが例外を投げても配信を続け、渡しそこねた通知の代わりに `Expired` で通知する

端末が受ける通知:

| 通知 | 種類 | 補足 |
| --- | --- | --- |
| 来店 | `visit.opened` / `updated` / `moved` / `closed` | |
| 店舗 | `store.updated` | |
| 品切れ | `stock.updated` | |
| 注文 | `order.created`、`order.lines.updated` | 上限のルールの数え方に使う |
| 呼び出し | `call.created` / `call.updated` | ホール端末の呼び出しの一覧に使う |
| チケット | `ticket.created` / `ticket.updated` | キッチン端末は一覧を再取得するので、内容を渡さない |

- テーブル端末は、注文履歴・呼び出し・支払の状態を、開いている間に再取得して出す
- JSON はソース生成 (`ClientJsonContext`) で読み書きし、リフレクションに頼らない。  
  端末のトリミングで、型の情報が消えないようにするため
- Android の端末は、Debug だけ平文の HTTP につなげる (開発のサーバ)。  
  Release は HTTPS だけにし、端末の設定と EMM の構成も https の接続先だけを受ける
- 異常終了したときの例外は記録し (`CrashReport`)、次の起動でログに残す。  
  お客様の画面には出さず、起動を待たせない
- 観測されなかったタスクの例外は、異常終了ではないので、ログにだけ残す

### 端末の登録

端末は自分の鍵 (`Components/DeviceKey`) で登録し、サーバの端末の設定でテーブルを受け取る。

- 鍵は Android の Keystore の P-256 で、秘密鍵はエクスポートできない
- 鍵は Keystore の形 (公開鍵は SubjectPublicKeyInfo、署名は DER) で返す。  
  API の形 (JWK、ES256 の JWT) には、`DeviceCredentials` で変換する
- 鍵のインターフェイス (`IDeviceKey`) の公開鍵と署名は、非同期にする (ブラウザの鍵は非同期でしか使えない)
- Android の鍵は、Keystore の操作を UI スレッドの外で行う

| 場面 | 端末の動き |
| --- | --- |
| 登録 | 端末の設定でペアリングコードを入れて登録する。EMM が登録トークンを配信していれば、登録していない端末は起動したときに自分で登録する |
| 起動 | トークンを再取得し、テーブル端末として登録されていることとテーブルを、端末の設定で確認する。テーブルを割り当てるまでは起動の画面で待つ |
| 表示 | テーブルの名前は、端末の設定 (`device.tableName`) のものを出す (端末ではテーブルを入れない) |
| 状態の報告 | 登録している間、1 分ごとにアプリのバージョンと電池を送る (`StatusReporter`) |
| 無効化 | トークンのリクエストが `DEVICE_REVOKED` で拒否されたら、登録と鍵を削除して端末の設定に戻る。無効にされたことを覚え、EMM の登録トークンでは自分で再登録しない |
| テナントの停止 | 起動の画面で、停止していることを出し、5 分ごとにリトライする (「もう一度試す」はすぐに確認する)。起動の画面がトークンを再取得できるまで、通知の再接続と状態の報告はトークンを求めない |
| 接続先の変更 | 登録は接続先ごとなので、登録した接続先と今の接続先が違えば、登録していないものとする。EMM が接続先を変更したら、起動からやり直す |

- 登録は、送った接続先の登録として覚える。  
  送る間に接続先が変わったら、覚えない
- 鍵は再登録しても再利用し、無効にされたときに削除する (次の登録で再作成する)
- 前の登録は、新しい登録でトークンを受け取ったときにサーバが無効にする。  
  登録のレスポンスが届かなければ、前の登録のまま使い続けられる
- 登録のリクエストには、アプリの端末の種類 (`TerminalOptions`) を入れる。  
  違う種類のコード (テーブル端末にホール端末のコードなど) は、サーバが登録せずに拒否する (`DEVICE_KIND_MISMATCH`。コードは使わない)
- 拒否された登録トークン (種類の違い、期限切れや取り消し) は、待っても通らない。  
  起動の失敗でも自動ではリトライしない (再配信してから、もう一度試す)

## 🌐 5. 多言語と色

### 多言語

- 画面の文言は、`Resources/Strings/AppResources.resx` (日本語、既定) と `AppResources.en.resx` (英語) に置く。  
  XAML は `{x:Static strings:AppResources.Xxx}` で引く
- 言語を選ぶと、`LanguageState` が UI のカルチャを切り替える。  
  表示中の画面を作り直して、文言を引き直す (注文リストは状態に残る)
- メニューの名前と説明、呼び出しの用件、チェーンの名前は、サーバの `LocalizedText` から選んだ言語で出す
- 選べる言語は、店舗の設定 (`languages`) の言語だけにする。  
  1 つなら、言語のボタンを出さない
- 起動して来店がないときと来店が終わったときは、端末の言語の設定によらず、店舗の初めの言語に戻す (店舗の設定を読むまでは日本語)
- 金額と時刻の書式は、言語で変えない
- 時刻は、店舗のタイムゾーンで出す (端末のタイムゾーンの設定によらない)
- サーバのエラーは、errorCode ごとに端末の文言 (日本語と英語) で出す。  
  割り当てのないものは共通の文言にする (サーバの文言は担当者向けの日本語なので出さない)

### 色

- 色は `Colors.xaml` の役割の名前で定義し、スタイル・画面・アイコンは役割の名前だけを使う
- Brand (主色、補助色)・Neutral・Status の役割は、起動のときにチェーンの設定の色 (`brand.theme`) で切り替える (`ThemeManager`)
- `Colors.xaml` の値は既定の色にし、設定にない役割は既定の色のままにする
- スタイルはこれらの色を `DynamicResource` で引き、アプリのリソースの一番上に置いたチェーンの色を使う
- System は起動・端末の設定・電卓の色で、チェーンの色に切り替えない。  
  スプラッシュとアプリのアイコンの色に揃えている
- チェーンの名前とロゴはチェーンの設定から受け取り、ヘッダと待受の印に出す。  
  ロゴを保存していなければ、名前の頭の文字を出す
- チェーンの名前は、店舗の名前 `storeName` と分ける

## 🔒 6. 専用端末

`Components/KioskManager` が、端末に合わせて専用端末にする。

- 画面がフォアグラウンドになるたびに、全画面を再適用する。  
  方式を再判定し、変わっていれば専用端末の設定を再適用する
- 動いている間に EMM がロックタスクを許したり外したりするので、スタッフメニューに出すときも方式を再判定する

| 方式 | 判別 | 行うこと |
| --- | --- | --- |
| Device Owner | アプリ自身が Device Owner | 下の端末の制限を適用して、ロックタスクに入る |
| 外部の管理 (EMM) | EMM がロックタスクを許している | ロックタスクに入る (端末の制限は EMM が適用する) |
| なし | どちらでもない (開発中の端末など) | 全画面にするだけ (ロックタスクに入ろうとすると、画面の固定の確認が出るため) |

Device Owner のときに適用する端末の制限:

| 対象 | 設定 |
| --- | --- |
| ロックタスク | このアプリだけを許し、ホーム・履歴・通知・電源のメニュー・ステータスバーの情報を出さない |
| ホームアプリ | 注文の画面 (`MainActivity`) を常に使うホームにする。電源を入れたときと、異常終了したときに起動する |
| ロック画面とステータスバー | 無効にする |
| 画面 | 充電中は点けたままにする |
| OS の更新 | 夜間 (2:00〜4:00) に入れる |
| 端末の操作 | 工場出荷時へのリセット、安全モード、利用者の追加を禁止する |

- 注文の画面は `lockTaskMode="if_whitelisted"` にする。  
  ロックタスクを許されていれば、起動したときにシステムがロックタスクに入れる (異常終了したあとの起動でも)
- 注文の画面はホームの候補にもなる。  
  ホームの役割 (Android 10 以降) は変わらないので、Device Owner でない端末のホームはそのまま
- スタッフメニューの「一時的に解除する」で、ロックタスクを抜けてシステムバーを出し、Android の設定を開ける。  
  「専用端末に戻す」かアプリを再起動すると、元に戻る
- Device Owner のレシーバ (`AdminReceiver`) は、adb から指せるように Java の名前を固定している (`tableorder.terminal.table/.AdminReceiver`)
- Debug は `testOnly` にして、adb から Device Owner を外せるようにしている。  
  Release は外せない (端末の初期化が要る)

エミュレータで確認した動き:

| 操作 | 結果 |
| --- | --- |
| ステータスバーを引き下ろす | 通知とクイック設定を開けない |
| ホーム・履歴のキー | 注文の画面のまま |
| 電源ボタンの長押し | 電源のメニューが出ない |
| 通知 | 割り込みの通知が出ない |
| 再起動 | 注文の画面がホームとして起動し、ロックタスクに入る。ロック画面は出ない |
| プロセスを止める | ホームとして再起動し、ロックタスクに入る。ホームアプリにしていないと (ランチャーから起動しただけでは)、ランチャーに戻る |
| Device Owner のアプリを止める | `am force-stop` と `am crash` が効かない (Debug は `run-as` で止める) |

### 管理対象の構成

接続先と端末の登録トークンは、外部の EMM が管理対象の構成で配信できる (`Components/ManagedConfiguration`)。

- 配信された値は、端末の設定より優先する (`Settings` が読む)
- 端末の値は書き換えないので、配信されなくなると端末の値に戻る
- 起動したときに読み、EMM が値を変更した通知を受けたときと、画面がフォアグラウンドになったときに再読み込みする
- 配信された値は、画面で変えられないようにする (端末の設定の画面は、入力の代わりに値を出す)
- スタッフの PIN は配信せず、管理画面の店舗の設定で決める
- 登録トークンは、登録していない端末が起動したときに使う (テーブルは管理画面で割り当てる)
- 接続先が変わったら、起動からやり直して再接続する (登録は接続先ごとなので、登録トークンがあれば再登録する)
- スタッフメニューの端末の情報に、配信されている設定を出す
- 配信の方法と値は [device-management.md](device-management.md) に書いた

## 📟 7. ホール端末の実装

ホールのスタッフが持つスマートフォン (縦向き) のアプリ。  
端末に共通の部品 (`TableOrder.Terminal`) はテーブル端末と同じものを使い、登録で送る端末の種類を `Hall` にする。

実装済み:

- 起動、端末の設定と登録、端末の画面
- 下部のタブ: 席 (案内と来店の詳細)、呼び出し、提供、品切れ
- 代理注文 (食後の品のお願い、明細の取消、会計の補助を含む)
- 状態と通知の受信、新しい呼び出しのアラート

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Modules/` | 画面とポップアップの View と ViewModel (`Startup`、`Setup`、`Device`、下部のタブの `Seats`・`Calls`・`Serving`・`Stock`、来店の詳細の `Visit`、代理注文の `Order`、`Dialogs`)、タブの画面の基底クラス (`TabViewModelBase`) |
| `Controls/` | タブの画面のヘッダ (`TabHeader`) とタブバー (`TabFooter`)。画面の ViewModel (`TabViewModelBase`) にバインドする |
| `State/` | 店舗 (`StoreState`。端末の設定で受けた店舗の設定と、店舗の今の状態)、メニューと品切れ (`MenuState`)、席 (`TableState`)、呼び出し (`CallState`)、提供 (`ServingState`) |
| `Models/` | 代理注文で使う形 (`ItemSelection`、`CartLine`) |
| `Usecase/` | 席・呼び出し・提供の一覧の再取得と操作の送信 (`HallUsecase`)、代理注文のルールの判定と送信 (`ProxyOrderUsecase`) |
| `Shell/` | 通知のレシーバ (`OrderEventReceiver`) と、画面へのイベント (`ShellEvent`) |
| `Components/` | 新しい呼び出しのアラート (`CallAlert`。端末の通知音と振動)、画面が消えている間もアプリを動かし続けるフォアグラウンドサービスの開始 (`CallWatch`) |
| `Resources/` | 色 (`Colors.xaml`)、ホール端末のスタイル (`Styles.xaml`)、画面の文言、アイコンのフォントとグリフの表、アプリのアイコン、スプラッシュ |
| `Platforms/` | Activity、Device Owner のレシーバ、フォアグラウンドサービス (`CallWatchService`)、マニフェスト、管理対象の構成の定義 |

### 画面

| 画面 | ViewId | 内容 |
| --- | --- | --- |
| 起動 | `Startup` | テーブル端末と同じ流れのあと、店舗、メニューと品切れ、席・呼び出し・提供の一覧を読む |
| 端末の設定 | `Setup` | 接続先、今の接続先での登録、ペアリングコード (テーブル端末と同じ) |
| 端末 | `Device` | 端末の情報、端末の設定、専用端末の一時的な解除 |
| 席 | `Seats` | テーブルのタイル。押すと案内か来店の詳細を開く |
| 来店の詳細 | `Visit` | 来店と注文の状態、来店の操作 |
| 代理注文 | `Order` | カテゴリごとの品、カート、注文する |
| 呼び出し | `Calls` | 終わっていない呼び出しのカード |
| 提供 | `Serving` | できあがった明細を、テーブルごとのカードに並べる |
| 品切れ | `Stock` | カテゴリごとの品の状態、注文の一時停止、すべて戻す |

起動:

- テーブル端末と同じ流れ: 接続先、登録、トークン、端末の設定、通知の接続
- ホール端末として登録されていなければ進まない
- 失敗したら、30 秒ごと (テナントの停止は 5 分ごと) にリトライする

端末:

- 端末の情報: 店舗、端末の名前、端末の ID、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリのバージョン
- 端末の設定と専用端末の一時的な解除は、スタッフの PIN を確認してから行う

席:

- テーブルを、店舗の並びの順に 2 列のタイルで並べる
- タイルには、名前と状態 (空き・来店中・会計中) を出す。  
  状態は、左端のバーの色でも示す
- 来店中は、人数、経過時間 (30 秒ごとに更新する)、未提供の品の数、終わっていない呼び出しの数を出す
- 空きは、定員を出す
- 空きを押すと案内 (人数のポップアップ)、来店中と会計中を押すと来店の詳細を開く

来店の詳細:

- 状態、人数、開いた時刻と経過時間、注文の合計、注文と明細の状態を出す
- 注文と明細の状態は、何回目の注文かと、明細ごとの調理と提供の段階。  
  できあがりは目立たせ、提供と取消は控えめにする
- 注文の見出しの右に「注文を入れる」を置く (代理注文の画面を開く)
- 食後に出す品があるときは、注文の下に「食後の品をお願いする」を置く (確認してから、すべて)
- 提供と取消を除く明細を押すと、取消を開く
- 下部のバーに、人数変更、席移動、会計 (明細のポップアップ)、来店を終える操作を置く
- 来店を終える操作は、注文のある来店と会計中は「レジで払った」、注文のない来店は「取りやめ」にする。  
  確認してから閉じて、席のタブに戻る
- お願いしていない食後の品があれば、閉じると作らないことを確認で伝える
- 会計中は、注文を入れる・席移動・食後の品のお願い・取消を押せない

代理注文:

- 上部にカテゴリのバー (先頭はカート、続けてメニューのカテゴリ) を置き、選んだカテゴリの品 (名前、価格、品切れと残りの数) を並べる
- 出せる条件 (時間帯、来店の子ども) を満たさない品と、出せる品のないカテゴリは隠す (並べ直すたびに求め直す)
- 品を押すと、品の詳細で選んでカートに入れる。  
  カートの品を押すと、確認してから外す
- 下部に「注文する」 (点数と合計) を置き、確認してから送って来店の詳細に戻る
- 送る前に出せる条件を確認し、満たさない明細はカートの明細に印を出す
- カートに品があるまま戻るときは、捨ててよいか確認する
- 注文を一時停止している間は、注文の一時停止のバーを出す

呼び出し:

- 終わっていない呼び出しを、古い順にカードで並べる
- カードには、テーブル、用件 (店舗の設定の名前)、呼ばれてからの時間 (30 秒ごとに更新する) を出す
- 状態は、左端のバーの色でも示す (呼ばれている間は注意の色)
- 呼ばれている呼び出しには「向かう」と「対応した」、向かっている呼び出しには「対応した」だけを置く。  
  どちらも確認せずに送る

提供:

- できあがった明細を、テーブルごとのカードに、できあがりの古い順に並べる
- 明細には、名前、オプション、数量、できあがってからの時間を出す
- 明細ごとの「提供した」と、明細が 2 つ以上のテーブルの「すべて提供した」を置く。  
  どちらも確認せずに送る
- 払い終えて閉じた来店の品も、その営業日のうちは並べ、カードに「会計済み」を出す

品切れ:

- 上部にカテゴリのバーを置く。  
  先頭は品切れと残りの数のある品だけの「品切れ・残り」、続けてメニューのカテゴリ、最後にオプション
- カテゴリのバーは、続きがある向きの端に送りのボタンを重ねる
- 選んだカテゴリの品に、名前と状態 (品切れ、残りの数) を出す (オプションには、グループの名前を添える)
- 品を押すと、状態を選ぶポップアップを開く
- 下部のバーに、「注文を止める」 (確認してから) か「注文を再開する」を、状態に合わせて置く
- 下部のバーに、「すべて戻す」 (確認してから) を置く。  
  品切れと残りの数のある品がないときは押せない

| ポップアップ | DialogId | 内容 |
| --- | --- | --- |
| 電卓 / メッセージ / 確認 | `InputNumber` / `Message` / `Confirm` (`TerminalDialogId`) | ペアリングコード、スタッフの PIN、残りの数、失敗のメッセージ、操作の確認 |
| 人数 | `GuestCount` | 大人と子ども (小学生以下) を増減のボタンで入れ、合わせて 1 人以上で決める。案内 (定員を添えるが、超えても止めない) と人数の変更で使う |
| 席の選択 | `MoveTable` | 空いている席 (名前と定員) から、移る席を選ぶ (確認せずに移す)。空いている席がなければ、空席がないことを出す |
| 品の詳細 | `OrderItem` | 代理注文で、オプション、出す時機 (選べる品だけ)、数量を選ぶ。表題の右に、オプションと数量を合わせた合計を出す |
| 明細の取消 | `LineCancel` | 取り消す明細を出し、数量が 2 以上なら取り消す数を選ぶ (はじめはすべて) |
| 会計 | `Bill` | 明細、内税、合計 (払った額と残り)、未提供の品の注意を出す。会計中でなければ「会計を始める」、会計中なら「会計を取りやめる」を出す |
| 品の状態 | `StockEdit` | 今の状態に印を付け、「売れる」「残りの数を決める」「品切れ」から選ぶ。残りの数は続けて電卓で入れ (0 は品切れになる)、今と同じ状態を選んだら送らない |

- 確認のポップアップを使う操作: 来店を終える、食後の品のお願い、すべて戻す、注文を止める、注文する、カートから外す、お客様への確認 (確認のルール)
- 品の詳細のオプションは、今の選択に印を付ける。  
  必須の組は、選ぶまで入れられない。  
  品切れと、出せる条件を満たさないオプションは選べない

画面に共通の扱い:

- 下部のタブの画面 (席、呼び出し、提供、品切れ) には、ヘッダとタブバーを置く
  - ヘッダ: タブの名前、店舗の名前、端末の画面を開くボタン、注文の一時停止の表示
  - タブバー: 呼び出しはまだ誰も向かっていない数、提供はできあがった明細の数を添える
- タブを押すと、そのタブの画面に切り替える (画面は切り替えるたびに作る)
- 時刻 (来店を開いた時刻、注文の時刻) は、店舗のタイムゾーン (店舗の設定) で出す (端末のタイムゾーンの設定によらない)
- 共通のポップアップと、起動・端末の設定の列の幅は、画面に収まらないときに左右に余白を残して縮める (`TerminalSizes`)。  
  タブレットでは、決めた幅のまま

端末の戻る:

| 画面 | 動き |
| --- | --- |
| タブの画面 (席のタブ以外) | 席のタブへ戻る |
| 席のタブ | 何もしない |
| 端末 | 開いたタブに戻る |
| 来店の詳細 | 席のタブに戻る |
| 代理注文 | 来店の詳細に戻る |

### 状態と通知

起動で、店舗の設定と今の状態、メニューと品切れ、席・呼び出し・提供の一覧を読む。  
`OrderEventReceiver` が、通知で更新する。

| 対象 | 通知での更新 |
| --- | --- |
| 店舗、品切れ | 通知の内容で更新する |
| 店舗の設定 (PIN、呼び出しの用件、注文のルール、店舗の名前) | バージョンが変わったら、タブの画面で起動からやり直して再読み込みする。来店の詳細と代理注文の画面では切り替えず、タブの画面に戻ったときにやり直す |
| 席、呼び出し、提供 | 変わる通知 (来店、注文、明細、呼び出し) を受けたら、一覧を再取得する。提供は注文の通知でも再取得する (持ち場のない品は、注文を受けたときにできあがるため) |

- 再取得する一覧の印は、届いたとき (`OrderEventReceiverBase.OnReceived`) に付ける。  
  まとめて届いた通知を扱い終えたあと (`OnDrainedAsync`) に、一覧を 1 回だけ再取得する
- 印は再取得の前に下ろす (再取得を待つ間に届いた通知の印を消さない)。  
  再取得できなかった一覧は、印を戻して次の通知のあとに再取得する
- 更新したら、表示中の画面に `ShellEvent` (`StoreChanged`、`StockChanged`、`TablesChanged`、`CallsChanged`、`ServingChanged`) で伝える
- 起動からやり直すイベント (`Restart`) は、テーブル端末と同じ

| 画面 | イベント | 対応 |
| --- | --- | --- |
| 来店の詳細 | 席の一覧の再取得 (`TablesChanged`) | 来店と注文を再取得する。来店が終わっていたら席のタブに戻る |
| 品切れのタブ | 品切れ (`StockChanged`。注文で残りの数が減ったときも届く) | 品の表示を更新する |
| 代理注文 | 席の一覧の再取得 | 来店を再取得する。終わっていたら席のタブ、会計中なら来店の詳細に戻る |
| 代理注文 | 品切れ | 品の状態を更新する |
| 代理注文 | 店舗 | 注文の一時停止のバーを更新する |

代理注文:

- 入れる前に、上限のルールと確認のルールを `ProxyOrderUsecase` で確認する (数え方は、テーブル端末とサーバと同じ `TagRules`)
  - 上限のルール: 来店の注文 (取消を除く) とカートを合わせて数える
  - 確認のルール: 文言でお客様に確認したかをスタッフに聞き、確認したら来店に記録する。  
    来店で 1 回のルールは、記録したら聞かない
- 送れたかわからない (通信できない) ときは、同じ来店で同じカートを送るときだけ、同じ注文の ID を再送する。  
  カートを変えたら、新しい注文にする

操作:

- 来店・明細・呼び出し・提供・品切れ・注文の一時停止・会計の操作は、`HallUsecase` が送る
- 操作を終えたら、変わったもの (席、呼び出し、提供、品切れ、店舗の今の状態) を再取得する。  
  通知でも再取得するが、操作した画面をすぐに更新するため
- 拒否されたとき (ほかで変更されていた、席が埋まっていた、会計中、来店が終わっていた) は、メッセージを出して再取得する
- 来店を直す・終える操作は、読んだ来店のバージョンを付けて送る
- 案内が送れたかわからない (通信できない) ときは、同じテーブルと人数の次の案内で、同じ来店の ID を再送する (サーバは同じ ID の再送に、開いた来店を返す)
- 返った来店が終わっていたら (開いたあとに閉じた)、使わずに新しく開く。  
  席の一覧にその来店が出たら、再送しない
- 呼び出しの向かう・対応したと提供は、ほかの端末が先に進めていても失敗にならない。  
  サーバは今の呼び出しを返し、提供済みの明細は飛ばす
- 一覧 (席のタイル、呼び出し、提供) は、再取得した並びに合わせて残る項目の内容を更新し、作り直さない (`ItemsHelper.Sync`。スクロールの位置を保つ)
- 残る項目も、出している値 (提供の数量とできあがりの時刻など) はすべて更新する (一部の取消は、同じ明細の数量を減らす)
- 払い終えた支払のある会計は、取りやめられない (サーバは会計中のまま返す)。  
  明細のポップアップは、取りやめを出さずに理由を出す
- 明細を出したあとに払われて、取りやめが効かなかったときも、メッセージを出す

新しい呼び出しのアラート:

- 新しい呼び出し (`call.created`) は、届いたとき (`OnReceived`) に `CallAlert` が、端末の通知音 (通知の音量) と振動 (通知の用途) で知らせる。  
  操作の途中とポップアップを開いている間も待たない
- 続けて届いたときは、3 秒の間を空けて 1 回にまとめる
- 画面が消えている間も知らせるため、画面がフォアグラウンドになったときに、フォアグラウンドサービス (`CallWatchService`。種類は `specialUse`) を始める。  
  部分ウェイクロックで、CPU を止めない
- フォアグラウンドサービスのアプリは Doze でも通信でき、通知の接続を保つ
- フォアグラウンドサービスの通知は、音のないチャネルに出す。  
  通知の許可は求めない (許可がなくても、フォアグラウンドサービスは動く)

### 色と言語

- 色の辞書 (`Colors.xaml`) の Brand・Neutral・Status の役割には、System の色に揃えた値を持つ
- チェーンの色に切り替えない (`ThemeManager` を持たない)
- 文言とサーバの文字 (店舗の名前) は、端末の言語で選ぶ (英語の端末は英語、ほかは日本語)

### 専用端末

テーブル端末と同じ仕組みを使う ([6. 専用端末](#-6-専用端末))。

- アプリの画面 (`MainActivity`) を、ロックタスクとホームの候補にする
- Device Owner のレシーバ (`tableorder.terminal.hall/.AdminReceiver`) と、管理対象の構成の定義を置く
- 専用端末の一時的な解除は、端末の画面で PIN を確認して行う

## 🙋 8. 受付機の実装

来店の開き方を受付機にした店の入口に、縦に置くタブレットのアプリ。  
お客様が人数を入れると、サーバが人数の入る空席を決めて来店を開き、受付機が席を案内する ([business.md](business.md#31-来店と人数))。  
端末に共通の部品とお客様の画面の部品 (`TableOrder.Terminal`) はテーブル端末と同じものを使い、登録で送る端末の種類を `Reception` にする。

実装済み:

- 起動、端末の設定と登録、スタッフメニュー
- 待受、人数、案内
- 状態と通知の受信

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Modules/` | 画面とポップアップの View と ViewModel (`Startup`、`Setup`、`Staff`、`Standby`、`Guests`、`Guide`、`Dialogs`) |
| `State/` | 端末の設定と空席 (`ReceptionState`)、店舗の今の状態 (`StoreState`。ラストオーダーの時刻、注文の一時停止、設定のバージョン) |
| `Usecase/` | 空席の再取得と、人数を送って来店を開く手順 (`ReceptionUsecase`) |
| `Shell/` | 通知のレシーバ (`OrderEventReceiver`) と、画面へのイベント (`ShellEvent`) |
| `Markup/` | アイコン (`AppIcons`) |
| `Resources/` | 色 (`Colors.xaml`。Brand・Neutral・Status の役割)、受付機のスタイル (`Styles.xaml`)、画面の文言、アイコンのフォントとグリフの表、アプリのアイコン、スプラッシュ |
| `Platforms/` | Activity、Device Owner のレシーバ、マニフェスト、管理対象の構成の定義 |

### 画面

| 画面 | ViewId | 内容 |
| --- | --- | --- |
| 起動 | `Startup` | テーブル端末と同じ流れのあと、店舗、チェーンのロゴ、空席を読む |
| 端末の設定 | `Setup` | 接続先、今の接続先での登録、ペアリングコード (テーブル端末と同じ) |
| スタッフメニュー | `Staff` | 端末の情報、端末の設定、専用端末の一時的な解除を 1 列に並べる。5 分操作しなければ、専用端末に戻して待受に戻る |
| 待受 | `Standby` | 上部のバー、いらっしゃいませ、受付の文言、受付の流れ、空席の状態、「受付する」 |
| 人数 | `Guests` | 受付の段階 (人数)、大人と子どもの大きな増減のボタン、合計、「席を決める」 |
| 案内 | `Guide` | 受付の段階 (ご案内)、決まったテーブル、人数。人数の入る空席がなかったときは満席 |

起動:

- テーブル端末と同じ流れ: 接続先、登録、トークン、端末の設定 (チェーンの色、スタッフの PIN、言語)、通知の接続
- 受付機として登録されていなければ進まない
- 失敗したら、30 秒ごと (テナントの停止は 5 分ごと) にリトライする

スタッフメニュー:

- 端末の情報: 店舗、端末の名前、端末の ID、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリのバージョン

待受:

- 上部のバー: チェーンの名前とロゴ、店舗の名前、言語 (今の言語を出し、押すと選ぶ。店舗の言語が 1 つなら出さない)
- 受付の流れ: 人数を入れる、席が決まる、お席へ
- 空席の状態: すぐに案内できる / 満席 / 受付を止めている / 本日の受付の終了 / 開店前は受付の始まる時刻。  
  アイコンと状態の色で示す
- 受け付けないとき (来店の開き方が受付機でない店、ラストオーダーの後) と、空いているテーブルがひとつもないときは、状態だけを出す。  
  受付の流れと「受付する」は出さない
- 注文を一時停止している間も受け付ける。  
  空席の状態に、一時停止の文言 (店舗の文言。なければ既定の文言) を注意の色で添える
- 言語を選んで受付せずに 60 秒たったら、店舗の初めの言語に戻す

人数:

- 大人と子ども (小学生以下) を、大きな増減のボタンで入れる (はじめは大人 2 人。合わせて 1 人以上)
- 「席を決める」で来店を開き、案内に進む。  
  ラストオーダーを過ぎていたら送らずに、受付の終了を表示して待受に戻る
- 戻るか、60 秒触らなければ待受に戻る (戻るまでの時間を添える)

案内:

- 決まったテーブルを主色の札にして大きく出し、「お席へお進みください」と人数を添える
- 人数の入る空席がなかったときは、満席と、スタッフが案内することを出す
- 注文を一時停止している間は、人数の下に一時停止の文言を添える (店舗の通知で更新する)
- 閉じるか、15 秒たつと待受に戻る。  
  残りの秒は、減っていくバーと文字で出す
- 起動からやり直すイベントを受けたら、案内を消さずに、閉じたときに起動に移る

画面のレイアウト:

- お客様の画面 (待受、人数、案内) は、受付機に固有のレイアウトにし、テーブル端末の画面を流用しない。  
  入口に縦に置いたタブレット (1200x1920) を、立って使うため
  - 上部に、チェーンのバー (印、名前、店舗の名前) を通す
  - 人数と案内の画面は、その下に受付の段階のバーを置く
  - 主な操作は、画面の幅いっぱいのボタンにして下部に置く
- 起動と端末の設定は、テーブル端末と同じ列のレイアウトのまま、縦置きに収める

| ポップアップ | DialogId | 内容 |
| --- | --- | --- |
| 電卓 / メッセージ | `InputNumber` / `Message` (`TerminalDialogId`) | ペアリングコード、スタッフの PIN、失敗のメッセージ、受付を止めたメッセージ |
| 言語 | `Language` | 言語をその言語の名前で並べ、今の言語に印を付ける (待受の言語のボタンから開く) |

### 遷移

```
起動 ──(登録なし、登録トークンなし)──> 端末の設定 ──登録 / 保存──> 起動
起動 ──(用意ができた)──> 待受
待受 ──受付する──> 人数 ──席を決める──> 案内 (テーブル / 満席) ──閉じる / 15 秒──> 待受
人数 ──戻る / 60 秒触らない──> 待受
人数 ──(受付を止めていた)──> [知らせ] ──> 起動
待受 ──ブランドの印の長押し──> [PIN] ──> スタッフメニュー ──閉じる──> 待受
待受 ──(チェーンと店舗の設定の変更)──> 起動
どの画面 ──(端末の無効化、テナントの停止、接続先の変更の知らせ)──> 起動
```

- 端末の戻るは、待受では何もしない。  
  人数・案内・スタッフメニューでは、待受に戻る (アプリの外へ出さない)
- 次のときは、言語を店舗の初めの言語に戻す (次のお客様が、初めの言語から始められるように)
  - 案内を閉じたとき
  - 人数の画面で、触らずに待受に戻ったとき
  - 待受で言語を選び、受付せずに離れたとき
- 人数の画面の戻るでは、選んだ言語のままにする (同じお客様が人数を入れ直すため)
- 待受に戻す時間は、操作の途中 (`BusyState`) なら次の機会に延ばす
- 人数の画面は、人数を変えるたびに、触らなかった時間を数え直す
- 失敗のメッセージを開いたまま時間が来たら、メッセージを閉じてから待受に戻す (お客様がメッセージを開いたまま離れたとき)
- スタッフメニューは、テーブル端末と同じく、ブランドの印を 3 秒押して PIN (店舗の設定) を入れると開く

### 状態と通知

- 起動で、端末の設定 (チェーンと店舗の設定)、店舗の今の状態、空いているテーブルを読む。  
  `OrderEventReceiver` が、通知で更新する
- 空いているテーブルは、来店の通知 (`visit.opened`、`visit.moved`、`visit.closed`) を受けたら再取得する (`GET /tables?status=Vacant`)
  - 再取得の印は、届いたとき (`OnReceived`) に付ける
  - まとめて届いた通知を扱い終えたあと (`OnDrainedAsync`) に、印を下ろしてから 1 回だけ再取得し、表示中の画面に `ShellEvent.VacancyChanged` で伝える
  - 再取得できなかったときは、待受に入ったときと 30 秒ごとに再取得する (次の来店の通知まで満席のままにしない)
- 空いているテーブルがひとつもなければ、待受を満席にする
- 人数が定員に入るかは、席を決めるときにサーバが確認する。  
  入る空席がなければ `NO_VACANT_TABLE` を返し、案内の画面に満席を出す
- 店舗は通知 (`store.updated`) の内容で更新し、表示中の画面に `ShellEvent.StoreUpdated` で伝える
- 待受は、設定のバージョンが起動のときに読んだ端末の設定と違えば、起動からやり直す (来店の開き方の変更も、これで反映する)。  
  ほかの変化 (ラストオーダーの時刻) は、文言を更新する
- ラストオーダーの時刻を過ぎたかは、待受が 30 秒ごとに、店舗のタイムゾーンの時刻で見直す。  
  過ぎたら、来店を開いても注文できないので受け付けない (受付機だけで止め、サーバは止めない)
- 来店を開くリクエストが送れたかわからない (通信できない) ときは、同じお客様が同じ人数で再送するときに、同じ来店の ID を再送する (人数が変われば新しく開く)
- 残した ID は、人数の画面に入るとき (次のお客様) に捨てる。  
  再送で返った来店が開いていなければ (スタッフが閉じたなど)、使わずに新しく開く
- 来店の開き方が変わっていた (`VISIT_OPENING_DISABLED`) ときは、メッセージを出してから起動からやり直す
- 起動からやり直すイベント (`Restart`) は、テーブル端末と同じ

### 色と言語

- チェーンの色は、テーブル端末と同じく、起動のときに `ThemeManager` が Brand・Neutral・Status の役割を切り替える
- 起動・端末の設定・スタッフメニューは、System の役割の色で組む

お客様の画面の色:

| 部分 | 色 |
| --- | --- |
| 上部のバー | 補助色 |
| 本文 | 地の色 |
| 主な操作、案内のテーブルの札 | 主色 |
| 空席の状態 | 状態の色 (すぐに案内できるは成功、満席は注意) |

- 文言とサーバの文字 (チェーンの名前、店舗の名前) は、待受で選んだ言語で出す (選べる言語は店舗の設定の言語)。  
  起動のときは、端末の言語の設定によらず、店舗の初めの言語から始める
- 言語を変えたら、待受を作り直して文言を引き直す

### 専用端末

テーブル端末と同じ仕組みを使う ([6. 専用端末](#-6-専用端末))。

- アプリの画面 (`MainActivity`) を、ロックタスクとホームの候補にする
- Device Owner のレシーバ (`tableorder.terminal.reception/.AdminReceiver`) と、管理対象の構成の定義を置く
- 専用端末の一時的な解除は、スタッフメニューで行う

## 🍳 9. キッチン端末の実装

厨房・デザート・ドリンクの持ち場に置くタブレット (横向き) のブラウザで開く、Web アプリ (Blazor WebAssembly)。

- サーバが `/kitchen` で配信し、接続先はアプリを配信したサーバにする
- 内容で名前の変わらないファイル (index.html、JavaScript の部品、スタイル) は、更新がすぐ届くように、ブラウザに毎回確認させる (`Cache-Control: no-cache`)
- API クライアント (`TableOrder.Client`) は、端末のアプリと同じもの (`IDeviceApi`、`IKitchenApi`、`IOrderEvents`) を使う

実装済み:

- 起動、端末の設定と登録、端末の画面
- チケット: 持ち場のタブ、明細の作り始めとできあがり、下げる、下げたチケットと戻す、遅れの色
- 品切れ、通知の受信、新しいチケットの音

### フォルダ

| フォルダ | 内容 |
| --- | --- |
| `Components/Pages/` | 画面 (`StartupPage`、`SetupPage`、`DevicePage`、`TicketsPage`、`DonePage`、`StockPage`) |
| `Components/Controls/` | 部品 (チケットのカード `TicketCard`、数を入れる `NumberPad`、品の状態を選ぶ `StockEditDialog`、メッセージ `MessageDialog`) |
| `Components/Helpers/` | 画面に出す文字の組み立て (`ViewHelper`) |
| `Browser/` | ブラウザの機能を使う部品 (端末の鍵 `BrowserDeviceKey`、`localStorage` の `BrowserStorage`、画面を消さないことと音の `KioskScreen`)。JavaScript の部品は `wwwroot/js/` に置く |
| `State/` | 端末の設定 (`Settings`。`IDeviceContext`)、店舗とメニュー (`StoreState`)、チケット (`TicketState`)、品切れ (`StockState`) |
| `Usecase/` | 登録、チケットの再取得と操作、品切れの設定 (`KitchenUsecase`) |
| `Shell/` | 通知のレシーバ (`KitchenEventReceiver`) と、状態の報告 (`StatusReporter`) |
| `Resources/` | 画面の文言 (`Strings/AppResources.resx`、`.en.resx`) |
| `wwwroot/` | 色の役割とスタイル (`css/app.css`)、アイコンのフォント、JavaScript の部品 |

### 画面

| 画面 | 経路 | 内容 |
| --- | --- | --- |
| 起動 | `/` | 鍵を作れるブラウザかを確認し、トークン、端末の設定、通知の接続のあと、店舗、メニュー、品切れ、チケットを読む |
| 端末の設定 | `/setup` | 接続先 (アプリを配信したサーバ)、今の登録、ペアリングコード (画面の数のボタンで入れる) |
| チケット | `/tickets` | 持ち場のタブと、チケットを古い順に左から並べる (入らなければ横にスクロールする)。下部のバーから、下げたチケット、品切れ、端末を開く |
| 下げたチケット | `/done` | 直近に下げたチケットを新しい順に並べ、「戻す」 (押し間違い) を置く |
| 品切れ | `/stock` | カテゴリのバー (品切れ・残り、メニューのカテゴリ、オプション) と品の一覧 (名前、品切れと残りの数)。品を押すと状態を選ぶポップアップ (売れる、残りの数を決める、品切れ) を開き、残りの数は数のボタンで入れる |
| 端末 | `/device` | 端末の情報 (店舗、端末の名前、受け持つ持ち場、端末の ID、接続先、音の知らせ、アプリのバージョン) と、端末の設定を開くボタン |

起動:

- 鍵を作れるブラウザかは、HTTPS か localhost かで確認する
- メニューは、持ち場と品を読む
- キッチン端末として登録されていなければ進まない
- 失敗したら、30 秒ごと (テナントの停止は 5 分ごと) にリトライする

チケット:

- 持ち場のタブは、受け持つ持ち場が 2 つ以上のときに出す。  
  「すべて」と持ち場ごとに、まだ作り始めていない明細のあるチケットの数を添える
- チケットには、テーブル、何回目の注文、経過時間、持ち場 (「すべて」のとき)、明細 (数量、名前、オプション、状態)、「下げる」を出す
- 明細を押すと作り始め、もう一度押すとできあがりにする (できあがり・提供済み・取消の明細は押せない)
- 下げると、残りの明細もできあがりになる
- 経過時間は 15 秒ごとに更新する。  
  店舗の設定の遅れの時間 (`kitchenAlertMinutes`) を過ぎたチケットは、見出しを注意の色にする
- 選んだ持ち場のタブは、ほかの画面から戻っても保つ (`TicketState`)

画面に共通の扱い:

- 操作を送っている間は、ボタンを押せなくする
- ほかの端末で先に進めていた (`LINE_STATUS_INVALID`、`NOT_FOUND`) ときは、再取得した一覧を出すだけにする
- 起動を終える前に途中の画面の URL を開いたとき (再読み込みしたときなど) は、その画面を作らずに起動からやり直す (`MainLayout`)。  
  画面は、起動で読んだメニューなどを使うため
- 物理キーボードを前提にしない (バンプバーは扱わない)。  
  数は、画面の数のボタンで入れる

### 状態と通知

- 起動で、端末の設定、店舗、メニュー、品切れ、まだ下げていないチケットを読む。  
  `KitchenEventReceiver` が、通知で更新する
- 起動で読み終えるまでに届いた通知は、読んだ状態に入っていないこともあるので、ためておく。  
  読み終えたあとに、届いた順に扱う (起動からやり直すイベントだけは、すぐに扱う)
- 通知の重複は接続ごとの seq で捨て、再接続したら数え直す
- チケットの通知 (`ticket.created` / `ticket.updated`) は内容を持たない。  
  届いたら、受け持つすべての持ち場のチケットを再取得する
  - 再取得の間に届いた通知は、再取得を終えたあとに 1 回だけ再取得する
  - 再取得できなかったら、10 秒後に再取得する
  - 操作のあとの再取得と重なっても、あとに頼んだ再取得のレスポンスを、古いレスポンスで上書きしない
- 新しいチケット (`ticket.created`) は音で知らせる (続けて届いたときは、3 秒の間を空けて 1 回にまとめる)
- 品切れ (`stock.updated`) は、通知の内容で更新する
- 操作が通ったら、変わった一覧を再取得する (通知でも再取得するが、操作した画面をすぐに更新するため)
- 状態の報告は 1 分ごとに送る (ブラウザは電池を読めないので、アプリのバージョンだけ)
- 次のときは、アプリを再読み込みして起動からやり直す
  - 設定のバージョンが変わった (`store.updated`)
  - この端末を変更した (`device.updated`)
  - 通知を追跡できない (`Expired`)
  - トークンを拒否された (無効化、テナントの停止)
  - 端末の設定で再登録した

### 端末の鍵と設定

- 端末の鍵は、WebCrypto でエクスポートできない P-256 の鍵を作り、鍵の組のまま IndexedDB に持つ (`wwwroot/js/device-key.js`)
- WebCrypto は安全な接続 (HTTPS か localhost) でしか使えない。  
  起動で確認し、使えなければメッセージを出して止まる
- WebCrypto の署名は r と s を並べた形なので、`DeviceCredentials.ToDerSignature` で、インターフェイスの約束どおりの DER にして返す
- 鍵を削除するときは、IndexedDB の操作を順に並べる。  
  削除したあとの操作が、削除する前の鍵を読まないようにするため
- 登録した端末の ID は、登録した接続先と組で `localStorage` に持つ。  
  今の接続先と違えば、登録していないものとする
- 端末の名前には、管理画面で区別できるように、ブラウザごとの値を付ける (`Browser XXXX`)

### 色と言語

- スタッフ向けなので、ホール端末と同じく System の色にそろえ、チェーンの色に切り替えない
- 色の値は、`wwwroot/css/app.css` の `:root` に、役割の名前の CSS 変数で持つ。  
  ほかの場所は、役割の名前で使う
- 文言は、ブラウザの言語で選ぶ (英語のブラウザは英語、ほかは日本語)
- メニューの名前 (料理、オプション、カテゴリ) と持ち場の名前は、サーバが返す日本語のまま出す (チケットと品切れの画面で同じ名前にする)
- 状態の色は、ホール端末と同じ使い分けにする (品切れは失敗の色、残りの数と遅れたチケットは注意の色)
- 角丸・影・グラデーションは使わない
- アイコンは、Material Icons のグリフにする

### 専用端末

- EMM のキオスクのブラウザで `/kitchen` を開く想定にする (全画面と URL の固定は、ブラウザに任せる)
- キオスクのブラウザでない (アドレスバーが出る) ときは、画面に触れたときに全画面にする。  
  戻るや通知で外れたら、次に触れたときに戻す
- 画面の Wake Lock は、画面がフォアグラウンドになるたびに再取得し、画面を消さない
- 新しいチケットの音は、ブラウザが許すまで (画面に触れるまで) 出せない。  
  チケットの画面に案内のバーを出し、触れたら消す (自動再生を許したブラウザでは出ない)
- 全画面と音は、画面に触れて指を離したとき (`pointerup`) に求める (ブラウザは、タッチの触れ始めを人の操作と認めない)

## 🏭 10. サーバの実装

端末が使う API と、通知 (SignalR) を実装した。

- API: 端末の登録とトークン、店舗・メニュー・品切れ・端末の設定、来店・テーブル・注文・キッチン・提供・呼び出し・会計・支払
- 未実装のもの: 外部の連携 (OAuth のクライアント、メニューの公開、Webhook) と、実際の決済サービス ([plan.md](plan.md))

### 層

```
端末 ──REST────> Server.Web (Endpoints) ──> Server.Core (Services ──> Accessors ──> SQLite)
端末 <──SignalR── Server.Web (StoreHub <── EventDispatcher) ──> Server.Core (EventService)
                   ├─ 管理画面 (Blazor Server) ──> Server.Core
                   ├─ 電子レシートの画面 (Blazor の静的な画面) を /receipts で配る ──> Server.Core
                   └─ キッチン端末 (KitchenApp、WebAssembly) を /kitchen で配る
```

- エンドポイント (`Endpoints/`) は、リクエストの形を検証して Service に渡し、結果をレスポンスにするだけにする
- Service は `TableOrder.Contract` の Request を受けて、Response を返す
- Accessor は、2-way SQL (`Accessors/Sql/`) で DB を読み書きする
- 入力の誤りと業務の失敗は、Service が `ServiceError` (`errorCode` と項目ごとの理由) で返す。  
  エンドポイントが `ApiProblems` で、HTTP のステータスと Problem Details にする
- データベースは SQLite にする (Microsoft.Data.Sqlite に SQLitePCLRaw.bundle_e_sqlite3 を足して、エンジンを 3.x 系にする)
- `Assets/Data/Schema.sql` を起動のたびに実行して、[database.md](database.md) のすべての表を作る

### テナントのコンテキスト

- 認証のあと、アクセストークンのクレーム (`tenant_id`、`store_id`、`device_kind`、`table_id`、`station_ids`) から、リクエストのコンテキスト (`ServiceContext`) を作る。  
  Service は、そこからテナントと店舗を受け取る
- Accessor は、テナントを持つ表を引数の `tenantId` で絞る。  
  すべての SQL がテナントで絞っていることは、テスト (`SqlTenantConditionTests`) で検証する
- テナントのわからないリクエスト (端末の登録、トークンのリクエスト、決済の通知、電子レシート) で引くのは、`DirectoryAccessor` だけにする。  
  引いた行のテナントで続ける
- テナントをまたぐバックグラウンド処理 (ディスパッチャのポーリング、古いデータの削除、失効リストの再読み込み) は、`BackgroundAccessor` に置く。  
  店舗の通知を読むときは、店舗のコンテキストを始めてから Service を呼ぶ
- ログの全行に、テナント・店舗・主体 (端末) を付ける
- リクエストの外 (バックグラウンド処理、管理画面の回線) は、始めている業務のコンテキストからテナントと店舗を付ける。  
  店舗ごとのバックグラウンド処理の失敗は、テナントと店舗を入れて記録する
- HTTP のログに本文を出す設定 (`Log:HttpDump`) でも、秘密を運ぶ API (登録、トークン、端末の設定) の本文は出さない
- 利用者は、メールアドレスではなく ID で記録する

### 端末の認証

| 段階 | API | 実装 |
| --- | --- | --- |
| 登録 | `POST /api/v1/devices/pair` | ペアリングコードか登録トークンで登録し、端末と公開鍵を記録する |
| トークン | `POST /api/v1/devices/token` | 端末の鍵で署名したワンタイムの JWT を検証し、アクセストークン (ES256、30 分) を作る |
| リクエスト | `Authorization: Bearer` | JwtBearer で署名と期限を検証し、端末の種類のポリシーで使える API を絞る |

登録:

- ペアリングコード (か登録トークンのハッシュ) で `DeviceEnrollments` の行を引き、アプリの端末の種類と比べる
- 店舗の書き込みの中で台数を数えてから、端末と公開鍵 (P-256 の JWK) を記録する。  
  公開鍵の座標は、読み取った値から書き直す
- 使わなくした店舗には登録せず、使わなくしたテーブルには置かない
- 接続元ごと (IPv6 は /64 ごと) に、1 分あたりの回数でレート制限する。  
  超えたら、`429` に `Retry-After` を付ける

トークン:

- JWT は、期限が 5 分以内であることと、jti が再利用されていないこと (リプレイ防止) を検証する
- アクセストークンは、端末の記録から作る
- 同じ鍵の前の登録 (再登録する前の端末) は、ここで無効にして、前の店舗に `device.updated` を送る

リクエスト:

- 範囲の外は `403` (`DEVICE_SCOPE`) にする
- `401` には、失敗の理由 (期限切れ、署名の誤り) を付けない

署名の鍵と失効:

- 署名の鍵は、設定 (`Token:SigningKey`。P-256 の秘密鍵の PEM) から読む。  
  開発の環境で空なら、起動のたびに作る
- 端末を無効にしたときとテナントを止めたときは、次のトークンを出さない (`DEVICE_REVOKED`、`TENANT_SUSPENDED`)
- 出したトークンも、失効リスト (`RevocationList`) で拒否する (`401`)。  
  対象は、無効にしてからトークンの期限を過ぎるまでの端末と、止めたテナント
- 失効リストは、JwtBearer がトークンを検証したあとに引く (リクエストごとにデータベースは引かない)
- 通知のハブは、接続した端末を覚え (`StoreHubConnections`)、失効リストに入った接続を切る
- 端末はトークンを再取得して拒否される。  
  無効にした端末は登録からやり直し、止めたテナントの端末は再開を待つ
- 失効リストは、端末を無効にする・テナントを止める・戻す Service が、変更したあとに再読み込みさせる (`IRevocationList`)
- バックグラウンド処理 (`RevocationWorker`) も、一定の間隔 (`Token:RevocationSweepSeconds`) で失効リストを再読み込みする。  
  ほかのサーバで変更したものも、数秒で拒否する
- ハブはトークンの期限が来た接続も切り、端末は新しいトークンで再接続する

### 書き込みと通知

- 店舗の状態を変える書き込みは、`EventService.WriteAsync` の中で次の順に行う
  1. 最初に店舗の通し番号の行 (`EventSequences`) を取り、店舗の書き込みを 1 つずつにする
  2. 変えた内容の通知を、同じトランザクションで `Events` に書く (コミットしなければ通知も捨てる)
  3. コミットしたら、Core は通知の増えた店舗だけを、`IEventPublisher` でディスパッチャに渡す
  4. Web のディスパッチャ (`EventDispatcher`) が、店舗ごとに `seq` の順で読み、ハブ (`StoreHub`) のグループに送る
- ディスパッチャは、一定の間隔 (`Event:SweepSeconds`) ですべての店舗の通し番号もポーリングし、ほかのサーバが書いた通知を送る。  
  サーバを並べても、どのサーバにつながる端末にも届く
  - ポーリングは、前のポーリングから間隔ごとに行う (Core から店舗が渡され続けるサーバでも止まらない)
  - 1 つの店舗で送れなくても、ほかの店舗には送る (送れなかった店舗は、次のポーリングで再送する)
  - 起動より前の通知は送らない。  
    端末が再接続したときに、`GET /events` で受け取る
- ハブのグループは、端末の種類と置き場所 (テーブル、持ち場) ごとに作り、名前にテナントと店舗を入れる。  
  持ち場の `id` はメニューごとなので、ほかの店舗と重なりうるため
- 通知の種類ごとの送信先 (`EventRoutes`) は、ハブの送り分けと `GET /events` の絞り込みで同じものを使う
- ハブは、端末をグループに入れ終えたら、`ready` で店舗の今の通し番号を送る
  - 端末は、初めはその番号から数える (このあとに今の状態を読む)
  - 再接続したときは、欠落した通知を読む (グループに入る前に届いた通知を取りこぼさない)
  - 再接続したときに `ready` より前に届いた通知では、番号を進めない。  
    欠落した通知と合わせて渡す
- 管理画面で端末の置き場所・名前を変更したときと無効にしたときは、店舗のすべての端末に `device.updated` を送る。  
  その端末だけが、起動からやり直す
- ディスパッチャは店舗の通知を送ったら、サーバの中でその店舗を見ている画面 (`StoreActivity`。管理画面の店内状況) にも伝える。  
  ほかのサーバが書いた通知も送るので、どのサーバで開いた画面にも届く

古いデータは、クリーンアップのバックグラウンド処理 (`CleanupWorker`) が `Cleanup:IntervalMinutes` ごとに削除する。

| データ | 削除するもの |
| --- | --- |
| 通知 | 残す時間 (24 時間) を過ぎたもの |
| ペアリングコード | 期限を過ぎたもの |
| 登録トークン | 期限を過ぎるか取り消してから、1 日たったもの |
| 閉じた来店と、その確認の記録・注文・明細・チケット・呼び出し・支払・電子レシート | 営業日から `Cleanup:VisitRetentionDays` 日を過ぎたもの |
| メニューの公開 | 今のメニューと直近の `Cleanup:MenuPublicationsKept` 件を残し、それより古いもの |

- 店舗のデータ (来店とメニューの公開) は、店舗ごとにコンテキストを始めて `CleanupService` で削除する
- 来店は、`Cleanup:VisitBatchSize` 件ずつのトランザクションで、子の表から削除する (ほかの書き込みを長く止めない)
- 店舗ごとに失敗を捕まえ、ほかの店舗は続ける

### 管理画面

管理画面 (Blazor Server) は、サインインしてから、上部のバーでテナントと店舗を選んで使う。

- 選んだテナントと店舗 (`StoreSelection`) は、回線の間だけ覚える
- 画面から Service を呼ぶときは、選んだテナントと店舗をコンテキスト (`BlazorServiceScope`) に入れ、API と同じ Service をその店舗のコンテキストで呼ぶ

| 項目 | 実装 |
| --- | --- |
| サインイン | 利用者 (`AdminUsers`) をデータベースに持ち、ASP.NET Core Identity の部品を自前のストアで使う |
| 認証方式 | 既定の認証方式を経路で選び、端末の API に Cookie を通さない |
| 役割 | 運営者・テナント管理者・店舗担当者。回線ごとの範囲 (`AdminScope`) で、選べるテナントと店舗を絞る |
| 再サインイン | セキュリティスタンプが変わったときと、止めた利用者・止めたテナントのときは、サインインからやり直させる |
| 多要素 | 認証アプリのワンタイムコード |
| 仮のパスワード | 管理者が利用者を足すときと再発行するときに、管理画面で作る |
| 利用者の管理 | テナントの利用者は `AdminUserService`、運営者は `OperatorService` で変更する |
| テナントの管理 | 登録と止める・戻すは `TenantService` |
| 店舗の管理 | `StoreSetupService` |
| テーブルの管理 | `TableSetupService` |
| 登録トークン | `DeviceEnrollmentService`。店舗と端末の種類に限って出す |
| 失効リスト | 端末を無効にしたとき (`DeviceService`) と、テナントを止めた・戻したとき (`TenantService`) に再読み込みし、端末の今のトークンと通知の接続を断つ ([端末の認証](#端末の認証)) |
| 初めの運営者 | 運営者がいなければ、起動のときに設定 (`Admin:InitialOperatorEmail`、`Admin:InitialOperatorPassword`) で作る (仮のパスワード) |

サインイン:

- 使う Identity の部品: `UserManager`、`SignInManager`、パスワードのハッシュ、ロックアウト、認証アプリのコード
- 自前のストアは、`AdminUserStore` から `AccountService` を呼ぶ
- パスワードは 12 文字以上にし、5 回続けて間違えたら 15 分止める
- 間違えた回数と止める時刻は、資格情報のバージョンを見ずに 1 文で書く (同時に間違えても数え漏らさない)
- サインインと多要素のコードの送信は、接続元ごとに 1 分あたりの回数でレート制限する (`RateLimit:SignInPerMinute`)。  
  超えた送信は、同じ画面に戻してメッセージを出す

認証方式:

- `/api` と `/hubs` は端末のアクセストークン、ほかは Cookie にする
- Cookie は 8 時間 (使えば延ばす) で、ほかのサイトからの遷移では送らない

役割:

- 範囲 (`AdminScope`) は、クレーム (役割、テナント、受け持つ店舗) から作る。  
  範囲の外は、選んでもコンテキストにしない
- 開ける画面は、ポリシー (`AdminPolicies`) で絞る

再サインイン:

- セキュリティスタンプ (`SecurityStamp`) は、Cookie と開いている回線のどちらも、1 分ごとに確認する
- 止めた利用者と、止めたテナントの利用者には、Cookie を再発行しない (パスワードの変更など)。  
  止めた利用者の資格情報は書かない
- セキュリティスタンプは、扱える範囲と資格情報 (役割、受け持つ店舗、パスワード、多要素、止める) を変えたときに変える。  
  名前だけなら変えない
- 回線は Cookie を延ばさないので、始めてから Cookie の期限 (8 時間) を過ぎたら、再サインインさせる

多要素:

- 鍵は文字で出し、データ保護で暗号化して持つ
- 回復用のコードも、鍵と同じくデータ保護で暗号化して持つ (DB だけが漏れても使えない)
- 使い始めるときは、先に回復用のコードを書く
- 外すときは、鍵とコードを捨てるのと一緒に、1 回の書き込みで外す
- 書けなかったら、Cookie を再発行せずにメッセージを出す

仮のパスワード:

- 管理画面で作ってハッシュにし、Service には平文を渡さない
- 平文は一度だけ見せる
- 仮のパスワードでサインインしたら、パスワードを変更するまで、ほかの画面 (アカウントと多要素の画面も) を開かない
- 今のパスワードと同じものには、変更させない

利用者の管理:

- `AdminUserService` は、選んだテナントで絞る
- メールアドレスは、すべてのテナントで一意にする。  
  足すときに形式を検証する (利用者名に使うので、Identity の文字の制限は使わない)
- 自分の役割は変えず、自分は止めない

テナントの管理:

- 止めると、テナントの利用者のセキュリティスタンプを変えて、開いている管理画面を再サインインさせる。  
  端末の登録とトークンも拒否する

店舗の管理:

- 新しい店舗の設定 (言語、支払方法、電子レシート、機能、呼び出しの用件、今のメニュー) は、選んだ店舗からコピーする
- 電子レシートの事業者の名前と登録番号は、コピーしない (フランチャイズの店は違うため)
- コピーしないときは、既定の設定 (電子レシートは出さない) とサンプルのメニュー (外部の連携でメニューを公開するまでの仮) にする
- 基本を変更したら、設定のバージョンを上げて `store.updated` を送る
- 使わなくするのは、使っている端末と開いている来店がないときだけ。  
  使わなくした店舗には、端末を登録しない

テーブルの管理:

- 追加・変更・並べ替え・使わなくするたびに、店舗の設定のバージョンを上げて `store.updated` を送る。  
  端末は、起動からやり直してテーブルを再読み込みする
- 使わなくするのは、来店中でなく、端末を置いていないときだけ

登録トークン:

- 台数 (1~1000) と期限 (1~30 日) を決めて出す
- トークン (32 バイトの乱数) は、出した画面で接続先と並べて一度だけ見せる。  
  サーバはハッシュだけを持つ
- 取り消すと、それからの登録を拒否する (登録した端末はそのまま)
- 登録した端末は、置き場所を割り当てるまで待つ

画面:

- サインイン・多要素のコード・パスワード・多要素の登録の画面は、Cookie を書くので、対話しない静的な画面にする (`[ExcludeFromInteractiveRouting]`)
- サインアウトはフォームの POST (`/account/sign-out`) で受け、偽造防止トークンを検証する

| 画面 | できること |
| --- | --- |
| サインイン (`/account/sign-in`) | メールアドレスとパスワード。多要素認証を使う利用者は、続けて認証アプリのコードか回復コード (`/account/sign-in-2fa`)。どこを間違えたかは分けて出さない |
| アカウント (`/account`) | 名前、役割、多要素認証の状態、パスワードの変更 (`/account/password`)、多要素認証の登録と解除・回復コードの再発行 (`/account/two-factor`)、サインアウト |
| ダッシュボード (`/`) | 契約中のテナント (運営者) か、担当店舗 (テナントの利用者) の一覧 |
| 端末 (`/devices`) | 店舗の端末の一覧、ペアリングコードの発行、登録トークンの発行と一覧・取消、置き場所の割り当てと名前の変更、無効化 |
| チェーン (`/brand`) | チェーンの名前 (日本語、英語)、ロゴ (置いた画像から選ぶ)、色 (役割ごと。空なら端末の既定の色)。運営者とテナント管理者だけが開ける |
| 利用者 (`/users`) | 選んだテナントの利用者 (テナント管理者と店舗担当者) の一覧、追加 (仮パスワードを一度だけ出す)、名前・役割・担当店舗の変更、仮パスワードの再発行、多要素認証の解除、停止・再開。運営者とテナント管理者だけが開ける |
| 店舗 (`/stores`) | 選んだテナントの店舗の一覧、追加、基本の変更、利用停止・利用再開。運営者とテナント管理者だけが開ける |
| テーブル (`/tables`) | 選んだ店舗のテーブルの一覧 (表示順、名前、エリア、席数、端末、状態)、追加、変更、並べ替え (前後と入れ替える)、利用停止・利用再開 |
| テナント (`/tenants`) | テナントの一覧 (コード、会社名、チェーン名、店舗数、状態)、登録、停止・再開 (確認してから)。運営者だけが開ける |
| 運営者 (`/operators`) | 運営者の一覧、追加、名前の変更、仮パスワードの再発行、多要素認証の解除、停止・再開。運営者だけが開ける |
| 店舗設定 (`/store-settings`) | 案内方法、機能の有無、言語、支払方法、電子レシート、呼び出しの用件、スタッフ PIN |
| 店内状況 (`/floor`) | テーブル・来店・呼び出し・品切れ・通知履歴の表示と、来店の登録・会計済み・取消 |

端末 (`/devices`):

- 端末の一覧: 種類、割り当て、最終通信、電池残量、アプリのバージョン、状態。  
  割り当てを待つ端末を先に出す
- ペアリングコードの発行: 種類と置き場所を決める。  
  有効期限 10 分、1 台のみ
- 登録トークンの発行: 種類、上限台数、有効期間を決める。  
  管理対象の構成のキー (`apiEndPoint`、`enrollmentToken`) と値を、一度だけ見せる

店舗 (`/stores`):

- 追加で入れるもの: 店舗コード、店舗名、タイムゾーン、営業時間、ラストオーダー、消費税の端数処理、注文の上限、スタッフ PIN、設定のコピー元

店舗設定 (`/store-settings`):

- 案内方法: スタッフ、受付機、セルフ着席
- 機能の有無: お会計のレジ払い、割り勘、ラストオーダーのお知らせ、お礼の画面の表示時間、キッチンの遅れの警告、時間帯の終了後の注文の猶予
- 電子レシート: テーブルで払い終えた来店に作り、お礼の画面に QR を出す。  
  レシートに出す事業者名と登録番号 (`T` と 13 桁) も入れる。  
  登録番号を入れるときは、事業者名も要る
- 呼び出しの用件: 使うものを選ぶ
- スタッフ PIN: 入れたときだけ変更する

店内状況 (`/floor`):

- テーブルの一覧: 空き・来店中・会計中、人数、経過時間、未提供、呼び出し
- 押したテーブルの来店: 人数、注文と明細の状態、注文額
- 未完了の呼び出し (用件の名前)、品切れと残数 (メニューの名前)、通知履歴 (直近の通知の種類と時刻)
- 空いているテーブルは、「来店登録」 (人数) ができる
- 来店は、「レジ会計済み」と「来店取消」 (注文のないまま帰った) ができる。  
  「レジ会計済み」は、依頼前の食後の品があれば、作らないことを確認で伝える
- 店内状況は、ホール端末が使えないときに来店を開き・閉じる画面を兼ね、ホール端末の API と同じ `VisitService` を呼ぶ (テーブル端末には同じ通知が届く)
- 選んだ店舗の通知を送るたびに (`StoreActivity`)、少し待ってから再取得する。  
  再取得しても、選んだテーブルと入れている人数は変えない

そのほか:

- チェーンと店舗の設定を変更すると、設定のバージョン (`Stores.SettingsVersion`) を上げて `store.updated` を送る。  
  チェーンの設定は、テナントのすべての店舗のバージョンを上げる
- テーブル端末は、待受で起動からやり直して反映する
- 管理画面はどの環境でも開き、サインインの画面のほかはサインインを求める
- API の説明 (Swagger UI) は、開発の環境だけで開く

### 電子レシート

テーブルで払い終えた来店の電子レシートは、お客様がお礼の画面の QR から開く画面 (`/receipts/{token}`) で見せる。

- サインインのない静的な画面にする (`[AllowAnonymous]`、`[ExcludeFromInteractiveRouting]`)
- 管理画面の外の素のレイアウト (`ReceiptLayout`) に、スマートフォン向けの 1 列で出す

| 項目 | 実装 |
| --- | --- |
| 引き方 | 推測できないトークン (16 バイトの乱数) で、電子レシートの行を引く (`DirectoryAccessor`)。その行のテナントと店舗で、来店・明細・支払を読む (`ReceiptService`) |
| 内容 | チェーンと店舗の名前、払い終えた日時 (店舗のタイムゾーン)、テーブル、明細、合計、税率ごとの対象額と税額 (内税)、支払 (方法と額)、事業者の名前と登録番号 |
| 事業者 | 店舗の設定の事業者の名前と登録番号を、電子レシートを作るときにコピーする (あとで変更しても、出したレシートは変えない)。登録番号のない店は、登録番号のないレシート (適格簡易請求書でない) にする |
| 言語 | ブラウザの言語 (`Accept-Language` の重みの順) で、日本語か英語を選ぶ (`ReceiptTexts`)。品の名前とオプションは、メニューの名前のその言語 (ない言語は日本語) |
| 見られる期間 | 来店と同じ (クリーンアップで来店と一緒に削除される) |
| 見つからないとき | `404` で「見つかりません」だけを出す (トークンがあるかないかのほかは見せない) |
| キャッシュと検索 | `Cache-Control: no-cache, no-store` と `X-Robots-Tag: noindex` を付ける |

- 明細と税は、会計と同じ計算 (`BillCalculator`) で作る。  
  閉じた来店は変わらないので、明細をコピーしない
- 明細には、品の名前とオプション、単価と数量、金額を出す。  
  税率が 2 つ以上なら、税率を添える

| `GET /api/v1/visits/{id}/receipt` | テーブル (自分のテーブル) | 電子レシートの URL と合計 (来店を閉じたあと。画面は [電子レシート](#電子レシート)) |
| `POST /api/v1/payments/callbacks/fake` | 匿名 (開発の環境だけ) | 仮の決済サービスの結果の通知 |
| `GET /api/v1/events?after=` | すべて | 欠落した通知 (端末の種類と置き場所に合うもの) |
| `/hubs/store` (SignalR) | すべて | 通知 (`event`) と、グループへの追加の完了 (`ready`。店舗の今の通し番号) |

- 端末の設定は、チェーンの名前・ロゴ・色、店舗の設定、呼び出しの用件、端末と置き場所を返す。  
  店舗の設定は、機能の有無、言語、支払方法、スタッフの PIN のハッシュ、設定のバージョン
- 来店の開始: 受付機はテーブルを送らず、人数の入る空席のうち定員の小さいテーブルに、サーバが開く (空席がなければ `NO_VACANT_TABLE`)。  
  テーブル端末は、自分のテーブルに開く
- 来店の操作
  - 移動は、開いているチケットも持ち場に通知する
  - 来店の終了は、会計中の待っている支払をやめる
  - 取りやめは、来店のバージョンで確認する
  - 来店を終えたら (テーブルで払い終えたときも)、終わっていない呼び出しを終える
- 注文を受けるときは、メニュー・オプション・数量・出せる条件・品切れ・ルールを検証し、残りの数を減らす。  
  出せる条件は、受けた時刻と来店の子どもで見る (時間帯の終わりは、店舗の設定の猶予まで受ける)

### 画像

- 画像 (料理の写真、チェーンのロゴ) は、テナントごとの保存先 (`IImageStore`) に名前で置く。  
  `ImageService` が名前を検証して返す
- 保存先は、開発とテストはファイル (`FileImageStore`。実行のフォルダの `images/{テナント}/`。設定 `Image:Directory`)、本番は Amazon S3 にする
- 名前は内容が変わると変わる (内容のハッシュを入れる) ので、置いた画像は変更しない
- 名前のルール (英小文字・数字・`-`・`_`・`.`、拡張子) は、`TableOrder.Domain.ImageNames` にある。  
  端末も、保存の前に同じもので検証する

### 決済と開発の環境のシミュレーション

- 決済サービスは、`IPaymentProvider` の実装で切り替える
- 今は仮の決済サービス (`FakePaymentProvider`) で、QR の内容を作る。  
  結果は、開発の環境の通知 (`POST /api/v1/payments/callbacks/fake`) か、シミュレーションで受ける
- 開発の環境では、スタッフ (キッチン、ホール) と決済サービスの代わりに、サーバが時間で進める (`Simulation` の設定。テストでは止める)
- 進めるもののある店舗をテナントをまたいで探し (`BackgroundAccessor`)、店舗ごとにコンテキストを始めて `SimulationService` を呼ぶ。  
  業務の処理と同じ書き込みと通知で進める
- ホール端末で提供と呼び出しを確認するときは、提供と向かうまでの秒 (`Simulation:ServedSeconds`、`Simulation:AcknowledgeSeconds`) を長くして起動する (サーバが先に進めないように)

| 対象 | シミュレーションの動き |
| --- | --- |
| 明細 | 注文 (食後の品はお願い) からの時間で、作り始め・できあがり・提供と進める |
| チケット | 明細がそろったら下げる |
| 払い終えて閉じた来店の品 | 進める (キッチンは作り続け、ホールはお席に運ぶ) |
| 呼び出し | 向かってから、対応を終える |
| 待っている支払 | 払い終える |

### 動かし方

- `dotnet run --project server/src/TableOrder.Server.Web` で起動し、8080 番で受ける (開発の環境は Swagger UI を `/swagger` に出す)
- テレメトリと一緒に動かすときは、Aspire の `server/src/TableOrder.Server.AppHost` を起動する
- スキーマは `CREATE TABLE IF NOT EXISTS` で作る。  
  表に列を足したときは、開発の DB (実行のフォルダの `data.db`) を削除して作り直す
- 開発の環境では、サーバが調理・提供・呼び出し・支払を時間で進めるので、テーブル端末だけで注文から会計までを確認できる
- テーブル端末をつなぐときは、端末の設定で接続先を開発のサーバ (エミュレータからは `http://10.0.2.2:8080`) にし、ペアリングコード (`100001`) で登録する
- 受付機で受け付けるときは、管理画面の店舗の設定で、来店の開き方を受付機にする。  
  サンプルのデモの店舗はスタッフなので、そのままでは受付機の待受に受付を止めている文言が出る
- 管理画面 (`/`) は、サンプルの利用者 (`operator@example.com` などと `tableorder-dev`) でサインインして開く
- 端末の画面 (`/devices`) でペアリングコードを出せば、サンプルの決まったコードのほかにも端末を登録できる
- 本番の環境では、初めの運営者のメールアドレスと仮のパスワード (`Admin:InitialOperatorEmail`、`Admin:InitialOperatorPassword`) を、シークレットで渡して起動する
- キッチン端末は `/kitchen` を開き、ペアリングコード (`100201`) で登録する。  
  端末の鍵に WebCrypto を使うので、HTTPS か localhost で開く
