# 実装計画

ファミリーレストランのテーブルに置くタブレットで、お客様が自分で注文するアプリ (テーブルオーダー) の実装計画。  
最初は画面とモックのレスポンスで作り、注文サーバができてからは端末を注文サーバにつないで動かす (モックは外した)。

- 業務の前提は [business.md](business.md) に合わせる
- 通信の形は [api-design.md](api-design.md) の想定に合わせる
- 作ったものの構成は [architecture.md](architecture.md) に書く

フェーズを終えたらチェックを付ける。  
作り終えたら設計文書に移し、この文書は消す。

## 🎯 前提

| 項目 | 内容 |
| --- | --- |
| 業態 | ファミリーレストランのチェーン (店内飲食。ドリンクバーあり、時間制のコースなし) |
| 対象 | テーブル端末は Android のタブレット (10 インチ前後、1920x1200、横向き)、ホール端末は Android のスマートフォン (縦向き) |
| 会計 | テーブル端末で行う (QR コード決済、クレジットカード)。現金はレジ |
| 言語 | 日本語と英語 (画面の文言、メニューの名前と説明) |
| 来店の開始 | 店舗の設定で、ホール端末 / 受付機 / テーブル端末から選ぶ ([来店の開き方](#-来店の開き方))。ホール端末はどの形でも開ける |
| 店舗の設定 | 端末はサーバとつながる前提。チェーンの名前・印・色・機能・料理の写真を、チェーンと店舗の設定から受け取る (1 つのアプリでほかのチェーンの店でも使う) |
| 構成 | モノレポ。区分 (共有、サーバ、端末) ごとのフォルダに置く ([プロジェクト](#プロジェクト)) |
| 通信 | リクエストは REST (Minimal API) か gRPC。通知・プッシュ・端末の状態は SignalR か gRPC のストリーム |
| テレメトリ | OpenTelemetry (OTLP) |
| 特例の扱い | ドリンクバー、お酒、キッズ、数量限定などはコードで分けず、メニューのタグとルールの設定で表す |
| 技術 | .NET 11 / .NET MAUI、画面の切り替えは Smart.Navigation |
| 基にした構成 | template-maui-keyboard (物理キーと Input 関連を除く)、example-maui-pos の端末、template-avalonia-desktop の画面の切り替え、template-maui-server の通信 |
| 確認 | エミュレータ Tablet_1920x1200_Android15 (220dpi、約 1396x873dp) |
| 将来 | Android の MDM 用 API (Device Owner、ロックタスク) で専用端末にする |

- 来店の開始の形
  - ホール端末: スタッフが開く
  - 受付機: お客様が人数を入れ、サーバが席を決める
  - テーブル端末: お客様が始める
- ホール端末が使えないときは、管理画面の店内状況で来店を開く
- 通信のエンドポイントが違っても、業務の処理は同じにする

## 🔎 UI の調査

国内のテーブルオーダーと海外のセルフオーダー (キオスク) の機能・画面の構成・UX の知見を調べ、取り込むものを決めた。

### 共通する機能

- 写真付きのメニュー、おすすめの表示、カスタマイズ (部位、ソース、サイズ)
- 注文履歴、スタッフの呼び出し
- 品切れ、アレルギーの表示、多言語 (英語・中国語・韓国語など)
- 会計 (POS との連携、割り勘、セルフレジ、テーブル決済)
- 年配の客層にも読める文字の大きさ、説明の要らない操作

### 画面の型

- 上にカテゴリを置き、写真付きの商品の一覧を並べる。  
  注文 (カート) は常に見えるところに件数と合計を出す
- 商品の詳細でオプションと数量を選んでからカートに入れる。  
  カートの中でも数量やオプションを直せる
- 注文を確定する前に内容を確認する
- 注文・履歴・会計を 1 つの画面の中の操作で回す

### UX の知見

- タッチの的は 10mm 以上 (年配の方は 11.4mm 以上)、間隔は 3〜12mm がよい
- 追加の提案 (アップセル) は注文の途中で何度も割り込まず、確定の前に 1 画面にまとめる (1 回の注文で 3 回未満)
- 提案を受ける / 断るボタンは同じ大きさ・同じ重みにする (断りにくくする設計は信頼を損ねる)
- アレルギーはカードと詳細の 2 段で示す
- 料理の写真を主役にする

### 飲食チェーンの例

- 大手のファミリーレストランのチェーンには、客席のデジタルメニューブックでテーブル決済 (QR コード決済、アプリのクレジット) をするところがある
- 回転寿司のチェーンには、入口のタッチパネルでチェックインすると、自動の案内で席に誘導するところがある (人数は受付で決まり、席の端末で注文する)
- POS の伝票は人数とテーブルを持つ (注文の API に客数とテーブルの項目がある)。  
  人数は客数として客単価の分母になる

### 取り込むこと

| 調べたこと | 本アプリでの形 |
| --- | --- |
| カテゴリを上に、カートを常に表示 | 上部のタブ、右に固定した注文リスト (件数と合計) |
| 詳細でオプションと数量を選ぶ | カードから商品の詳細を開く (オプションのない商品はカードの + ですぐ入れる) |
| 確定の前の確認 | 注文の確認 (追加の提案は 1 枠だけ) |
| 履歴・呼出・会計 | 下部の操作バー |
| ドリンクバー | 単品とセットのオプションにタグ (`drink-bar`) を付け、人数より少なければ提案のルールで注文の確認に出す |
| 食後のデザート | 詳細で「食後にお持ちする」を選べ、注文履歴からお願いする |
| テーブル決済 | お会計の画面で QR コード決済とカード、電子レシートの QR |
| 人数 | 来店の開始で入れ (今はテーブル端末でお客様が入れる)、ヘッダに出す。提案のルールと割り勘の目安に使う |
| 品切れ・アレルギー | カードに品切れの幕、詳細にアレルギー (特定原材料 8 品目) とカロリー |
| タップ領域 | 64dp (約 10mm) 以上、主な操作は 80dp 以上 |

## 🌐 接続先と障害対策の調査

テーブルオーダーと飲食店の POS (国内外のクラウド型の製品) が、どこにつなぎ、回線が切れたときにどうしているかを調べた。

### 店舗の中の仕組みの型

| 型 | 接続先 | 店舗の中の仕組み | 回線が切れたとき |
| --- | --- | --- | --- |
| ハブの端末 | クラウド | 有線でつないだ 1 台をハブにし、同じ LAN の端末・キッチンの表示・キッチンプリンタをつなぐ | 注文は LAN の中でキッチンの表示とプリンタに届く。回線が戻るとクラウドへ送る |
| 店舗のサービス | クラウドと店舗のサービス | 店舗に取引を受け持つサービスを置く | 店舗のサービスが取引をため、回線が戻ると送る。設定の変更は届かず、レポートは遅れる |
| 店舗の機器 | クラウド | オプションの小さな機器を店舗に置く | 注文を機器にためて営業を続け、回線が戻るとクラウドへ送る |
| 端末の間の LAN | クラウド | 端末どうしが LAN でつながる | LAN が生きていれば、注文・キッチンの印刷・端末の間の共有は続く。カード決済とメニューの変更は止まる |
| 端末に保存 | クラウド | 端末に注文と売上を残す | 注文と売上を端末に残して営業を続ける |

- 多くはクラウドを正とし、回線が切れても注文を厨房へ通す仕組み (ハブの端末、店舗のサービス、店舗の機器) を店舗に置く
- 回線が切れている間に止まるのは、カード決済 (オンラインの承認)、メニューと設定の変更の配信、本部のレポート
- 共通の備えは、LTE の予備回線、SD-WAN、UPS、ハンディや手書きの伝票への切り替え

### 本アプリでの考え方

| 段階 | 接続先 | 回線が切れたとき |
| --- | --- | --- |
| 1 (最初) | 端末はクラウドの注文サーバに直接つなぐ | 縮退して動く |
| 2 (必要になったら) | 店舗にエッジ (同じ API を出す小さなサーバ) を置き、端末はエッジにつなぐ。エッジはクラウドと同期する | 店舗の LAN の中で注文・調理・提供・呼び出しを続け、回線が戻ると同期する |

- 段階 1 の縮退
  - 注文は端末に残し、同じ `id` で再送する
  - 通知は再接続し、通し番号 (`seq`) で追いつく
  - 会計はレジへ案内する
- 店舗のエッジもクラウドと同じ API (リクエストと通知) を出す。  
  端末は接続先を変えるだけで済む
- どちらの段階でも、次の仕組みで障害に気付いて戻せるようにする
  - 端末が採番する `id` (再送で重複しない)
  - 通知の通し番号とキャッチアップ
  - 端末の状態とテレメトリの監視 (SignalR、OTLP)

## 🎨 デザイン

### 方針

- 角丸・影・グラデーション・すりガラスを使わない (よくある生成された UI の見た目を避ける)
- 明るい背景のボタン・タブ・メッセージのアイコンは色付きの絵文字にし、何をするものかを一目でわかるようにする。  
  色で塗ったボタンと濃いバーは、白い単色のアイコンにする
- 四角い面と罫線と色の面で組む。  
  バー (ヘッダ、タブ、下部の操作) は画面の端まで通し、隣の列のバーと高さを揃える
- 料理の写真と、料理名・価格の文字組みで見せる
- 色は役割の名前で定義し、チェーンのイメージカラーに切り替えられるようにする
- 起動と端末の設定 (システムの画面) は、チェーンの色ではなくシステムの色とロゴで組む
- 英語では語が長くなる。  
  タブとボタンは幅に余裕を持たせ、料理名は 2 行まで折り返す

### 色の役割

色は `Resources/Styles/Colors.xaml` に役割の名前で定義し、スタイル・画面・アイコンは役割の名前だけを使う。  
表の色は既定の色。  
Brand・Neutral・Status の役割は、起動のときにチェーンの設定の色に切り替える (実装は [architecture.md](architecture.md#-5-多言語と色))。

| 区分 | 役割 | 既定 | 使うところ |
| --- | --- | --- | --- |
| Brand | `Primary` / `PrimaryPressed` / `OnPrimary` | 朱 `#C53D13` | 選択中のタブ、注文の確定などの主な操作 |
| Brand | `PrimaryContainer` / `OnPrimaryContainer` | 淡い朱 `#FBE4DA` | 件数、選んだオプション、提案の枠 |
| Brand | `Secondary` / `SecondaryPressed` / `OnSecondary` | 墨 `#22201C` | お会計などの強い操作、待受の地 |
| Neutral | `Canvas` | `#F3F0EA` | 画面の地 |
| Neutral | `Surface` / `SurfaceVariant` | `#FFFFFF` / `#EAE6DE` | 面 (ヘッダ、タブ、カード、パネル) / 沈んだ面 (押下、増減のボタン) |
| Neutral | `OnSurface` / `OnSurfaceVariant` | `#22201C` / `#6B665C` | 本文 / 補足の文字 |
| Neutral | `Outline` / `OutlineVariant` | `#D6D0C4` / `#E7E2D9` | 罫線 / 薄い区切り |
| Neutral | `Disabled` / `OnDisabled` | `#E4E0D8` / `#A29C90` | 押せない操作 |
| Neutral | `Scrim` / `OnScrim` | 黒 60% / 白 | ポップアップの後ろと売り切れの幕 |
| Status | `Error` / `OnError` | `#B3261E` | 失敗 |
| Status | `Success` / `OnSuccess` | `#2E7D32` | 注文と支払の完了 |
| Status | `Warning` / `OnWarning` | `#A15C00` | まだ出していない品、ラストオーダー |
| System | `SystemCanvas` / `SystemSurface` / `OnSystemCanvas` / `OnSystemCanvasVariant` / `SystemOutline` / `SystemAccent` / `SystemAccentPressed` / `OnSystemAccent` | 灰 `#F4F5F7`、墨 `#1F2328` | 起動、端末の設定、電卓 (スプラッシュとアプリのアイコンの色と揃える) |

- 面と文字は対 (`Xxx` と `OnXxx`) で使い、コントラスト比 4.5 以上を保つ
- アイコン (`Markup/AppIcons`) は色の値を持たず、役割の名前から色を引く
- チェーンの設定の色 (`brand.theme`) は、役割の名前と色の組で受け取る。  
  設定にない役割は既定の色にする

### チェーンの名前と印

- チェーンの名前とロゴは、チェーンの設定 (`brand.name`、`brand.logoImageName`) から受け取る。  
  ヘッダと待受の印に出す (1 つのアプリでほかのチェーンの店でも使う)
- ロゴは地の色を含む正方形の画像にする。  
  保存していない間は、印に名前の頭の文字を出す
- 店舗の名前 (端末の設定の `storeName`) は店ごとの値で、チェーンの名前とは分ける (今の画面には出さない)

サンプルのデータのチェーン:

| チェーン | ロゴ | 色 |
| --- | --- | --- |
| バニーズ (Bunny's) | うさぎ | 既定の色 |
| さつき軒 (Satsukiken) | サツキの花 | 紅と藍 |

### 寸法と文字

| 要素 | 寸法 |
| --- | --- |
| ヘッダ | 高さ 64dp |
| カテゴリのタブ | 高さ 64dp、幅 144dp 以上 |
| 下部の操作・注文の確定 | 高さ 80dp |
| 注文リストの列 | 幅 400dp |
| メニューのカード | 4 列 3 段、高さ 208dp (絵 148dp、文字 2 行 60dp)、間隔 8dp |
| 注文リストの行 | 2 段 (料理名と数量の増減 64dp、食後の印・オプション・金額) |
| タップ領域 | 64dp 以上 (主な操作は 80dp 以上) |

- メニューのカードは 1 画面に 4 列 3 段 (12 品) を見せる (注文リストを右に置く注文端末は 3 段が多い)
- ヘッダ・タブ・下部の操作はタップ領域の高さまで詰め、残りの高さをカードの絵に回す

| 用途 | 文字の大きさ |
| --- | --- |
| 待受の見出し | 72 |
| 合計の金額 | 28〜32 |
| ヘッダ・パネルの見出し、詳細の価格 | 22〜24 (太字) |
| タブ・操作 | 20〜22 (太字) |
| 本文 | 18 |
| カードの料理名と価格 | 17 (太字) |
| 補足 | 13〜16 |

### 写真の代わり (サンプル)

- 料理の絵 (4:3) をサンプルの写真としてサーバに置き、カテゴリで地の色を変える
  - 肉料理: 木の台と鉄板
  - パスタとサイド: 白い皿
  - デザート: 淡い桃色
  - ドリンク: 淡い青
- 端末は写真を保存していない間、写真の場所に面の色とチェーンのロゴを出す (ロゴもなければナイフとフォークのアイコン)
- 実際の写真はサーバから受け取り、端末に保存して使う ([店舗の設定で動く端末](#-店舗の設定で動く端末))

## 📐 メイン画面の配置

上にヘッダとカテゴリのタブ、左にメニューのカード、右に注文リスト、下に履歴・呼出・会計を置く。  
注文リストの列は右端に固定し、注文の確定は下部の操作バーと同じ高さに並べる。

```
+------+---------------------------------------+--------------------+------------------+
| ##   | チェーンの名前                        | テーブル 12・3 名  | 言語 / Language  |  ヘッダ 64dp
+-----------+------------+---------+-----------+---------+-------+---------------------+
| おすすめ  | ハンバーグ | パスタ  | デザート  | キッズ  | …     | ご注文リスト  [4]   |  タブ 64dp / 注文リストの見出し
+-----------+------------+---------+-----------+---------+-------+---------------------+
| +------------+ +------------+ +------------+ +------------+    | ハンバーグ [-] 2 [+]|
| |人気        | |            | |   売切れ   | |NEW         |    | セット・DB    ¥3,256|  メニュー (4 列 3 段のカード)
| |          + | |          + | |            | |          + |    | パフェ     [-] 1 [+]|  注文リスト (2 段の行)
| |ハンバーグ  | |ドリア      | |ステーキ    | |パフェ      |    | 食後            ¥699|
| |        ¥999| |        ¥599| |      ¥1,499| |        ¥699|    | サラダ     [-] 1 [+]|
| +------------+ +------------+ +------------+ +------------+    |                 ¥459|
| (同じ高さのカードがあと 2 段。多いときは縦にスクロール)        |                     |
|                                                                +---------------------+
|                                                                | 合計 (税込) ¥4,414  |
+---------------------+---------------------+--------------------+---------------------+
| 注文履歴            | 店員呼出            | お会計 (補助色)    | 注文を確定する      |  操作 80dp (主色は確定だけ)
+---------------------+---------------------+--------------------+---------------------+
```

- ヘッダ: チェーンの名前、テーブルと人数、言語 (今の言語を出し、押すと言語を選ぶポップアップを開く)
- カテゴリのタブ: 横にスクロールする。  
  続きがある向きの端に送りのボタン (‹ ›) を重ね、まだタブがあることを示す
- カード: 写真、料理名 (2 行まで)、価格 (税込)、印 (おすすめ、人気、NEW、期間限定)、品切れの幕、すぐ入れる + (オプションのない商品だけ。写真の右下に重ねる)
- カードの文字は 2 行の高さで揃える
  - 料理名の 1 行目は価格の上まで使う。  
    2 行目に入ったときだけ価格の分を空け、価格は最後の行の右に置く
  - 行の高さは固定し、英語でも価格を料理名の 2 行目にそろえる
- カードを押すと商品の詳細 (プレビュー) を開く
- 注文リストの行: 上の段に料理名と数量の増減 (0 で削除)、下の段に食後の印、選んだオプション、金額。  
  オプションは省略せずに折り返して全部見せる。  
  行を押すと詳細を開いて直せる
- 注文の確定は、リストが空のときは押せない

### キッチン端末

キッチン端末は表示とサーバへの操作だけなので、Web の画面を全画面で出せば足りる。  
ブラウザの全画面 (操作が要り、戻るや通知で外れる) には頼らず、次のようにする。

| 課題 | 対応 |
| --- | --- |
| 全画面 | EMM のキオスクのブラウザで URL を固定して開く |
| 通信が切れたとき | 表示を保ち、つながったら `seq` で欠落した通知を再取得する。Blazor Server は切れると操作できないので、WebAssembly にする |
| 音の通知 | キオスクのブラウザで自動再生を許す (許せない端末は、起動したあとに 1 回触れてもらう) |
| 画面を消さない | 画面の Wake Lock か、端末の設定 |
| 端末の登録 | ペアリングコードを 1 回入れる。鍵はブラウザから取り出せない形で持つ |
| バンプバー | 扱わない (物理キーボードを前提にせず、触って操作する) |
| 伝票のプリンタ | 扱わない (KDS を前提にする) |

- EMM のキオスクのブラウザがない店や、自前の Device Owner の店のために、Web の画面を全画面で開くだけの端末アプリ (WebView) を作る余地を残す
- API クライアントのライブラリ (`TableOrder.Client`) は WebAssembly でも動く。  
  テーブル端末と同じく、このライブラリの API クライアント (`IKitchenApi`、`IOrderEvents`) を使う

### ほかのアプリ

| アプリ | 判断 | 内容 |
| --- | --- | --- |
| 管理画面 (店舗と端末) | 作る (`Server.Web` の中に置く) | 端末のペアリングとテーブルの割り当て、登録トークン、店舗の設定 (注文の一時停止、ラストオーダー、色)、端末の状態 |
| 受付機 | 作る | 来店の開き方を受付機にした店で、お客様が入れた人数からサーバが席を決めて来店を開く。受付機は席を案内する (順番待ちは扱わない) |
| お客様のスマートフォンからの注文 | 作らない (API の想定の範囲の外) | 作るならサーバが配信する Web アプリ (`TableOrder.{用途}App`) にし、読み込みの軽さを優先した構成を別に考える |
| 店舗のエッジ | 検討 | サーバ (`Server.Core`、`Server.Web`) を店に置き、クラウドとの同期を足す形にする |
| 本部の管理システム、POS、決済サービス、配膳ロボット | 外部のシステム | サーバのエンドポイント (API、Webhook) でつなぎ、このリポジトリにアプリは作らない |

### 決めたこと (サーバ)

- リクエストは REST (Minimal API)、通知は SignalR で作る。  
  gRPC は必要になってから足す (業務の処理はエンドポイントによらず同じにしてある)
- 接続先はクラウドに直接つなぐ (店舗のエッジは後で考える)
- 端末の認証は、端末の鍵で署名した短命の JWT にする (流れは [api-design.md](api-design.md#15-認証認可)、決めるときに調べたことは [端末の認証](#-端末の認証))
- 複数の会社 (テナント) が契約して使う形にする (ルールは [api-design.md](api-design.md#16-テナント)、決めるときに調べたことは [マルチテナント](#-マルチテナント))
  - テナントと店舗はアクセストークンのクレームで決め、認証のあとは信用する
  - リクエストの中の `id` は、テナントと店舗の中で引く
- 外部のシステムは、テナントごと (POS は店舗ごと) のクライアントで、OAuth 2.0 の client credentials のアクセストークンを受け取る
- ホール端末は .NET MAUI、キッチン端末は Web (Blazor WebAssembly) で作る
- データベースは template-maui-server と同じ SQLite で始め、本番は Amazon RDS にする (エンジンと移し方は [本番の環境](#-本番の環境))
- 本番は AWS。  
  サーバはコンテナにして Amazon ECS (AWS Fargate) で動かし、インフラは C# の IaC (AWS CDK) で定義する ([本番の環境](#-本番の環境))
- データベースの表は [database.md](database.md) の設計に合わせる
- 通知はデータベースの `Events` を正にする。  
  サーバごとのディスパッチャが通し番号の順に読み、ハブで送る (サーバを並べてもバックプレーンを置かない)
- データベースは 1 つにし、すべての表に `TenantId` を持たせる (主キー・索引・外部キーの先頭にも置く。[database.md](database.md#テナントの持ち方))
- API の URL はリソースごとに 1 つにし、端末の種類ごとに使える範囲を認可で絞る (端末ごとの一覧は [api-design.md](api-design.md#-4-端末ごとの-api))

### 通信 (想定)

| エンドポイント | 内容 |
| --- | --- |
| REST (Minimal API) | リクエスト (`/api/v1`。[api-design.md](api-design.md))。端末の状態 (電池、アプリのバージョン) の報告も含む |
| gRPC | 同じリクエストを gRPC のサービスでも出す (必要になってから) |
| SignalR | 通知 (店舗の出来事) を `seq` の順に送り、端末がつながっているかも接続で見る。再接続したら、欠落分を `GET /events` で再取得する |
| OTLP | テレメトリ (ログ、メトリクス、トレース)。送れない間は端末にためて再送する |

- REST と gRPC は同じ業務の処理を呼び、違いはエンドポイントの形だけにする (例外と結果の分類は `ApiResult` の `ApiStatus` に揃える)
- ポートは template-maui-server に合わせる
  - 8080: REST と SignalR
  - 9090: gRPC (h2c)
  - 4317 / 4318: OTLP
- 端末は接続先 (リクエスト、gRPC、テレメトリ) を、端末の設定 (QR かペアリング) で受ける

## 📡 通信の枠

テーブル端末が使う API ([api-design.md](api-design.md)) を、すべての端末に共通の `IDeviceApi` とテーブル端末の `ITableApi` (`TableOrder.Client`) にまとめた。  
REST の API クライアント (`RestDeviceApi`、`RestTableApi`) と通知の受信 (`SignalROrderEvents`) で、注文サーバにつなぐ (実装は [architecture.md](architecture.md#注文サーバの実装))。  
画面と業務の流れはモックで作り、注文サーバができてからモックは外した ([店舗の設定で動く端末](#-店舗の設定で動く端末))。

| --- | --- |
| `IDeviceApi` の `PairAsync` / `AuthenticateAsync` / `ReportStatusAsync` / `GetConfigAsync` | `POST /devices/pair` / `POST /devices/token` / `POST /devices/me/heartbeat` / `GET /devices/me/config` |
| `GetStoreAsync` / `GetMenuAsync` / `GetStockAsync` | `GET /store` / `GET /menu` / `GET /stock` |
| `GetCurrentVisitAsync` / `ConfirmAsync` | `GET /devices/me/visit` / `POST /visits/{id}/confirmations` |
| `CreateOrderAsync` / `GetOrdersAsync` / `ReleaseAsync` | `POST /visits/{id}/orders` / `GET /visits/{id}/orders` / `POST /visits/{id}/orders/release` |

- 通知 (`IOrderEvents`) で受けるもの: 来店の開始・変更・移動・終了、店舗の変更 (注文の一時停止、ラストオーダー)、品切れ、注文と明細の変化 (上限のルールの数え方)

- 注文履歴・呼び出し・支払の状態は、開いている間に再取得して表示する
- メニューの公開 (`menu.published`。メニューの再読み込み) は、サーバにメニューを公開する API を作るときに端末のレシーバに足す

## 🔑 端末の認証

端末ごとの鍵で署名して、短命のアクセストークン (JWT) を受け取る形に決めた。  
流れは [api-design.md](api-design.md#15-認証認可) に書き、ここには決めるときに調べたことと残っていることを置く。

### 調べたこと

- クラウドの POS やテーブルオーダーが公開している API の認証は、連携する他社のサーバやアプリ向けの OAuth 2.0 / OIDC。  
  自社の端末が持つ資格情報 (形式・期限・保存場所) は公開されていない
- 自社の端末の登録には 2 つの型がある (今の想定のペアリングコードは前者)
  - 管理画面で短いコードを出し、端末で入れる
  - 管理者が端末ごとに 1 回サインインし、従業員は PIN で使う
- 毎回送る短命のアクセストークンは JWT が多い (期限は 25 分から 1 日)。  
  端末が長く持つ資格情報は JWT ではなく、リフレッシュトークンか端末の中の鍵・証明書にしている
- 期限の長い JWT をそのまま送る形は、期限まで取り消せないので避ける。  
  長く使う資格情報に JWT を使うのは、端末の秘密鍵で署名して数分で使い捨てる形 (クライアントの認証の JWT) だけ

### 方式の比較

| 方式 | 良い点 | 弱い点 |
| --- | --- | --- |
| 期限のない端末のトークン (元の想定) | 実装が簡単で、すぐ取り消せる | 盗まれると取り消すまで使える。リクエストごとに照会が要る |
| リフレッシュトークンと短命の JWT | 一般的で、盗用を交換のときに見つけられる | 盗めば使える秘密が端末に残る。交換の行き違いで端末が外れることがある |
| 端末の鍵と短命の JWT (採用) | 秘密を端末から取り出せない (複製できない)。交換の状態を持たず、店舗のエッジでも公開鍵だけで検証できる | 鍵の生成と署名を作り込む |
| 端末の証明書 (mTLS) | 強い | 証明書の発行・更新と、ロードバランサでの扱いが重い |

### 残っていること

- ペアリングの向きを逆にし、端末が出した QR をサインイン済みの管理画面で承認する形も考える (誰でも呼べるエンドポイントで、推測できるコードを受けずに済む)
- サーバは JwtBearer で検証し、トークンは小さな自作のエンドポイント (`POST /devices/token`) で出す
- スタッフは端末の認証と分け、今のとおり PIN で識別する

## 🏢 マルチテナント

複数の会社 (テナント) が契約して使う形にし、テナントと店舗はアクセストークンのクレームで決めることにした。  
端末は 1 つの店舗に、外部のクライアントは 1 つのテナントに属するので、リクエストでテナントを選ぶ値は要らない。  
データベースは 1 つにし、すべての表に `TenantId` を持たせる ([database.md](database.md#テナントの持ち方))。  
ルールは [api-design.md](api-design.md#16-テナント) に書き、ここには決めるときに調べたことと残っていることを置く。

### 調べたこと

- 飲食の POS と注文のクラウドのサービスは、契約・加盟店・店舗の `id` をパスかヘッダで指す型が多い。  
  ただし、使えるテナントと店舗はトークンで限っている。  
  指す値は選ぶためのもので、使えるかはトークンで確認する
- パスやヘッダで指すのは、1 つの資格情報で複数の店舗やテナントを扱う連携 (他社のアプリ、複数の店舗をまとめて管理するグループ) のため。  
  店の端末は 1 つの店舗に属し、ほかの店舗に移すときは再登録する
- クラウドのマルチテナントの設計の指針が求めること
  - テナントは、検証したトークンのクレームから取る。  
    リクエストの中の値 (パス、ヘッダ、本文) から取らない
  - トークンのテナントが、知っているテナントかを確認する
  - データの読み書きをテナントで絞る
  - テナントのコンテキストをすべての層で引けるようにし、開発者がテナントを意識しなくて済む実装にする
- API の脆弱性の一覧の 1 番目は、リクエストの中の `id` でほかの利用者のデータを読めること (オブジェクト単位の認可の漏れ)。  
  推測できない `id` にするだけでは足りない。  
  `id` ごとに、トークンの範囲のものかを確認する
- テナントごとのレート制限 (1 つのテナントの負荷でほかを遅くしない) と、ログとメトリクスへのテナントの付与 (テナントごとに見られるようにする) が一般的

### 方式の比較

| 方式 | 良い点 | 弱い点 |
| --- | --- | --- |
| パスにテナント (`/{テナント}/...`) | どのテナントのリクエストか URL でわかる。テナントごとの振り分けがしやすい | トークンとパスの食い違いを毎回確認する。端末の設定の URL がテナントごとに変わる |
| ヘッダにテナント・店舗 | 1 つの資格情報で複数の店舗を扱える | 食い違いを毎回確認する。付け忘れと取り違えが起きやすい |
| サブドメイン (`{テナント}.example.com`) | Web の画面でテナントがわかり、サインインの振り分けに使える | 証明書と DNS の管理が要る。端末の接続先がテナントごとに変わる |
| トークンのクレーム (採用) | リクエストに選ぶ値がなく、取り違えが起きない。接続先がすべてのテナントで同じ | 1 つの資格情報で複数のテナントを扱えない (テナントごとにクライアントを持つ) |

### 残っていること

- 大きなテナントを別のデータベースに移す手順 (同じスキーマのデータベースに、そのテナントの行を移す)
- テナントの中のまとまり (ブランド、地域) が要るか。  
  要るなら店舗の属性にし、管理画面の絞り込みと外部のクライアントの範囲に使う
- テナントごとのサインイン (組織の ID 基盤とつなぐ) を作るなら、サインインの画面でテナントを選ぶ方法 (サブドメイン、メールのドメイン) を決める

## 🚀 本番の環境

本番は AWS で動かす。  
サーバ (`TableOrder.Server.Web`) はコンテナにして Amazon ECS (AWS Fargate) で動かし、データベースは Amazon RDS にする。  
インフラはコード (IaC) で定義し、IaC のプロジェクトも C# で作る (AWS CDK の C# 版)。  
ここには決めることと直すことを置き、作ったら構成 ([architecture.md](architecture.md)) に移す。

### 構成 (想定)

| 部分 | AWS のサービス | 内容 |
| --- | --- | --- |
| サーバ | Amazon ECS (AWS Fargate)。台数を負荷で増減する | REST、SignalR、管理画面、キッチン端末の配信 |
| ロードバランサ | Application Load Balancer | TLS を終える。WebSocket (SignalR) を通し、管理画面 (Blazor Server) は同じタスクに寄せる |
| データベース | Amazon RDS (エンジンは PostgreSQL が候補。複数の AZ に置く) | 今の SQLite の表を移す ([database.md](database.md)) |
| 共有のキャッシュ | Amazon ElastiCache (Valkey / Redis 互換) | トークンのリクエストの `jti`、レート制限 |
| 秘密の値 | AWS Secrets Manager | データベースの接続、トークンの署名の鍵、Webhook の鍵 |
| テレメトリ | タスクの隣の AWS Distro for OpenTelemetry Collector から Amazon CloudWatch と AWS X-Ray へ | ログ、メトリクス、トレース (テナントと店舗を付ける) |
| 前で絞る | AWS WAF | レート制限、登録の試行の上限 |
| イメージ | Amazon ECR | サーバのコンテナのイメージ |
| IaC | AWS CDK (C#) | ネットワーク、コンテナ、データベース、秘密、監視を、環境 (開発、検証、本番、大きなテナントの専用の環境) ごとに作る |

### コンテナで複数台を動かすために直すこと

- トークンのリクエストのリプレイ防止 (`jti`) を、サーバの中のキャッシュから ElastiCache (かデータベース) に移す
- 失効リスト (無効にした端末、止めたテナント) は、どのタスクもデータベースから数秒ごとに再読み込みする (作った。外部のクライアントを足すときも同じにする)
- レート制限は、タスクごとではなく全体で数える (AWS WAF で絞るか、ElastiCache で数える)
- 通知は、各タスクのディスパッチャがデータベースの通し番号を一定の間隔で見て、自分につながる端末に送る。  
  バックプレーンなしで全台の端末に届き、遅れはポーリングの間隔まで。  
  遅れを縮めるなら、PostgreSQL の `LISTEN` / `NOTIFY` で、店舗の通知が増えたことを全台に通知する
- 管理画面 (Blazor Server) は接続をつなぎ続ける。  
  ALB のスティッキーセッションで同じタスクに寄せ、データ保護の鍵を共有する
- バックグラウンドの処理のうち、Webhook の再送と古いデータの消去は、1 台だけで動かすか、ロックで重ならないようにする (通知のディスパッチャは全台で動かす)
- 起動のたびにスキーマを作る今の形をやめ、デプロイの前にマイグレーションを 1 回だけ流す (ECS の 1 回だけのタスク)
- ALB で TLS を終え、サーバは転送ヘッダ (元の方式と送り元) を受ける。  
  ヘルスチェックの経路を、ALB のターゲットグループと ECS に見せる
- 設定は環境変数と Secrets Manager から受け取り、秘密 (署名の鍵、接続文字列) を設定のファイルに置かない

### データベースを移すために直すこと

- RDS のエンジンは、部分索引、遅延の外部キー、`RETURNING`、行のセキュリティを持つ PostgreSQL を候補にする (Aurora PostgreSQL とも比べる)
- 型を直す
  - guid は uuid
  - datetime はタイムゾーン付きの時刻
  - json は jsonb
  - bool は boolean
- 型の変換 (TypeHandler) とサンプルのデータも合わせる
- SQLite に固有の書き方 (`PRAGMA`、日付の関数、`INSERT OR`) を直す。  
  SQL のテスト (テナントの条件の検証) は、移した先のデータベースでも流す
- テナントの条件を、データベースの行のセキュリティ (RLS) でも適用する (リクエストごとにテナントを接続の変数に入れる)
- 接続の数を限る (接続のプール。台数を増やすときは RDS Proxy を置く)
- RDS の自動バックアップと時点の復元、読み取りの複製 (集計は複製から読む) を決める

### IaC

- プロジェクトは新しい区分 `infra/` に置く案 (`infra/src/TableOrder.Infra`、ソリューションは `infra/TableOrder.Infra.slnx`)。  
  サーバのソリューションに入れないのは、AWS CDK のライブラリが大きく、サーバのビルドと検証を重くしないため
- 環境 (開発、検証、本番) は同じコードから作り、値 (タスクの数、データベースの大きさ、ドメイン) だけを変える
- 大きなテナントの専用の環境 ([api-design.md](api-design.md#16-テナント)) も同じコードで作る (端末の接続先は EMM で配信し直す)
- 開発の構成 (Aspire の AppHost) と、設定のキーと名前 (接続文字列、OTLP の送り先) を揃える。  
  Aspire の AWS の統合で、AppHost から CDK のスタックを扱う方法もある
- CI でデプロイする: コンテナのイメージを作って ECR に置く → CDK の適用 → マイグレーション → ECS のサービスの入れ替え
- IaC のテストは、作る資源の定義を確認する (タスクの数、AZ、暗号化、外に開くポート)

## 🏪 店舗の設定で動く端末

テーブル端末を 1 つのアプリのまま、チェーンと店舗の設定で切り替えられるようにした (実装は [architecture.md](architecture.md))。

- 切り替えるもの: チェーンの名前・ロゴ・色・機能・料理の写真・スタッフの PIN
- 端末は注文サーバにつながる前提にした (モックは外した)。  
  来店はスタッフが管理画面の案内で開く
- 端末の登録と置き場所、チェーンと店舗の設定、案内は、サーバの管理画面で最低限を扱えるようにした
- サンプルの 2 つのテナントは別のチェーン (バニーズとさつき軒) にした。  
  同じアプリのまま、ペアリングコード (`100001` / `200001`) で再登録するだけでチェーンが変わることを、エミュレータで確認した

残り:

- 本部が写真とロゴを置く API (`PUT /images/{name}`) は、外部の連携で作る。  
  写真は端末の画面に合う大きさ (1280x960 ほど) の JPEG か WebP にし、本部が置くときに縮める
- 設定は、チェーンと店舗の初期設定の内容に限っている。  
  文言 (待受やお礼の画面など) と表示の細かな変更 (商品の印、アイコン、待受の画像) を設定で変えるかは、要るときに決める

## 🚪 来店の開き方

来店の開き方を店舗の設定で選べるようにする。  
どの形でも、ホール端末からは来店を開ける (席の決め直しや、困ったときのため)。

| 設定 | 流れ | 来店を開く端末 |
| --- | --- | --- |
| スタッフ (`Hall`。既定) | 入口でスタッフが人数を聞いて席を決め、ホール端末で来店を開く | ホール端末 |
| 受付機 (`Reception`) | お客様が受付機で人数を入れる。サーバが人数の入る空席を決めて来店を開き、受付機が席を案内する | 受付機、ホール端末 |
| 席 (`Table`) | お客様が空いている席に座り、テーブル端末の待受で人数を入れて始める | テーブル端末、ホール端末 |

- 店舗の設定 (`features.visitOpening`) に持ち、管理画面の店舗の設定で選ぶ
- サーバは、設定で許した端末からだけ来店を開く (ほかは `403` `VISIT_OPENING_DISABLED`)
- 受付機はテーブルを送らない。  
  サーバが、人数の入る空席のうち定員の小さいテーブル (同じなら並びの順) を選ぶ。  
  空席がなければ `409` (`NO_VACANT_TABLE`) を返し、受付機は満席を出してスタッフに引き継ぐ
- テーブル端末は、自分のテーブル (トークンで決まる) にだけ来店を開ける
- テーブル端末の待受は設定で変わる (スタッフと受付機は案内を待つ文言、席は人数を入れて始めるボタン)
- 順番待ち (受付機で番号を取り、席が空いたら呼び出す) と、大人数でテーブルをまとめる形は扱わない
- 決めるときに調べたこと: 回転寿司のチェーンは、受付機が席を決める形がふつう。  
  ファミリーレストランはスタッフの案内が基本 (混む店は順番待ちの発券を足し、入口で席を指定する店もある)

## 📟 ホール端末

ホールのスタッフが持つスマートフォン (縦向き) のアプリ (`TableOrder.HallApp`) にする。  
来店の開き方 ([来店の開き方](#-来店の開き方)) のどの形でも、ホール端末からは来店を開ける。  
サーバの API と通知はそろっているので ([api-design.md](api-design.md#43-ホール端末-ihallapi))、端末の側を作る。

### 方針

| 項目 | 決めたこと |
| --- | --- |
| 端末 | Android のスマートフォン、縦向き (確認はスマートフォンのエミュレータ、1080x2400) |
| 画面の組み方 | 下部のタブ (席、呼び出し、提供、品切れ) で切り替え、待っている件数をタブに出す。面とバーはテーブル端末と同じ形 (角丸・影なし、タップ領域は 64dp 以上) |
| 色 | スタッフの道具なので、チェーンの色ではなく System の役割の色で組む |
| 言語 | 端末の言語の設定に従う (日本語と英語) |
| 専用端末 | テーブル端末と同じ仕組み (外部の EMM、自前の Device Owner) を使う |
| 端末の設定 | 店舗のスタッフの PIN で守る (テーブル端末と同じ) |
| 通知 | 新しい呼び出しは音と振動で通知する (画面が消えている間も) |
| 管理画面の案内 | 店内状況に移す。ホール端末が使えないときに、そこで来店を開いて閉じる |
| 代わりの注文の確認のルール | スタッフがお客様に確認し、ホール端末から確認を記録してから注文する (確認の API をホール端末にも開く) |

### 画面

| 画面 | 内容 |
| --- | --- |
| 起動 | テーブル端末と同じ流れ (接続先、登録、トークン、端末の設定、通知の接続、店舗・メニュー・品切れ・席・呼び出し・提供の読み込み)。ホール端末として登録されていなければ進まない |
| 端末の設定 | 接続先とペアリングコード (テーブル端末と同じ) |
| 席 | テーブルの一覧 (空き・来店中・会計中、人数、経過時間、まだ出していない品、呼び出し)。空きを押すと案内、来店中を押すと来店の詳細 |
| 案内 | 人数 (大人、子ども) を入れて来店を開く |
| 来店の詳細 | 人数、開いた時刻、注文と明細の状態を出す。操作は、人数を変える、席を移る、代わりの注文、食後の品のお願い、明細の取消、会計の手伝い (明細、会計の開始と取りやめ)、レジで払った (閉じる)、取りやめ (注文のないとき) |
| 代わりの注文 | カテゴリと品を選び、数量とオプションを入れて注文する (確認と上限のルールを検証する) |
| 呼び出し | 終わっていない呼び出し (テーブル、用件、経過時間)。向かう、対応した |
| 提供 | できあがった明細をテーブルごとに並べ、提供したら外す |
| 品切れ | 品ごとの売り切れと残りの数、すべて戻す、注文の一時停止と再開 |
| 端末 | 端末の情報 (店舗、端末の名前、接続先、電池、アプリのバージョン) と端末の設定 (PIN で開く) |

### 通知

| 通知 | ホール端末の動き |
| --- | --- |
| `visit.opened` / `visit.updated` / `visit.moved` / `visit.closed` | 席の一覧と来店の詳細を更新する |
| `order.created`、`order.lines.updated` | 来店の詳細と提供の一覧を更新する |
| `call.created` / `call.updated` | 呼び出しの一覧を更新する (新しい呼び出しは音と振動) |
| `stock.updated`、`menu.published` | 品切れの一覧と代わりの注文のメニューを更新する |
| `store.updated` | 注文の一時停止を表示する。設定のバージョンが変わったら、タブの画面で起動からやり直す |
| `device.updated` | 起動からやり直す |

### 作るもの

- API クライアント `IHallApi` と、注文サーバの実装 `RestHallApi` (`TableOrder.Client`)。  
  サーバのテストで、本物のサーバにつないで確認する
- 端末に共通の部品 `TableOrder.Terminal` (`terminal/src/`) を作り、テーブル端末から移す ([端末に共通の部品](#端末に共通の部品-tableorderterminal))

### 端末に共通の部品 (`TableOrder.Terminal`)

テーブル端末とホール端末が使う部品を、Android の .NET MAUI のライブラリ (`terminal/src/TableOrder.Terminal`) に移す。  
画面 (`ViewId`) は持たず、各アプリに置く。  
ポップアップは、どの端末でも同じもの (電卓、メッセージ、確認) だけを持つ。

| 区分 | 移すもの | 共有の仕方 |
| --- | --- | --- |
| 端末の部品 | 端末の情報 (`DeviceInformation`)、端末の鍵 (`DeviceKey`)、専用端末 (`KioskManager`)、EMM の設定 (`ManagedConfiguration`)、クラッシュレポート (`CrashReport`) | ライブラリの登録の拡張メソッドで DI に入れる。生成の DI が型を作れるように、アプリの `GeneratedFactory` に型を足す |
| 状態と手順 | 端末の設定 (`Settings`)、端末の状態 (`DeviceState`)、スタッフの PIN (`StaffLock`)、端末の登録 (`DeviceUsecase`)、状態の報告 (`StatusReporter`) | 端末の部品と同じ |
| レシーバの基底クラス | 操作の途中と遷移の間は通知を待たせて順に渡す仕組みと、起動からやり直しを求める通知 (無効化、テナントの停止、端末の変更、EMM の接続先、追いつけない欠落) | 各アプリのレシーバが基底クラスを継承する。通知の扱いと画面への通知は、アプリで決める |
| ポップアップ | 電卓 (`InputNumber`)、メッセージ (`Message`)、確認 (`Confirm`) と、その入口 (PIN の確認を含む) | ID はライブラリの列挙型に持ち、アプリのポップアップの登録に足す (登録と呼び出しは ID の型を問わない) |
| 画面の基盤 | ポップアップの ViewModel の基底クラス、ポップアップと遷移のプラグイン (全画面、外から閉じる、手触り、リークの検出)、添付プロパティ (`Behaviors`)、アイコンの描画 | アプリの `MauiProgram` から使う。フォントのファイルとグリフの表 (`MaterialIcons`。生成したファイル) は、アイコンを使う画面を持つ各アプリに置く |
| 色とスタイル | System の役割の色と、システムの画面 (起動、端末の設定、スタッフメニュー)・ダイアログ・電卓・基本のスタイル | ライブラリの辞書をアプリの `App.xaml` に入れる。Brand・Neutral・Status の役割の色の値は各アプリが持ち、ライブラリのスタイルは役割の名前で引く |
| 文言 | 移したものが使う文言 (ダイアログのボタン、PIN の確認、通信の失敗など) | ライブラリの resx (日本語と英語) に置き、アプリの resx から外す |

- テーブル端末に残すもの: 画面 (起動、端末の設定、スタッフメニューを含む)、チェーンの色 (`ThemeManager`)、料理の写真 (`ImageCache`)、メニュー・来店・カート・言語・店舗の状態、注文の手順 (`OrderUsecase`)、言語のポップアップ、QR コードの表示
- 起動・端末の設定・スタッフメニューの画面は、各アプリに置く。  
  向き (タブレットの横向き、スマートフォンの縦向き) と、起動で読むものが違うため。  
  登録や設定の手順は共通の部品を呼ぶ
- Device Owner のレシーバと管理対象の構成の定義は、各アプリに置く (Android の名前と EMM の管理画面の説明が、アプリごとに違うため)
- テーブル端末とホール端末のソリューションに入れて検証する。  
  Android だけを対象にするライブラリなので、単独のテストは持たない。  
  動きは各アプリのエミュレータで確認する

### 基盤

起動から下部のタブまでの枠と、ホール端末の状態とレシーバを作る。  
タブの中身 (席の一覧、呼び出し、提供、品切れ) は次の段階から作り、それまでは作っていないことを表示する。

| 項目 | 決めたこと |
| --- | --- |
| 画面 | 起動 (`Startup`)、端末の設定 (`Setup`)、端末 (`Device`)、下部のタブの画面 (席 `Seats`、呼び出し `Calls`、提供 `Serving`、品切れ `Stock`) |
| 下部のタブ | タブごとに画面を分け、タブを押すと画面を切り替える。ヘッダとタブバーは部品 (`Controls/`) にして各画面に置く |
| タブの件数 | 呼び出しのタブにはまだ誰も向かっていない呼び出しの数、提供のタブにはできあがった明細の数を出す |
| ヘッダ | タブの名前、店舗の名前、端末の画面への入口。注文を一時停止している間は、ヘッダの下にメッセージのバーを出す |
| 端末の画面 | 端末の情報 (店舗、端末の名前、端末の id、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリのバージョン) を出す。端末の設定と専用端末の一時的な解除は、スタッフの PIN を確認してから行う |
| 戻る | タブの画面は席のタブに、端末の画面は開いたタブに戻る。席のタブでは何もしない (アプリの外へ出さない) |
| 起動 | テーブル端末と同じ流れ (接続先、登録、トークン、端末の設定、通知の接続) のあと、店舗、メニューと品切れ、席・呼び出し・提供の一覧を読んで席のタブに進む。ホール端末として登録されていなければ進まない |
| 状態 | 店舗 (`StoreState`。端末の設定で受けた店舗の設定と、店舗の今の状態)、メニュー (`MenuState`。メニューと品切れ)、席 (`TableState`)、呼び出し (`CallState`)、提供 (`ServingState`) |
| レシーバ | 店舗と品切れは、通知の中身で更新する。席・呼び出し・提供は、変わる通知を受けたら一覧を再取得する |
| 色 | ホール端末の色 (`Colors.xaml`) は、Brand・Neutral・Status の役割に System の色に揃えた値を持つ。チェーンの色には変えない (`ThemeManager` を持たない) |
| 言語 | 文言とサーバの文字 (店舗の名前など) を、端末の言語 (日本語、英語) で選ぶ |
| 専用端末 | テーブル端末と同じ。アプリの画面 (`MainActivity`) をロックタスクとホームの候補にし、Device Owner のレシーバと管理対象の構成の定義を置く |

- 起動と端末の設定の戻るは、テーブル端末と同じ
- レシーバの再取得と画面への通知
  - まとめて届いた通知は、扱い終えたあとに 1 回だけ再取得する
  - 再取得できなかった一覧は、次の通知のあとに再取得する
  - 状態を更新したら、表示中の画面に通知する

共通の部品と API クライアントは、次のように直す。

- 登録で検証する端末の種類は、アプリが `AddTerminalComponents` に渡す (テーブル端末は `Table`、ホール端末は `Hall`)
- レシーバの基底クラスに、待っていた通知を扱い終えたときに呼ぶメソッドを足す (ホール端末は一覧の再取得に使う)
- 共通のポップアップと、起動・端末の設定の列の幅は、画面に収まらないときに左右に余白を残して縮める (タブレットの見た目は変えない)
- 呼び出しの通知 (`call.created` / `call.updated`) を、API クライアントで受ける形にする (`CallCreatedEvent` / `CallUpdatedEvent`)
- メニューの公開の通知 (`menu.published`) は、テーブル端末と同じく、メニューを公開する API を作るときに受ける

### 席と来店

席のタブの中身と、来店を開く・直す・終える操作を作る。  
代わりの注文、食後の品のお願い、明細の取消、会計の手伝いは、7 段目で来店の詳細に足す。

| 項目 | 決めたこと |
| --- | --- |
| 席のタブ | テーブルを店舗の並びの順に、2 列のタイルで並べる |
| 案内 | 空きのタイルを押すと人数 (大人、子ども) のポップアップを開き、来店を開く。定員を添えるが、超えても止めない |
| 来店の詳細 | 来店中・会計中のタイルを押すと開く画面 (`Visit`)。状態、人数、開いた時刻と経過時間、注文の合計、注文と明細の状態を出す |
| 来店の操作 | 来店の詳細の下部のバーに、人数変更、席移動 (会計中は押せない)、来店を終える操作を置く |
| 席を移る | 空いている席の一覧のポップアップから選ぶ (確認せずに移す。戻すときは移し直す)。空いている席がなければメッセージを出す |
| 来店を終える | 確認してから閉じ、席のタブに戻る |
| 表示の更新 | 来店の詳細は、席の一覧を再取得したとき (`TablesChanged`) に来店と注文を再取得する。来店が終わっていたら席のタブに戻る |
| 失敗 | ほかで変更されていた (`VERSION_MISMATCH`)、席が埋まっていた (`TABLE_OCCUPIED`)、会計中 (`CHECKOUT_IN_PROGRESS`) などは、メッセージを出して再取得する |
| 時刻 | 店舗のタイムゾーンで出す (端末のタイムゾーンの設定によらない) |

- 席のタブのタイル
  - 名前と状態 (空き・来店中・会計中) を出す。  
    状態は左端のバーの色でも示す
  - 来店中は、人数・経過時間・まだ出していない品の数・終わっていない呼び出しの数を出す
  - 空きは定員を出す
  - 経過時間は 30 秒ごとに更新する
- 案内を送れたかわからない (通信できない) ときは、同じテーブルの次の案内で同じ来店の id を再送する
- 来店の詳細の注文と明細の状態は、何回目の注文かと、明細ごとの調理と提供の段階
- 来店を終える操作は、注文のある来店と会計中は「レジで払った」、注文のない来店は「取りやめ」にする。  
  どちらかしか通らないので、1 つのボタンを切り替える

### 呼び出しと提供

呼び出しのタブと提供のタブの中身を作る。  
新しい呼び出しは、どの画面にいても音と振動で通知する。

- 呼び出しのタブ
  - 終わっていない呼び出し (呼ばれている、向かっている) を、古い順にカードで並べる
  - カードにテーブル、用件 (店舗の設定の名前)、呼ばれてからの時間を出す。  
    時間は 30 秒ごとに更新する
  - 左端のバーの色で状態を示す (呼ばれている間は目立つ色)
- 呼び出しの操作
  - 呼ばれている呼び出しは「向かう」と「対応した」、向かっている呼び出しは「対応した」だけを出す (向かわずに対応してもよい)
  - 確認せずに送る
  - ほかの端末が先に進めていても失敗にしない (サーバが今の状態を返す)
- 呼び出しの通知
  - 新しい呼び出し (`call.created`) を受けたら、どの画面でも端末の通知の音と振動で通知する (ポップアップを開いている間も待たない)
  - 続けて届いたときは、間を空けて 1 回にまとめる
  - 音量は端末の設定に従う
- 提供のタブ
  - できあがった明細を、テーブルごとにできあがりの古い順に並べる
  - 明細に名前、オプション、数量、できあがってからの時間を出す
- 提供の操作
  - 明細ごとの「提供した」と、テーブルの「すべて提供した」(明細が 2 つ以上のとき) を置く
  - 確認せずに送り、提供した明細は一覧から外す
- 表示の更新
  - 操作のあとと、通知を受けたとき (`CallsChanged`、`ServingChanged`) に一覧を更新する
  - 残る項目は作り直さずに中身を変え、スクロールの位置を保つ
- 失敗: 来店が終わっていた (`VISIT_NOT_OPEN`)、取消か食後まで止めている明細 (`LINE_STATUS_INVALID`) などは、メッセージを出して再取得する
- 開発の環境: サーバの自動の進行 (`Simulation`) は、提供と呼び出しも進める。  
  ホール端末で確認するときは、提供と向かうまでの秒を長くして起動する

### 画面が消えている間の通知

ホール端末は、スタッフがポケットに入れて持ち歩く。  
画面が消えている間も、新しい呼び出しを音と振動で通知する。  
画面が消えると Activity が止まり、しばらくすると Doze で通信と CPU が止まる。  
そのため、フォアグラウンドサービスでアプリを動かし続ける。

- フォアグラウンドサービス
  - 画面がフォアグラウンドになったときに始め (動いていれば何もしない)、アプリが動いている間は止めない
  - フォアグラウンドサービスを動かすアプリは、Doze でも通信でき、通知の接続を保てる
- サービスの種類: `specialUse` (店のサーバとの通知の接続を保ち、スタッフの呼び出しを通知する)。  
  ほかの種類は用途が合わない (`dataSync` は 1 日 6 時間まで、`remoteMessaging` は端末の間の文章の受け渡し)
- CPU
  - フォアグラウンドサービスの間は部分ウェイクロックを持ち、画面が消えても CPU を止めない
  - CPU が止まると、通知の接続の生存確認が遅れて切れ、届いた呼び出しの音も遅れる
  - 電池を使うので、充電はシフトの間にする前提にする
- フォアグラウンドサービスの通知
  - 音のない通知チャネルに、呼び出しを通知していることを出す。  
    押すとアプリの画面に戻る
  - 通知の許可 (Android 13 以降) は求めない。  
    許可がなくてもフォアグラウンドサービスは動き、端末の動いているアプリの一覧に出る
- 振動: 振動に通知の用途を付ける (端末の通知の振動の設定に従う)。  
  用途のない振動は、バックグラウンドにいる間は捨てられることがある
- 音: 今のとおり、端末の通知の音を通知の音量で鳴らす
- OS のプッシュ: OS のプッシュの仕組みでも届けられる。  
  このシステムの外のサービスを通るので、今は作らない ([backlog.md](backlog.md))
- 確認の方法: エミュレータで画面を消して Doze に入れ (`dumpsys deviceidle force-idle`)、テーブル端末から呼ぶ。  
  振動の記録 (`dumpsys vibrator_manager`) と音を確認する

### 品切れ

品切れのタブの中身 (品切れと残りの数、すべて戻す、注文の一時停止と再開) を作る。

- 品切れのタブ
  - 上にカテゴリのバーを置き、選んだカテゴリの品を並べる
  - カテゴリの並びは、先頭に「品切れ・残り」、続けてメニューのカテゴリ、最後に「オプション」
  - 開いたときは「品切れ・残り」(品切れと残りの数のある品だけ) を出す
  - 品には名前と状態 (品切れ、残りの数) を出す。  
    オプションにはグループの名前を添える
  - 横にスクロールするカテゴリのバーは、続きがある向きの端に送りのボタンを重ねる (テーブル端末と同じ)
- 品切れの操作
  - 品を押すと、状態を選ぶポップアップ (売れる、残りの数を決める、品切れ) を開く
  - 残りの数は電卓で入れる (0 は品切れになる)
  - 今と同じ状態を選んだら送らない
- すべて戻す: 確認してから、すべての品を売れるように戻す。  
  品切れと残りの数のある品がないときは押せない
- 注文の一時停止
  - 下部のバーに「注文を止める」(確認してから) と「注文を再開する」の、状態に合うどちらかだけを出す
  - テーブル端末に出す文言は送らず、テーブル端末の既定の文言にする
- 表示の更新: 操作のあとと、品切れと店舗の通知を受けたとき (`StockChanged`、`StoreChanged`) に更新する

### 代わりの注文

来店の詳細に、代わりの注文、食後の品のお願い、明細の取消、会計の手伝いを足す。

- 来店の詳細の操作
  - 注文の見出しの右に「注文を入れる」を置く
  - 食後に出す品があるときは、注文の下に「食後の品をお願いする」を置く
  - 明細を押すと取消を開く
  - 下部のバーは、人数を変える・席を移る・会計を 1 行に並べる
  - 会計中は、注文を入れる・食後の品のお願い・取消を押せない
- 代わりの注文の画面 (`Order`。来店の詳細から開く)
  - 上にカテゴリのバー (先頭はカート、続けてメニューのカテゴリ)、品の一覧 (名前、価格、品切れと残りの数)、下に「注文する」(点数と合計) を置く
  - カートの品を押すと、確認してから外す
  - 戻るとき、カートに品があれば、捨ててよいか確認してから来店の詳細に戻る
  - 席の一覧の通知で来店を再取得する。  
    終わっていたら席のタブ、会計中なら来店の詳細に戻る
  - 品切れの通知で品の状態を更新する
- 品の詳細: 品を押すとポップアップで、オプション、出す時機 (選べる品だけ)、数量を選んでカートに入れる
  - 必須の組は、選ぶまで入れられない
  - 品切れのオプションは選べない
- 確認のルール: 確認の品を入れる前に、ルールの文言でお客様に確認したかをスタッフに聞く。  
  確認したら来店に記録する (来店で 1 回のルールは、記録したら聞かない)
- 上限のルール: 来店の注文 (取消を除く) とカートを合わせて上限を超える品は入れない
- 注文を送る
  - 確認してから送り、送れたら来店の詳細に戻る
  - 送れたかわからない (通信できない) ときは、同じ注文の id で再送する
  - 断られたら、理由 (品切れ、残りの数、上限、一時停止、ラストオーダーなど) を表示する
- 明細の取消: 提供済みと取消を除く明細を押すと、取り消す数量 (数量が 2 以上のとき) を選ぶポップアップを開いて送る (理由は送らない)
- 食後の品のお願い: 食後に出す品 (止めている明細) を、確認してからすべてお願いする
- 会計の手伝い
  - 「会計」で明細のポップアップを開く (品、数量、金額、税、合計、払った額、残り、まだ出していない品の注意)
  - 会計を始める (会計中でないとき) と会計を取りやめる (会計中のとき) の、状態に合うどちらかだけを出す

### 並べた確認

テーブル端末 (タブレット、テーブル 1) とホール端末 (スマートフォン) を同じサーバにつなぎ、案内から会計までを両方の画面で確認する。  
ホール端末の操作がテーブル端末に届くこと (と、その逆) を見る。

| 場面 | 操作 | 確認すること |
| --- | --- | --- |
| 案内 | ホール端末で空きの席に案内する | テーブル端末が待受から注文の画面になり、人数を出す。ホール端末の席が来店中になる |
| 注文 | テーブル端末で注文する | ホール端末の席にまだ出していない品の数、来店の詳細に注文が出る。できあがった品は提供の一覧に出る |
| 呼び出し | テーブル端末で店員を呼ぶ | ホール端末が音と振動で通知する。向かうでテーブル端末に向かっていることを出し、対応したで消える |
| 提供 | ホール端末で提供したを送る | テーブル端末の注文履歴が提供済みになる |
| 人数 | ホール端末で人数を変える | テーブル端末のヘッダの人数が変わる |
| 代わりの注文 | ホール端末で注文を入れる (お酒の確認を含む) | テーブル端末の注文履歴に出て、上限のルールに数える。ホール端末で記録した確認は、テーブル端末で聞き直さない |
| 明細の取消 | ホール端末で明細を取り消す | テーブル端末の注文履歴が取消になる |
| 食後の品 | テーブル端末で食後の品を頼み、ホール端末でお願いする | ホール端末の来店の詳細に、食後の品とお願いのボタンが出る。お願いしたら、テーブル端末の注文履歴で調理に進む |
| 品切れ | ホール端末で品切れにし、注文を止める | テーブル端末のカードが売り切れになる。注文の画面に一時停止のメッセージを出し、確定を止める |
| 席の移動 | ホール端末で席を移し、戻す | 移すとテーブル端末は待受に戻り、戻すと注文の画面になる |
| 会計の手伝い | ホール端末で会計を始め、取りやめる | テーブル端末の注文の画面に会計中のメッセージを出して確定を止め、取りやめたら消す |
| テーブルでの会計 | テーブル端末で払う | ホール端末の席が会計中になり、払い終えたら空きになる。テーブル端末はお礼から待受に戻る |
| レジで払った | ホール端末でレジで払ったを送る | テーブル端末が待受に戻る |

ホール端末で会計を始めたときのテーブル端末の動きは決めていなかったので、決めた。  
確認で見つけた食い違い (確認の記録) も直す。

- 会計中のテーブル端末
  - ほかの端末 (ホール端末) で会計を始めたら、テーブル端末の注文の画面に会計中のメッセージを出し、注文の確定を止める (会計の明細が変わらないように)
  - お会計の画面には進めて、テーブルで払える
  - 会計をやめたらメッセージを消す
- 確認の記録の通知
  - 食い違い: ホール端末で記録した確認 (お酒の年齢) を、テーブル端末が同じ来店でもう一度聞いていた
  - サーバは、確認を新しく記録したら来店の変更 (`visit.updated`) を通知する。  
    テーブル端末は、答えた確認を更新する (答え直しは通知しない)
- 開発のサーバの自動の進行は、向かうまでと提供までの秒を長くして動かす (呼び出しと提供をホール端末で操作できるように)
- 見つけた食い違いは、決めたことをこの節に書いてから直す

## 🙋 受付機

来店の開き方を受付機にした店の入口に置く、縦置きのタブレットのアプリ (`TableOrder.ReceptionApp`) にする。  
お客様が人数を入れると、サーバが人数の入る空席を決めて来店を開く。  
受付機は席を案内する ([来店の開き方](#-来店の開き方))。  
サーバの API と通知はそろっているので ([api-design.md](api-design.md#45-受付機-ireceptionapi))、端末の側を作る。

### 方針

| 項目 | 決めたこと |
| --- | --- |
| 端末 | Android のタブレットを縦に置く (確認は縦置きのタブレットのエミュレータ、1200x1920) |
| 使う店 | 来店の開き方が受付機の店。ほかの店では、待受に受付を止めている文言を出して受け付けない |
| 画面の組み方 | 入口に立ったお客様が触る、受付機に固有の縦置きの画面にする (テーブル端末の画面を流用しない。[縦置きの画面](#縦置きの画面))。タップ領域は大きくする (主な操作は 80dp 以上) |
| 画面の流れ | 待受から人数の画面に進み、席を決めて案内の画面を出し、待受に戻る。入力の途中で離れたら待受に戻す |
| 色と言語 | お客様向けなので、テーブル端末と同じくチェーンの名前・ロゴ・色を出す。言語は店舗の言語から選べるようにする |
| 専用端末 | テーブル端末と同じ仕組み (外部の EMM、自前の Device Owner)。スタッフメニューは、チェーンの印の長押しと PIN で開く |
| 席の決め方 | 受付機はテーブルを送らず、サーバが人数の入る空席のうち定員の小さいテーブルを選ぶ。人数の入る空席がなければ満席を出し、スタッフに引き継ぐ |
| 受付を止める時刻 | ラストオーダーの時刻を過ぎたら受け付けない (来店を開いても注文できないため。受付機だけで止め、サーバは止めない) |
| 注文の一時停止 | 受け付ける。待受と案内の画面に、テーブル端末と同じ一時停止の文言を出し、席で注文を待つことを先に伝える |
| 扱わないもの | 順番待ち (番号を取って呼び出す)、大人数でテーブルをまとめる案内、満席をホール端末に通知すること |

- 注文の一時停止の間も受け付けるのは、一時停止が厨房の追いつかない間の短い状態で、席は足りているため。  
  入口でお客様を止めない

### 画面

| 画面 | 内容 |
| --- | --- |
| 起動 | テーブル端末と同じ流れ (接続先、登録、トークン、端末の設定、店舗、チェーンのロゴ、空席、通知の接続)。受付機として登録されていなければ進まない |
| 端末の設定 | 接続先とペアリングコード (テーブル端末と同じ) |
| スタッフメニュー | 端末の情報 (店舗、端末の名前、端末の id、接続先、専用端末、EMM の設定、電池、ネットワーク、アプリのバージョン)、端末の設定、専用端末の一時的な解除。縦置きに合わせて、情報と操作を 1 列に並べる |
| 待受 | チェーンの名前とロゴ、店舗の名前、言語、いらっしゃいませ、受付の流れ、空席の状態、「受付する」 |
| 人数 | 大人と子ども (小学生以下) を増減のボタンで入れ (合わせて 1 人以上)、合計の人数を出す。「席を決める」で来店を開く |
| 案内 | 決まったテーブルを大きく出し、人数と「お席へお進みください」を添える |

- 起動で読む端末の設定: チェーンの色、スタッフの PIN、言語
- 待受
  - 空席がひとつもないときは、満席を出す
  - 受付を止めているとき (来店の開き方が受付機でない店、ラストオーダーの後) は、その状態を出す
  - 満席と受付を止めているときは、「受付する」と受付の流れを出さない
  - 注文を一時停止している間は、空席の状態に一時停止の文言を添える
- 人数: 戻るか、しばらく触らなければ待受に戻る (戻るまでの時間を添える)
- 案内
  - 注文を一時停止している間は、一時停止の文言も添える
  - 人数の入る空席がなかったときは、満席とスタッフが案内することを出す
  - 閉じるか、しばらくたつと待受に戻る (残りの秒を出す)

### 縦置きの画面

入口に縦に置いたタブレット (1200x1920。およそ 873x1396dp) を、立ったお客様が使う。  
テーブル端末の画面 (横置き。補助色の地に左寄せの文字) は流用せず、受付機に固有の組み方にする。

| 部分 | 決めたこと |
| --- | --- |
| 上部のバー | 補助色のバーを画面の幅に通し、チェーンの印 (長押しでスタッフメニュー)、チェーンの名前、店舗の名前を出す。待受だけ、右に言語のボタンを置く |
| 段階のバー | 人数と案内の画面は、上部のバーの下に受付の段階 (1 人数、2 ご案内) を並べる。今の段階を主色の面にする |
| 本文 | 地の色の上に、中央にそろえた大きな文字と面 (パネル) を置く |
| 操作 | 主な操作は画面の幅いっぱいのボタンにして下に置き (高さ 128dp)、戻るはその下に置く (高さ 88dp) |
| 待受 | いらっしゃいませ、受付の文言、受付の流れ、空席の状態、受付する |
| 人数 | 大人と子どもの面に大きな増減のボタン (高さ 128dp) を並べ、合計の人数と、触らずに待受に戻るまでの時間を添える |
| 案内 | 決まったテーブルを主色の札にして、離れても読める大きさで出す。待受に戻るまでの残りの秒を、減っていくバーと文字で出す |
| システムの画面 | 起動と端末の設定は、テーブル端末と同じ列の組み方にする (縦置きでも収まる)。スタッフメニューは情報と操作を 1 列に並べる |

- 待受の受付の流れ: 人数を入れる、席が決まる、お席へ (アイコンつきの 3 つの面)
- 待受の空席の状態: すぐに案内できる / 満席 / 受付を止めている / 本日の受付の終了。  
  アイコンと状態の色で示す。  
  注文の一時停止は、同じ面に注意の色で添える
- 案内の満席は、アイコンと文言で出す

### 通知

| 通知 | 受付機の動き |
| --- | --- |
| `visit.opened` / `visit.moved` / `visit.closed` | 空席を再取得し、待受の満席の文言を切り替える |
| `store.updated` | 設定のバージョンが変わったら (来店の開き方を含む)、待受で起動からやり直す。ラストオーダーの時刻を更新する |
| `device.updated` | 起動からやり直す |

### 作るもの

- API クライアント `IReceptionApi` と、注文サーバの実装 `RestReceptionApi` (`TableOrder.Client`)。  
  サーバのテストで、本物のサーバにつないで確認する
- テーブル端末と受付機に共通のお客様向けの部品を、テーブル端末から `TableOrder.Terminal` に移す (テーブル端末の動きは変えない)
  - チェーンの色 `ThemeManager`
  - 画像の保存 `ImageCache`
  - チェーンの印 `BrandMark`
  - 言語 `LanguageState`
- 受付機のアプリを `TableOrder.Terminal` に載せ、Device Owner のレシーバと管理対象の構成の定義を足す

### 受付の流れ

| 項目 | 決めたこと |
| --- | --- |
| 来店を開く | 人数を送って来店を開く (`POST /visits`。テーブルは送らない) |
| 送れたかわからないとき (通信できない) | 同じお客様が同じ人数でもう一度送るときに、同じ来店の id で再送する。返った来店が開いていなければ、新しく開く |
| 満席 | 人数の入る空席がない (`409` `NO_VACANT_TABLE`) ときは、案内の画面に満席を出す |
| 受付を止めた | 来店の開き方が変わっていた (`403` `VISIT_OPENING_DISABLED`) ときは、メッセージを出してから起動からやり直す |
| 待受に戻る時間 | 人数の画面は触らずに 60 秒 (失敗のメッセージを開いたままでも閉じて戻す)、案内の画面は 15 秒 |
| 言語を戻す | 案内を閉じたときと、人数の画面で触らずに待受に戻ったときは、店舗の初めの言語に戻す |
| 空席の状態 | 空席の一覧 (`GET /tables?status=Vacant`) を起動のときと来店の通知で読み、ひとつもなければ待受を満席にする |

- 再送に使う来店の id は、人数の画面に入るときに捨てる
- 言語を戻すのは、次のお客様が初めの言語から始められるようにするため。  
  人数の画面の戻るでは、同じお客様が入れ直すので戻さない
- 人数が定員に入るかは、席を決めるときにサーバが確認する

### 並べた確認

受付機 (縦置きのタブレット) とテーブル端末 (横置きのタブレット。テーブル 1) とホール端末 (スマートフォン) を同じサーバにつなぎ、受付から会計までを確認する。

| 場面 | 操作 | 確認すること |
| --- | --- | --- |
| 受付 | 受付機で人数を入れて席を決める | 受付機が、人数の入る空席のうち定員の小さいテーブル (テーブル 1) を案内する。ホール端末の席は来店中になって人数を出し、テーブル端末は待受から注文の画面になる |
| 注文 | テーブル端末で注文する | ホール端末の来店の詳細に、受付機で入れた人数と注文が出る |
| 満席 | 受付機で入る空席のない人数を入れる。ほかの席をすべて埋めてから戻す | 案内の画面に満席を出す。席が埋まると待受が満席の文言になって受付するを消し、空くと戻る |
| レジで払った | ホール端末でレジで払ったを送る | テーブル端末が待受に戻り、ホール端末の席が空きになる |

### 進め方

| 段階 | 中身 |
| --- | --- |
| 1. 準備 | 決めたことを文書 (業務、API、構成) と規則に入れる。`IReceptionApi` と `RestReceptionApi` を作る |
| 2. 共通の部品 | お客様向けの部品を、テーブル端末から `TableOrder.Terminal` に移す (テーブル端末の動きは変えず、エミュレータで確認し直す) |
| 3. 基盤 | 起動、端末の設定と登録、スタッフメニュー、専用端末と EMM、レシーバ、チェーンの色と言語 |
| 4. 受付 | 待受、人数、案内、満席、受付を止めているとき |
| 5. 確認 | 受付機・テーブル端末 (タブレット) とホール端末 (スマートフォン) を並べ、受付から注文までを確認する。README に受付機の画面を載せる |

- 段階ごとに文書を先に直してから作る。  
  検証 (`verify.py`) とエミュレータで確認する
- 受付機で確認するときは、管理画面の店舗の設定で来店の開き方を受付機にし、終わったら戻す。  
  受付機は縦置き、テーブル端末は横置きのタブレットのエミュレータで見る

## 🍳 キッチン端末

厨房・デザート・ドリンクの持ち場に置くタブレット (横向き) のブラウザで開く、Web アプリ (`TableOrder.KitchenApp`。Blazor WebAssembly) にする。  
注文の明細を持ち場ごとに分けたチケットを出す。  
作り始め・できあがり・下げるを送り、品切れを設定する。  
サーバの API と通知はそろっているので ([api-design.md](api-design.md#44-キッチン端末-ikitchenapi))、端末の側を作る (Web アプリにする理由と置き方は [キッチン端末](#キッチン端末))。

### 方針

| 項目 | 決めたこと |
| --- | --- |
| 端末 | Android のタブレット (横向き) の、EMM のキオスクのブラウザで `/kitchen` を開く |
| 確認の環境 | アプリの中のブラウザ (タブレットの横向きの大きさ) と、テーブル端末と同じタブレットのエミュレータのブラウザ |
| 画面の組み方 | スタッフが使う画面にする。上に持ち場のタブ、チケットを古い順に並べ、下部のバーに下げたチケット・品切れ・端末への入口を置く |
| タップ領域 | 大きくする (離れて見る、手がふさがっている) |
| 色 | スタッフ向けなので、ホール端末と同じく System の色にそろえ、チェーンの色に変えない |
| 言語 | 文言はブラウザの言語で選ぶ (英語のブラウザは英語、ほかは日本語)。料理の名前はサーバが日本語で返す |
| 明細の操作 | 明細を押すと作り始め、もう一度押すとできあがりにする |
| 下げる | チケットの「下げる」で、残りの明細をできあがりにして下げる。下げたチケットは一覧から戻せる (押し間違い) |
| 持ち場 | 受け持つ持ち場が 2 つ以上なら、上に「すべて」と持ち場ごとのタブを置き、まだ作り始めていないチケットの数を添える。1 つならタブを出さない |
| 遅れ | チケットができてからの時間を出し、店舗の設定の時間 (`kitchenAlertMinutes`。既定は 15 分、`0` は色を変えない) を過ぎたら注意の色にする |
| 品切れ | ホール端末と同じ操作 (品切れ、残りの数、売れる) の画面を置く。すべて戻すと注文の一時停止は、ホール端末だけにする |
| 通知 | 新しいチケットを音で通知する。ブラウザが音を出せるように、起動の後に 1 回触れてもらう (キオスクのブラウザで自動再生を許していれば要らない) |
| 鍵 | ブラウザの WebCrypto で取り出せない P-256 の鍵を作り、IndexedDB に持つ (HTTPS か localhost でしか使えない)。署名が非同期になるので、`IDeviceKey` の公開鍵と署名を非同期にする |
| 画面を消さない | 画面の Wake Lock を、画面がフォアグラウンドになるたびに再取得する |
| 全画面 | キオスクのブラウザに任せる。キオスクのブラウザでない (URL バーが出る) ときは、画面に触れたときに全画面にする (外れたら次に触れたときに戻す) |
| 操作の入力 | 触って操作する |
| 扱わないもの | 伝票のプリンタ、バンプバー (物理キーボードを前提にしないため)、まとめ表示 (同じ品の数を合わせて出す)、調理の順番の指示 |

### 画面

| 画面 | 内容 |
| --- | --- |
| 起動 | 接続先 (アプリを配信したサーバ)、登録、トークン、端末の設定、店舗、メニュー (持ち場と品切れにする品)、品切れ、チケット、通知の接続。キッチン端末として登録されていなければ進まない |
| 端末の設定 | ペアリングコードで登録する (接続先はアプリを配信したサーバなので入れない) |
| チケット | 持ち場のタブと、チケットを古い順に左から並べる。入らなければ横にスクロールする |
| 下げたチケット | 直近に下げたチケットを新しい順に出し、戻すを置く |
| 品切れ | カテゴリのバーと品の一覧 (名前、品切れと残りの数)。品を押すと状態を選ぶ |
| 端末 | 端末の情報 (店舗、端末の名前、受け持つ持ち場、端末の id、接続先、アプリのバージョン)、再登録 (確認してから) |

- 起動に失敗したら、30 秒ごと (テナントの停止は 5 分ごと) にリトライする
- チケットの中身: テーブル、何回目の注文、経過時間、明細 (名前、オプション、数量、状態)、下げる
- 取り消した明細は、取消とわかるように残す

### 通知

| 通知 | キッチン端末の動き |
| --- | --- |
| `ticket.created` | チケットを足し、音で通知する |
| `ticket.updated` | チケットを更新する (明細の状態、取消、下げた、戻した) |
| `stock.updated` | 品切れの表示を更新する |
| `store.updated` | 店舗の今の状態を更新する。設定のバージョンが変わったら起動からやり直す (遅れの時間) |
| `device.updated` | 起動からやり直す (受け持つ持ち場の割り当て) |

### 作るもの

- API クライアント (`TableOrder.Client`)
  - `IDeviceKey` の公開鍵と署名を非同期にする (テーブル端末・ホール端末・受付機は形を合わせる)
  - キッチン端末の API クライアント `IKitchenApi` と、注文サーバの実装 `RestKitchenApi` を足す
  - チケットの通知 (`TicketCreatedEvent`、`TicketUpdatedEvent`) を足す
  - サーバのテストで、本物のサーバにつないで確認する
- 店舗の設定: 遅れの時間 (`kitchenAlertMinutes`) を機能の有無に足し、管理画面の店舗の設定で変更できるようにする (店舗の機能の JSON に足すので、表は変えない)
- キッチン端末
  - `TableOrder.Client` を載せる
  - ブラウザに、鍵 (WebCrypto と IndexedDB を使う JavaScript の部品) と端末の設定 (登録した接続先と端末の id) を持つ
  - System の色の役割は、CSS の変数にする (ホール端末の値にそろえる)

### 並べた確認

キッチン端末 (タブレットのエミュレータのブラウザ) とテーブル端末 (同じタブレットで切り替える。テーブル 1)・ホール端末 (スマートフォン) を同じサーバにつなぎ、注文から調理と提供までを確認する。

| 場面 | 操作 | 確認すること |
| --- | --- | --- |
| 注文 | テーブル端末で注文する (食後の品を含む) | キッチン端末に持ち場ごとのチケットが出て、持ち場のタブにまだ作り始めていないチケットの数が出る。食後の品はまだ出ない |
| 作り始めとできあがり | キッチン端末で明細を押す | 明細が作っている・できあがりになり、できあがった品がホール端末の提供の一覧に出る |
| 下げる | キッチン端末でチケットを下げる | 残りの明細ができあがりになり、チケットが一覧から下げたチケットに移る |
| 提供 | ホール端末で提供したを送る | キッチン端末の明細が提供済みになり、テーブル端末の注文履歴がお届け済みになる |
| 食後の品 | テーブル端末で食後の品をお願いする | デザートの持ち場にチケットが出る |
| 品切れ | キッチン端末で品切れにする | テーブル端末のカードが売り切れになる |
| 遅れ | 店舗の設定の遅れの時間を短くして待つ | 時間を過ぎたチケットの見出しが注意の色になる |
| 再読み込み | キッチン端末で途中の画面 (品切れ、端末) を再読み込みする | 起動からやり直してチケットの画面に戻る |

- 同じタブレットで切り替えると、バックグラウンドに回したアプリは、フォアグラウンドに戻したときに通知を扱う。  
  店では 1 台で 1 つのアプリをフォアグラウンドにしておくので、この遅れは起きない

### 進め方

| 段階 | 中身 |
| --- | --- |
| 1. 準備 | 決めたことを文書 (業務、API、データベース) と規則に入れる。`IDeviceKey` の非同期化、`IKitchenApi` と `RestKitchenApi`、チケットの通知、店舗の設定の遅れの時間 |
| 2. 基盤 | 起動、端末の設定と登録 (ブラウザの鍵)、レシーバ、端末の画面、画面を消さない、音、色と文言 |
| 3. チケット | 持ち場のタブ、チケットの一覧と明細の操作、下げる、下げたチケットと戻す、経過時間と遅れ |
| 4. 品切れ | 品の一覧と状態の設定 |
| 5. 確認 | キッチン端末とテーブル端末 (タブレット)・ホール端末 (スマートフォン) を並べ、注文から調理と提供までを確認する ([並べた確認](#並べた確認-2))。README にキッチン端末の画面を載せる |

- 段階ごとに文書を先に直してから作る。  
  検証 (`verify.py`) と画面で確認する
- キッチン端末で確認するときは、作り始めとできあがりまでの秒を長くしてサーバを起動する (開発のサーバの自動の進行が、キッチンを先に進めないように)

## 🔐 管理画面

管理画面 (Blazor Server。`TableOrder.Server.Web` の中) にサインインと利用者の役割を作り、開発の環境のほかでも開けるようにする。  
あわせて、次のものを作る。

- テナント・店舗・テーブルの管理
- EMM の登録トークンの発行
- 出したトークンの失効リスト
- 店内状況の画面

業務の処理は、今のとおり Service を直接呼ぶ。  
呼ぶときのコンテキストは、役割で絞ったテナントと店舗にする ([管理画面](business.md#管理画面))。

### 方針

- サインイン
  - 利用者をデータベースに持ち、メールアドレスとパスワードでサインインする
  - ASP.NET Core Identity の部品 (`UserManager`、`SignInManager`、パスワードのハッシュ、ロックアウト、認証アプリのコード) を、自前の表と Accessor で使う (Entity Framework は使わない)
  - 外部の ID 基盤 (OIDC) は、後から足せる形にする
- サインインの保ち方
  - Cookie で保つ (8 時間。使っていれば延ばす)
  - 検証の方法は経路で分ける。  
    `/api` と `/hubs` は端末のアクセストークン、ほかは Cookie にする (端末の API に Cookie を通さない)
- パスワード
  - 12 文字以上 (文字の種類は問わない)
  - 5 回続けて間違えたら 15 分止める
  - 管理者が出す仮のパスワードは一度だけ見せ、次のサインインで変更させる
  - メールでの招待と再設定は扱わない (管理者が仮のパスワードを再発行する)
- 多要素: 認証アプリのワンタイムコード (TOTP)
  - 利用者が自分のアカウントの画面で登録し (鍵は文字で出す)、回復用のコードを 10 個出す
  - 認証アプリの鍵はデータ保護で暗号にし、回復用のコードはハッシュで持つ
  - 認証アプリをなくしたときは、管理者が外す
- 役割: 運営者・テナント管理者・店舗担当者の 3 つ
  - 運営者はテナントに属さず、テナントを選んで扱う
  - テナント管理者は属するテナントのすべての店舗、店舗担当者は受け持つ店舗だけを扱う
- 店舗のコンテキスト: 選べるテナントと店舗を役割で絞る。  
  Service を呼ぶコンテキストには、役割の範囲で検証したテナントと店舗だけを入れる (画面で選んだ値をそのまま信じない)
- 再サインイン
  - 資格の印 (セキュリティスタンプ) を変更するとき: 利用者を止めたとき、役割や受け持つ店舗を変えたとき、パスワードを変えたとき、テナントを止めたとき
  - 開いている管理画面も、1 分のうちに再サインインさせる
  - 止めたテナントの利用者はサインインできない
- 初めの運営者: 運営者がひとりもいなければ、起動のときに設定 (秘密の値) のメールアドレスと仮のパスワードで作る。  
  開発の環境は、サンプルのデータに利用者を入れる
- 開く環境: どの環境でも開き、サインインの画面のほかはサインインを求める (Swagger UI の API の説明は、開発の環境だけのまま)

  本番の環境では、タスクの間で鍵を共有する ([本番の環境](#-本番の環境))
- 扱わないもの
  - 外部の ID 基盤 (OIDC)
  - メールでの招待と再設定
  - 操作の記録 (監査ログ)
  - 1 人の利用者が複数のテナントに属すること
  - 外部のクライアントと Webhook の画面 (外部の連携で作る)

### 登録トークン

| 項目 | 決めたこと |
| --- | --- |
| 範囲 | 店舗と端末の種類に限り、台数 (1~1000) と期限 (1~30 日) を決めて出す |
| 持ち方 | トークンは 32 バイトの乱数を Base64URL にし、発行の画面で一度だけ見せる (接続先と並べて、管理対象の構成に入れる値として出す)。データベースにはハッシュ (SHA-256) だけを持つ |
| 置き場所 | テーブル端末のテーブルとキッチン端末の持ち場は、登録したあとに端末の画面で割り当てる (テーブル端末は割り当てを待つ) |
| 取り消し | 取り消すと、それからの登録を断る (登録した端末はそのまま) |
| 残す期間 | ペアリングコードは期限を過ぎたら消す (同じコードを再発行できるように)。登録トークンは、期限を過ぎるか取り消してから 1 日で消す (それまでは一覧に出す) |

### 失効リスト

| 項目 | 決めたこと |
| --- | --- |
| 一覧 | 無効にした端末 (無効にしてからトークンの期限が過ぎるまで) と、止めたテナントを、サーバが覚える |
| 再読み込み | 起動のときにデータベースから読み、そのあとは数秒ごとに再読み込みする (サーバを並べても、どのサーバも数秒で同じ一覧になる)。無効にする・止める操作を受けたサーバは、すぐに再読み込みする |
| API | アクセストークンを検証したあとに一覧を引き、当たれば `401` にする (リクエストごとにデータベースは引かない)。端末はトークンを再取得し、`DEVICE_REVOKED` / `TENANT_SUSPENDED` で止まる |
| 通知の接続 | ハブはつないだ端末を覚え、一覧に入った端末とテナントの接続を切る。アクセストークンの期限が来た接続も切り、端末は新しいトークンで再接続する |

## 🍱 時間帯とキッズで出し分けるメニュー

ランチや朝定食のように時間帯で出す品と、子どもがいる来店だけに出すキッズメニューを、メニューのタグとルールで出し分ける。  
あわせて、2 つ目のサンプルのチェーンを和食の定食の店 (さつき軒) にし、時間帯とキッズを確認できるメニューにする。

### 方針

- 条件の持ち方
  - メニューに時間帯 (`dayparts`。コード、名前、店舗の現地時刻の始まりと終わり) を持たせる
  - ルールに、出せる条件の種類 (`Availability`) を足す
  - ルールが指すタグの品とカテゴリは、条件 (時間帯のどれかの中、子どもがいる) をすべて満たすときだけ出し、受け付ける
  - メニューは一日じゅう同じバージョンのままにする (時刻に合わせて再公開しない)
- 時間帯: 始まり ≤ 時刻 < 終わり。  
  終わりが始まりより前なら日をまたぐ。  
  曜日は扱わない
- キッズ: 来店の子ども (小学生以下) が 1 人以上のとき。  
  数は限らない (子どもの人数までの上限は backlog に置く)
- 見せ方
  - 条件を満たさない品とカテゴリは隠す (タブも、ほかのカテゴリの中の品も、人数分の提案も)
  - 品がひとつも出せないカテゴリも隠す
  - オプションは、品切れと同じく理由を添えて選べなくする
  - ホール端末の代わりの注文も同じにする。  
    キッチン端末の品切れの画面は、すべて出す
- 判定
  - 最後に決めるのはサーバ。  
    注文を受けた時刻 (店舗のタイムゾーン) と来店の子どもの人数で検証する
  - 満たさない明細は、`422` (`ITEM_UNAVAILABLE`) で明細ごとに返す
  - 検証の順は、メニュー・オプション・数量のあと、品切れの前
- 終わりの猶予
  - サーバは、時間帯の終わりから店舗の設定の分数 (`daypartGraceMinutes`。既定は 2 分、`0` は猶予なし、10 分まで) のうちに届いた注文も受ける (確定を押したあとの通信の遅れで断らない)
  - 端末は終わりの時刻で隠すので、新しく頼めるのは終わりの時刻まで
  - 始まりには猶予を付けない
- 再送と食後の品
  - 同じ id の再送は、時間帯によらず受け付けた注文を返す (今のルール)
  - 食後の品のお願いは受け付け済みの注文なので、時間帯の外でもよい
- 切り替わり
  - 端末は自分の時計と来店の人数で出し分ける。  
    時刻の見直し (30 秒ごと) と人数の変更 (`visit.updated`) で直す
  - タブとカードは、お客様の操作の途中 (ポップアップを開いている間など) でなければ並べ直す。  
    途中なら次の見直しで並べ直す
  - カートに入れるとき (商品の詳細、すぐ追加) と、注文を確定するときにも検証する
  - ホール端末は、並べ直すたび (カテゴリを変えたとき、カートを変えたとき、来店を再取得したとき) に再判定する
- 終わる前の表示: 時間帯の終わりの、ラストオーダーの表示と同じ分数 (`lastOrderNoticeMinutes`) 前から、注文の画面に「ランチのご注文は 15:00 までです」を出す (注文の停止とラストオーダーの表示を先に出す)
- カート
  - 条件を満たさなくなった品は、カートの行に理由を出し、外すまで注文を確定させない
  - 理由は、時間帯が終わったら「時間外」、子どもを 0 人にしたら「お子様のみ」
  - 送れたかわからない注文の再送は止めない (届いていれば、サーバは受けた注文を返す)
- 断られたとき
  - `ITEM_UNAVAILABLE` は、出せない品があることを表示して出し分けを直す
  - 送れたかわからない注文の再送で断られたら、その印を外してカートを直せるようにする
- 時計のずれ: 端末の時計がずれていても、最後はサーバが決める (断られたら品を外して再送してもらう)

### メニューの形 (想定)

```jsonc
"dayparts": [
  { "code": "morning", "name": { "ja": "朝", "en": "Morning" }, "start": "07:00", "end": "10:30" },
  { "code": "lunch", "name": { "ja": "ランチ", "en": "Lunch" }, "start": "11:00", "end": "15:00" }
],
"rules": [
  { "id": "…", "kind": "Availability", "targetTag": "lunch", "dayparts": ["lunch"] },
  { "id": "…", "kind": "Availability", "targetTag": "kids", "requiresChildren": true }
]
```

- 出せる条件のルールは、商品のタグ (選んだオプションのタグも) とカテゴリのタグに効く

### 作るもの

- 共有
  - メニューの時間帯と出せる条件のルール (`MenuResponse.Dayparts`、`MenuRuleKind.Availability`)
  - `ErrorCodes.ItemUnavailable`
  - 店舗の設定の猶予の分数 (`daypartGraceMinutes`)
  - 時間帯の中かと、終わりまでの残りを求める部品 (`StoreHours`)
  - 満たさない理由 (`TagRules.CheckAvailability`、`UnavailableReason`)
- 端末に共通の部品: メニューの出し分けの判定 (`MenuAvailability`。テーブル端末とホール端末で使う)
- サーバ: 注文の検証 (出せる条件と終わりの猶予)、管理画面の店舗の設定の猶予の分数、2 つのサンプルのメニューと、さつき軒のチェーンの設定・ロゴ・写真
- テーブル端末: メニューの出し分けとタブの並べ直し、終わる前の表示、カートの時間外、カートに入れるときと確定するときの検証、提案の絞り込み、文言
- ホール端末: 代わりの注文の出し分け (店舗のタイムゾーンと来店の人数で)、カートに入れるときと送るときの検証、文言

### 並べた確認

確認用の DB で、さつき軒のメニューの時間帯を今の時刻の近くに変える。  
テーブル端末 (タブレット) とホール端末 (スマートフォン) で確認する。

| 場面 | 操作 | 確認すること |
| --- | --- | --- |
| 時間帯 | 時間帯の始まりと終わりをまたぐ | 朝定食・ランチのタブと品が時刻で出たり隠れたりし、終わる前の表示が出る |
| カートの時間外 | カートにランチの品を入れたまま終わりの時刻を過ぎる | カートの行に時間外が出て、外すまで確定できない |
| 猶予 | 終わりの直後 (猶予の中) と、猶予を過ぎてから注文を送る | 猶予の中は受け付け、過ぎたら断られてメッセージが出る |
| キッズ | 子ども 0 人と 1 人で来店を開き、ホール端末で人数を直す | お子様のタブと品が出たり隠れたりし、カートのキッズの品に印が付く |
| ホール端末 | 代わりの注文 | テーブル端末と同じく出し分ける |

| 3. サンプルのデータ | さつき軒 (チェーンの名前・ロゴ・色、和食のメニューと写真)、バニーズのキッズの出し分け |
| 4. テーブル端末 | 出し分けと切り替わり、終わる前の表示、カートの時間外、確定の前の検証 |
| 5. ホール端末 | 代わりの注文の出し分けと検証 |
| 6. 確認 | 並べた確認、README の画像 (さつき軒のメニューの画面) |

- 段階ごとに文書を先に直してから作る。  
  検証 (`verify.py`) と画面で確認する

## 🧹 古いデータのクリーンアップ

動かし続けると増え続ける行 (閉じた来店とその注文・会計、再公開したメニュー) を、残す期間を過ぎたらバックグラウンドの処理で消す。  
売上の正は POS (外部の連携) にあり、注文サーバの来店は問い合わせと集計に使う間だけ残す。

### 方針

| 項目 | 決めたこと |
| --- | --- |
| 消すもの | 閉じた来店 (払い終えた、取りやめた) と、その確認の記録・注文・明細とオプション・チケット・呼び出し・支払・電子レシート |
| 残す期間 | 来店の営業日 (店舗のタイムゾーン、開店の時刻が区切り) から 90 日 (サーバの設定 `Cleanup:VisitRetentionDays`)。開いている来店 (来店中、会計中) は消さない |
| メニューの公開 | 店舗ごとに、今のメニューと直近の 10 件を残して消す (`Cleanup:MenuPublicationsKept`) |
| 消し方 | 店舗ごとにコンテキストを始め、古い来店を 1 回 200 件まで (`Cleanup:VisitBatchSize`) ずつ、1 つのトランザクションで子の表から消す (ほかの書き込みを長く止めない) |
| 間隔 | 今のクリーンアップ (通知、ペアリングコード、登録トークン) と同じ 1 時間ごと。設定は `Cleanup` にまとめる (`Event:CleanupMinutes` を `Cleanup:IntervalMinutes` に移す) |
| 記録 | 消した件数をログに残す |
| 今回作らないもの | 解約したテナントの行と画像 (テナントの解約の操作を作るときに一緒に作る)、Webhook の送り状況 (外部の連携で Webhook を作るときに) |

- 営業日で数えるので、同じ営業日の来店がまとまって消え、集計と問い合わせの単位とそろう
- 今の状態は変わらないので、消しても通知は送らない
- 失敗は店舗ごとに捕まえ、ほかの店舗は続ける

### 進め方

| 段階 | 中身 |
| --- | --- |
| 1. 準備 | 決めたことを計画と規則に入れる |
| 2. サーバ | クリーンアップの処理 (`CleanupService`、`CleanupAccessor`)、設定 (`CleanupSetting`)、ログ、テスト。作ったものを文書 (データベースの残す期間、構成、backlog、README) に移す |

- 画面は変わらないので、エミュレータでは確認しない

## 🧾 電子レシートの画面

支払が揃った来店の電子レシートを、テーブル端末が QR で出す URL (`/receipts/{トークン}`) で、お客様のスマートフォンに見せる。

### 方針

- 見せ方
  - サーバの Blazor の静的な画面 (サインインなし。推測できないトークンを知る人だけが開ける)
  - 管理画面の外の素の枠で、スマートフォン向けの 1 列にする
  - 検索に載せず、キャッシュさせない
- 引き方
  - トークンで電子レシートの行を引く (`DirectoryAccessor`。テナントのわからないリクエスト)
  - その行のテナントと店舗のコンテキストで、来店の会計の明細を作る (`BillCalculator`)。  
    閉じた来店は変わらないので、明細をコピーしない
- 中身
  - 適格簡易請求書の記載事項: 事業者の名前と登録番号、払い終えた日時、明細 (品の名前とオプション、数量、金額)、税率ごとの対象額と税額、合計
  - そのほか: チェーンと店舗の名前、テーブル、支払 (方法と額)
  - 税率が 2 つ以上ある来店は、明細に税率を添える (どの品がどの税率かを示す)
- 事業者の名前と登録番号
  - 店舗の設定に持つ。  
    フランチャイズの店は店ごとに事業者が違うので、店舗を足すときにコピーしない
  - 登録番号は T と 13 桁の半角の数字にする。  
    入れるときは事業者の名前も求める
  - 電子レシートには、作ったときの値をコピーする (あとで店舗の設定を変えても、出したレシートの事業者は変えない)
  - 登録番号のない店は、登録番号のないレシート (適格簡易請求書でない) として出す
- 言語: ブラウザの言語 (日本語、英語) で出す。  
  品の名前とオプションは、メニューの名前からその言語を選ぶ (ない言語は日本語)
- 見られる期間: 来店と同じ (営業日から 90 日。クリーンアップで消えたら見つからない)
- 見つからないとき: トークンがない・消えたときは、404 で「見つかりません」を出す (トークンがあるかないかのほかは見せない)
- 開発の DB: 店舗と電子レシートの列を足すので作り直す (スキーマは起動のときに SQL から作り、今ある DB の表は変えない)

### 進め方

| 段階 | 中身 |
| --- | --- |
| 1. 準備 | 決めたことを計画と規則に入れる |
| 2. サーバ | 店舗の事業者の名前と登録番号 (スキーマ、サンプルのデータ、店舗の設定の Service と管理画面、検証)、電子レシートの画面 (`ReceiptService`、画面、文言)、テスト。作ったものを文書 (業務、データベース、構成、backlog、README) に移す |
| 3. 確認 | エミュレータのテーブル端末で払い、出た QR の URL の画面をスマートフォンの大きさのブラウザで開いて確認する |

- 店舗の中で閉じない機能 (お客様のスマートフォンで開く) は、いったん止めている。  
  画面とテストを作ったところで止め、README の画像は載せない

## 🔗 外部の連携

本部の管理システム・POS とつなぐところは、このシステムの中で閉じないので、今は作らずに設計だけを置く。  
対象は、外部のクライアント、メニューと写真の公開、POS の参照と来店の終了、Webhook。

- API の形: [API の想定](api-design.md#46-外部) の各節
- 表: [database.md](database.md) の `ApiClients`・`WebhookEndpoints`・`WebhookDeliveries`・`MenuPublications`
- 作っていない機能: [backlog.md](backlog.md) にまとめた

### 方針

| 項目 | 決めたこと |
| --- | --- |
| 作る範囲 | 今は作らない。作るときは外部のクライアントを先に作り、メニューと写真の公開、端末の再読み込み、POS、Webhook の順に足す |
| 外部のクライアント | テナント管理者が管理画面で発行する。テナント全体 (本部) か 1 つの店舗 (POS) に属し、使える範囲 (`scope`) を決める |
| トークン | OAuth 2.0 の client credentials で出す。端末と同じ署名の鍵の JWT (30 分) にする |
| 秘密 | `client_secret` と Webhook の鍵は 32 バイトの乱数にし、出した画面で一度だけ見せる。`client_secret` は SHA-256 で持ち、Webhook の鍵は署名に使うのでデータ保護で暗号にして持つ |
| 取り消し | 取り消したクライアントの出したトークンは、端末と同じく失効リストで拒否する |
| メニューの公開 | 本部がメニューを丸ごと公開し、受け取ったらすぐに今のメニューを切り替える。時間帯で出す品はメニューの時間帯とルールで表すので、時刻に合わせて再公開しない ([時間帯とキッズで出し分けるメニュー](#-時間帯とキッズで出し分けるメニュー)) |
| 端末の反映 | `menu.published` で、テーブル端末・ホール端末・キッチン端末がすぐに再読み込みする。テーブル端末は来店中もすぐに再読み込みし、カートの使えなくなった品を外してメッセージを出す |
| POS | 店舗に限るクライアントで、テーブルと来店と会計の明細を読み、レジで払った来店を終える。売上は Webhook (`visit.closed`) で受け取る |
| Webhook | 送り先は管理画面で登録する。店舗の通知を書くトランザクションで送るもの (配信) を作り、バックグラウンドの処理が送る |
| Webhook の再送 | 受け取られるまで、間隔を延ばしながら 24 時間再送し、過ぎたらあきらめる。管理画面で送り状況を見て、あきらめた配信を再送できる |
| レート制限 | リクエストの数を、クライアントごととテナントごとに制限する (`429`) |

### 外部のクライアント

| 項目 | 決めたこと |
| --- | --- |
| 発行 | 名前、範囲、店舗 (POS は店舗に限る) を決めて発行し、`client_id` (GUID) と `client_secret` を一度だけ見せる |
| 範囲 | `menu.publish` (写真を置き、メニューを公開する)、`visits.read` (テーブル・来店・会計の明細を読む)、`visits.close` (来店を終える)。範囲の外のリクエストは `403` (`CLIENT_SCOPE`) |
| トークン | `POST /oauth/token` (フォームの本文。`grant_type=client_credentials`、`client_id`、`client_secret`、任意の `scope`)。範囲を省けばクライアントの範囲すべてにし、範囲の外を求めたら `invalid_scope` |
| クレーム | `sub` はクライアントの Id、`tenant_id`、店舗に限るクライアントは `store_id`、`scope` (空白で区切る)。端末のクレーム (`device_kind`) は持たない |
| 断るとき | 知らないクライアント・違う秘密・取り消したクライアントは、どれも `401` `invalid_client` にして理由を見せない。止めたテナントは `400` `unauthorized_client` |
| 秘密の再発行 | 新しい秘密を一度だけ見せ、前の秘密はすぐに使えなくする (相手の設定を変えるまで止まる) |
| 最後に使った時刻 | トークンを出した時刻を記録し、使われていないクライアントを見つけられるようにする |

### メニューと写真の公開

| 項目 | 決めたこと |
| --- | --- |
| 写真 | `PUT /images/{name}` (`image/png` / `image/jpeg` / `image/webp`、2 MB まで。中身の先頭で形式を検証する) |
| 写真の名前 | 今のルール (内容のハッシュを入れる) にする。同じ名前で同じ中身なら `204`、違う中身なら `409` (`IMAGE_CONFLICT`) |
| 公開 | `POST /menu/publications` (`MenuPublishRequest { storeCodes, menu }`) → `200` (`{ menuVersion, storeCodes }`)。テナント全体のクライアントは店舗コードを並べ、店舗に限るクライアントは自分の店舗だけに公開する |
| 検証 | 誤りは `400` (`VALIDATION_ERROR`) で、項目の場所 (`menu.items[3].optionGroupIds[0]`) ごとに理由を返す |
| 店舗 | 複数の店舗への公開は 1 つのトランザクションにし、知らない店舗コードがあれば全体を断る |
| バージョン | `menuVersion` はサーバが店舗ごとに採番する (同じ中身の公開でも変える) |
| 持ち場 | 持ち場の Id は再公開しても変えない (キッチン端末の受け持ちが Id を指す)。消えた持ち場のチケットは出さない |
| 品切れ | 公開で消えた商品とオプションの品切れの行を消し、`stock.updated` を送る |
| 通知 | 店舗ごとに `menu.published` (`{ menuVersion }`) を送り、公開したクライアントを記録する (`MenuPublications.ApiClientId`) |

公開で検証する項目:

- Id の重なり
- 指すもの (カテゴリの商品、商品のオプションの組と持ち場、ルールの提案する商品)
- 価格と差額 (0 以上)
- 税率
- 選ぶ数 (`0 ≤ minSelect ≤ maxSelect ≤ オプションの数`)
- 写真の名前が保存先にあること
- 名前の日本語

### 端末の再読み込み

| 端末 | 決めたこと |
| --- | --- |
| テーブル端末 | `menu.published` を受けたら、来店中でもすぐにメニューと品切れを再読み込みする |
| ホール端末 | すぐに再読み込みする。代わりの注文のカートも、テーブル端末と同じく合わせ直す |
| キッチン端末 | すぐに再読み込みする (持ち場の名前と品切れの画面) |
| 写真 | 名前は内容で変わるので、新しい名前の写真だけを取りに行く |
| 通知の受信 | `TableOrder.Client` の通知に `menu.published` を足す (今は読み捨てている) |

- テーブル端末のカート
  - 商品とオプションがあって価格が同じ品は残す。  
    ほかは外し、「メニューが変わりました」と出す
  - 商品の詳細と注文の確認を開いていたら閉じる
  - 注文が公開と行き違って `MENU_CHANGED` で断られたときも、再読み込みして同じように表示する

### POS

| 項目 | 決めたこと |
| --- | --- |
| クライアント | 店舗に限るクライアントに `visits.read` と `visits.close` を持たせる |
| 読む | `GET /tables` (テーブルと今の来店)、`GET /visits/{id}`、`GET /visits/{id}/bill` (会計の明細と合計) |
| 来店を終える | `POST /visits/{id}/close` (`closedBy` は `Register`、`version`、任意の `staffId`) で終え、通知 `visit.closed` を送る。会計中も閉じられ、バージョンが違えば `409` で再取得する |
| 流れ | レジで払うお客様のテーブルを選び、会計の明細で精算して来店を終える。明細の商品コード (`ItemCode`) で POS の商品と合わせる |
| 売上 | 売上の取り込みは Webhook の `visit.closed` (会計の明細と支払) で行う |

### Webhook

| 項目 | 決めたこと |
| --- | --- |
| 送り先 | 名前、URL (本番は `https` だけ)、送る種類、店舗 (省けば全店舗) を管理画面で登録する。鍵はサーバが作って一度だけ見せ、再発行できる |
| 種類 | `order.created` (注文)、`visit.closed` (来店、会計の明細、支払)、`stock.updated` (品切れ) |
| 本文 | `{ id, type, occurredAt, tenantId, storeId, storeCode, seq, data }` (`id` は配信の Id) |
| 署名 | `X-Signature: t={送った時刻の Unix 秒},v1={HMAC-SHA256(鍵, "{t}.{本文}") の 16 進}`。受信側は時刻が 5 分より古いものを捨てる |
| 配信の作成 | 店舗の通知を書くトランザクションで、種類と店舗の合う送り先ごとに配信 (`WebhookDeliveries`) を作る。本文は作るときにコピーする (古い通知を消しても再送できる) |
| 送る | バックグラウンドの処理が、送る時刻の来た配信を送る (1 回の時間切れは 10 秒)。`2xx` で送れたことにする |
| 再送 | `2xx` 以外・時間切れ・通信の失敗は、1 分から倍にして 1 時間までの間隔で、作ってから 24 時間再送する。過ぎたらあきらめ (`Abandoned`)、管理画面で再送できる |
| 順番 | 順番は保たない (再送で前後する)。受信側は `seq` で重なりを捨て、来店は最後の状態 (`visit.closed`) で決める |
| 止める | 送り先を止めると、待っている配信をあきらめにする |
| 残す期間 | 送れた配信は 7 日、あきらめた配信は 30 日で消す (`CleanupWorker`) |

- 送り先の一覧はテナントごとに覚え、管理画面で変更したら再読み込みする

### 画面

| 画面 | 経路 | 使える役割 | 内容 |
| --- | --- | --- | --- |
| 外部のクライアント | `/clients` | 運営者、テナント管理者 | 一覧 (名前、範囲、店舗、最後に使った時刻、状態)、発行 (秘密を一度だけ見せる)、秘密の再発行、取り消し |
| Webhook | `/webhooks` | 運営者、テナント管理者 | 送り先の一覧・登録・変更・止める、鍵の再発行、送り状況 (配信の一覧を状態と種類で絞る、あきらめた配信の再送) |

### 表の直し

`ApiClients`・`WebhookEndpoints`・`WebhookDeliveries` は表を作ってあるが、作るときに次を直す。

| 表 | 直すこと |
| --- | --- |
| `ApiClients` | `UpdatedAt`・`Version` (秘密の再発行と取り消しの楽観ロック)、`LastUsedAt` (最後にトークンを出した時刻) を足す |
| `WebhookEndpoints` | 鍵を暗号にして持つ (`Secret` を、データ保護で暗号にした値にする) |
| `WebhookDeliveries` | 管理画面の絞り込みに `Type` を足す。あきらめた配信を再送するときは、`Status` を `Pending` に戻して回数と時刻を数え直す |

### 作るときの段階

| 段階 | 中身 |
| --- | --- |
| 1. 外部のクライアント | 表の直し、`POST /oauth/token`、範囲のポリシー (`CLIENT_SCOPE`)、失効リストにクライアントを追加する、レート制限、管理画面 |
| 2. 写真とメニューの公開 | `PUT /images/{name}`、`POST /menu/publications` (検証、品切れの削除、`menu.published`) |
| 3. 端末の再読み込み | 通知の受信、テーブル端末のカートの合わせ直し、ホール端末とキッチン端末の再読み込み。エミュレータで公開の反映を確認する |
| 4. POS | 範囲のポリシーを今の API に足す |
| 5. Webhook | 配信を作る、送るバックグラウンドの処理、署名、管理画面と送り状況 |

- テストは、外部のクライアントをテストのサーバにつないで動かす。  
  Webhook は、テストの受信側 (テストのサーバの中の HTTP のエンドポイント) で受けて確認する

## ✅ 確認の方法

- ビルド・テスト・解析: `python .claude/skills/verify/scripts/verify.py` (Release と Debug の警告 0、テスト、InspectCode 0 件、改行コード、文書の改行)
- 画面: `emu.py boot Tablet_1920x1200_Android15` (受付機は縦置きの `Tablet_1200x1920_Android15`)、`emu.py install`、`emu.py shot` で撮って確認する (`.claude/skills/emulator/`)
- 外部の EMM: `emu.py emm` で EMM の代わりの DPC を入れ、ロックタスクの許可と管理対象の構成を配信して確認する
- フェーズの終わりに、主な画面を撮って README の画像にする
