# 実装計画

ファミリーレストランのテーブルに置くタブレットで、お客様が自分で注文するアプリ (テーブルオーダー) の実装計画。  
最初は画面のモックだけを作り、通信はサービス層がモックの応答を返す形にする。  
業務の前提は [business.md](business.md)、通信の形は [api-design.md](api-design.md) の想定に合わせ、作ったものの構成は [architecture.md](architecture.md) に書く。  
フェーズを終えたらチェックを付け、作り終えたら設計文書に移して、この文書は消す。

## 🎯 前提

| 項目 | 内容 |
| --- | --- |
| 業態 | ファミリーレストランのチェーン (店内飲食。ドリンクバーあり、時間制のコースなし) |
| 対象 | Android のタブレット (10 インチ前後、1920x1200、横向き) |
| 会計 | テーブル端末で行う (QR コード決済、クレジットカード)。現金はレジ |
| 言語 | 日本語と英語 (画面の文言、メニューの名前と説明) |
| 来店の開始 | 最終的にはスタッフ (ホール端末) か受付機が人数を入れて来店を開く。ホール端末ができるまでは、テーブル端末でお客様が人数を入れて開く (`selfStart`) |
| 構成 | モノレポ。区分 (共有、サーバ、端末) ごとのフォルダに置く ([プロジェクト](#プロジェクト)) |
| 通信 | 要求は REST (Minimal API) か gRPC、通知・プッシュ・端末の状態は SignalR か gRPC のストリーム、テレメトリは OpenTelemetry (OTLP)。入口が違っても業務の処理は同じにする |
| 特例の扱い | ドリンクバー、お酒、キッズ、数量限定などはコードで分けず、メニューのタグとルールの設定で表す |

| 基にした構成 | template-maui-keyboard (物理キーと Input 関連を除く)、example-maui-pos の端末、template-avalonia-desktop の画面の切り替え、template-maui-server の通信 |
| 確認 | エミュレータ Tablet_1920x1200_Android15 (220dpi、約 1396x873dp) |
| 将来 | Android の MDM 用 API (Device Owner、ロックタスク) で専用端末にする |

## 🔎 UI の調査

国内のテーブルオーダーと海外のセルフオーダー (キオスク) の機能・画面の作り・UX の知見を調べ、取り込むものを決めた。

### 共通する機能

- 写真付きのメニュー、おすすめの表示、カスタマイズ (部位、ソース、サイズ)
- 注文履歴、スタッフの呼び出し
- 品切れ、アレルギーの表示、多言語 (英語・中国語・韓国語など)
- 会計 (POS との連携、割り勘、セルフレジ、テーブル決済)
- 年配の客層にも読める文字の大きさ、説明の要らない操作

### 画面の型

- 上にカテゴリ、写真付きの商品の一覧を並べ、注文 (カート) は常に見えるところに件数と合計を出す
- 商品の詳細でオプションと数量を選んでからカートに入れ、カートの中でも数量やオプションを直せる
- 注文を確定する前に内容を確かめる
- 注文・履歴・会計を 1 つの画面の中の操作で回す

### UX の知見

- タッチの的は 10mm 以上 (年配の方は 11.4mm 以上)、間隔は 3〜12mm がよい
- 追加の提案 (アップセル) は注文の途中で何度も割り込まず、確定の前に 1 画面にまとめる (1 回の注文で 3 回未満)
- 提案を受ける / 断るボタンは同じ大きさ・同じ重みにする (断りにくくする作りは信頼を損ねる)
- アレルギーはカードと詳細の 2 段で示す
- 料理の写真を主役にする

### 飲食チェーンの例

- 大手のファミリーレストランのチェーンには、客席のデジタルメニューブックで QR コード決済とアプリのクレジットによるテーブル決済をしているところがある
- 回転寿司のチェーンには、入口のタッチパネルでチェックインすると自動の案内で席に誘導するところがある (人数は受付で決まり、席の端末で注文する)
- POS の伝票は人数とテーブルを持つ (注文の API に客数とテーブルの項目がある)。  
  人数は客数として客単価の分母になる

### 取り込むこと

| 調べたこと | 本アプリでの形 |
| --- | --- |
| カテゴリを上に、カートを常に表示 | 上部のタブ、右に固定した注文リスト (件数と合計) |
| 詳細でオプションと数量を選ぶ | カードから商品の詳細を開く (オプションのない商品はカードの + ですぐ入れる) |
| 確定の前の確認 | 注文の確認 (追加の提案は 1 枠だけ) |
| 履歴・呼出・会計 | 下部の操作の帯 |
| ドリンクバー | 単品とセットのオプションにタグ (`drink-bar`) を付け、人数より少なければ提案のルールで注文の確認に出す |
| 食後のデザート | 詳細で「食後にお持ちする」を選べ、注文履歴からお願いする |
| テーブル決済 | お会計の画面で QR コード決済とカード、電子レシートの QR |
| 人数 | 来店の開始で入れ (今はテーブル端末でお客様が入れる)、ヘッダに出す。提案のルールと割り勘の目安に使う |
| 品切れ・アレルギー | カードに品切れの幕、詳細にアレルギー (特定原材料 8 品目) とカロリー |
| タッチの的 | 押せる面は 64dp (約 10mm) 以上、主な操作は 80dp 以上 |

## 🌐 接続先と障害対策の調査

テーブルオーダーと飲食店の POS (国内外のクラウド型の製品) が、どこにつなぎ、回線が切れたときにどうしているかを調べた。

### 店舗の中の仕組みの型

| 型 | 接続先 | 店舗の中の仕組み | 回線が切れたとき |
| --- | --- | --- | --- |
| ハブの端末 | クラウド | 有線でつないだ 1 台をハブにして、同じ LAN の端末・キッチンの表示・キッチンプリンタをつなぐ | 注文は LAN の中でキッチンの表示とプリンタに届き、回線が戻るとクラウドへ送る |
| 店舗のサービス | クラウドと店舗のサービス | 店舗に取引を受け持つサービスを置く | 店舗のサービスが取引をためて、回線が戻ると送る。設定の変更は届かず、レポートは遅れる |
| 店舗の機器 | クラウド | オプションの小さな機器を店舗に置く | 注文を機器にためて営業を続け、回線が戻るとクラウドへ送る |
| 端末の間の LAN | クラウド | 端末どうしが LAN でつながる | LAN が生きていれば注文・キッチンの印刷・端末の間の共有は続く。カード決済とメニューの変更は止まる |
| 端末に保存 | クラウド | 端末に注文と売上を残す | 注文と売上を端末に残して営業を続ける |

- 多くはクラウドを正とし、回線が切れても注文を厨房へ通す仕組み (ハブの端末、店舗のサービス、店舗の機器) を店舗に置く
- 回線が切れている間に止まるのは、カード決済 (オンラインの承認)、メニューと設定の変更の配信、本部のレポート
- 共通の備えは、LTE の予備回線、SD-WAN、UPS、ハンディや手書きの伝票への切り替え

### 本アプリでの考え方

| 段階 | 接続先 | 回線が切れたとき |
| --- | --- | --- |
| 1 (最初) | 端末はクラウドの注文サーバに直接つなぐ | 縮退して動く。注文は端末に残して同じ `id` で送り直し、通知はつなぎ直して通し番号 (`seq`) で追いつく。会計はレジへ案内する |
| 2 (必要になったら) | 店舗にエッジ (同じ API を出す小さなサーバ) を置き、端末はエッジにつなぐ。エッジはクラウドと同期する | 店舗の LAN の中で注文・調理・提供・呼び出しを続け、回線が戻ると同期する |

- 店舗のエッジもクラウドと同じ API (要求と通知) を出し、端末は接続先を替えるだけで済むようにする
- どちらの段階でも、端末が採番する `id` (送り直しで重複しない)、通知の通し番号と追いつき、端末の状態とテレメトリの監視 (SignalR、OTLP) で、障害に気付いて戻せるようにする

## 🎨 デザイン

### 方針

- 角丸・影・グラデーション・すりガラス・絵文字を使わない (よくある生成された UI の見た目を避ける)
- 四角い面と罫線と色の面で組み、帯 (ヘッダ、タブ、下部の操作) を画面の端まで通して、隣の列の帯と高さを揃える
- 料理の写真と、料理名・価格の文字組みで見せる
- 色は役割の名前で定義し、チェーンのイメージカラーに替えられるようにする
- 起動と端末の設定 (システムの画面) は、チェーンの色ではなくシステムの色とロゴで組む
- 英語では語が長くなるので、タブとボタンは幅に余裕を持たせ、料理名は 2 行まで折り返す

### 色の役割

色は `Resources/Styles/Colors.xaml` に役割の名前で定義し、スタイル・画面・記号は役割の名前だけを使う。  
チェーンのイメージカラーに合わせるときは Brand の節を差し替える。

| 区分 | 役割 | 既定 | 使うところ |
| --- | --- | --- | --- |
| Brand | `Primary` / `PrimaryPressed` / `OnPrimary` | 朱 `#C53D13` | 選択中のタブ、注文の確定などの主な操作 |
| Brand | `PrimaryContainer` / `OnPrimaryContainer` | 淡い朱 `#FBE4DA` | 件数、選んだオプション、提案の枠 |
| Brand | `Secondary` / `SecondaryPressed` / `OnSecondary` | 墨 `#22201C` | お会計などの強い操作、待受の地 |
| Neutral | `Canvas` | `#F3F0EA` | 画面の地 |
| Neutral | `Surface` / `SurfaceVariant` | `#FFFFFF` / `#EAE6DE` | 面 (ヘッダ、タブ、カード、パネル) / 沈んだ面 (押下、増減のボタン) |
| Neutral | `OnSurface` / `OnSurfaceVariant` | `#22201C` / `#6B665C` | 本文 / 補足の文字 |
| Neutral | `Outline` / `OutlineVariant` | `#D6D0C4` / `#E7E2D9` | 罫線 / 薄い区切り |
| Neutral | `Disabled` / `OnDisabled` | `#E4E0D8` / `#A29C90` | 押せない操作 |
| Neutral | `Scrim` / `OnScrim` | 黒 60% / 白 | ポップアップの後ろと売り切れの幕 |
| Status | `Error` / `OnError` | `#B3261E` | 失敗 |
| Status | `Success` / `OnSuccess` | `#2E7D32` | 注文と支払の完了 |
| Status | `Warning` / `OnWarning` | `#A15C00` | まだ出していない品、ラストオーダー |
| System | `SystemCanvas` / `SystemSurface` / `OnSystemCanvas` / `OnSystemCanvasVariant` / `SystemOutline` / `SystemAccent` / `SystemAccentPressed` / `OnSystemAccent` | 灰 `#F4F5F7`、墨 `#1F2328` | 起動、端末の設定、電卓 (スプラッシュとアプリのアイコンの色と揃える) |

- 面と文字は対 (`Xxx` と `OnXxx`) で使い、コントラスト比 4.5 以上を保つ
- 記号 (`Markup/AppIcons`) は色の値を持たず、役割の名前から色を引く
- 店舗の設定からブランド色を受け取って起動時に替える仕組みは、後のフェーズで作る (API の `theme` は役割の名前で色を返す)

### チェーンの名前と印

チェーンの名前は画面の文言 (`AppResources.resx` と `AppResources.en.resx`) の `BrandName` に、印は `Markup/AppIcons` の `BrandGlyph` (Material Icons のグリフ) に置き、Brand の色と合わせて替える。  
今はチェーンを「バニーズ」(Bunny's) とし、印をうさぎにしている。  
店舗の名前 (端末の設定の `storeName`) は店ごとの値で、チェーンの名前とは分ける (今の画面には出さない)。

### 寸法と文字

| 要素 | 寸法 |
| --- | --- |
| ヘッダ | 高さ 64dp |
| カテゴリのタブ | 高さ 64dp、幅 144dp 以上 |
| 下部の操作・注文の確定 | 高さ 80dp |
| 注文リストの列 | 幅 400dp |
| メニューのカード | 4 列 3 段、高さ 208dp (絵 148dp、文字 2 行 60dp)、間隔 8dp |
| 注文リストの行 | 2 段 (料理名と数量の増減 64dp、食後の印・オプション・金額) |
| 押せる面 | 64dp 以上 (主な操作は 80dp 以上) |

- メニューのカードは 1 画面に 4 列 3 段 (12 品) を見せる (注文リストを右に置く注文端末は 3 段が多い)
- ヘッダ・タブ・下部の操作は押せる面の高さまで詰め、残りの高さをカードの絵に回す

| 用途 | 文字の大きさ |
| --- | --- |
| 待受の見出し | 72 |
| 合計の金額 | 28〜32 |
| ヘッダ・パネルの見出し、詳細の価格 | 22〜24 (太字) |
| タブ・操作 | 20〜22 (太字) |
| 本文 | 18 |
| カードの料理名と価格 | 17 (太字) |
| 補足 | 13〜16 |

### 写真の代わり (モック)

- 料理の絵 (SVG、4:3) を写真の代わりに置き、カテゴリで地の色を変える (肉料理は木の台と鉄板、パスタとサイドは白い皿、デザートは淡い桃色、ドリンクは淡い青)
- 実際の写真はサーバから受け取り、端末に保存して使う (後のフェーズ)

## 📐 メイン画面の配置

上にヘッダとカテゴリのタブ、左にメニューのカード、右に注文リスト、下に履歴・呼出・会計を置く。  
注文リストの列は右端に固定し、注文の確定は下部の操作の帯と同じ高さに並べる。

```
+------+---------------------------------------+--------------------+------------------+
| ##   | チェーンの名前                        | テーブル 12・3 名  | 言語 / Language  |  ヘッダ 64dp
+-----------+------------+---------+-----------+---------+-------+---------------------+
| おすすめ  | ハンバーグ | パスタ  | デザート  | キッズ  | …     | ご注文リスト  [4]   |  タブ 64dp / 注文リストの見出し
+-----------+------------+---------+-----------+---------+-------+---------------------+
| +------------+ +------------+ +------------+ +------------+    | ハンバーグ [-] 2 [+]|
| |人気        | |            | |   売切れ   | |NEW         |    | セット・DB    ¥3,256|  メニュー (4 列 3 段のカード)
| |          + | |          + | |            | |          + |    | パフェ     [-] 1 [+]|  注文リスト (2 段の行)
| |ハンバーグ  | |ドリア      | |ステーキ    | |パフェ      |    | 食後            ¥699|
| |        ¥999| |        ¥599| |      ¥1,499| |        ¥699|    | サラダ     [-] 1 [+]|
| +------------+ +------------+ +------------+ +------------+    |                 ¥459|
| (同じ高さのカードがあと 2 段。多いときは縦にスクロール)        |                     |
|                                                                +---------------------+
|                                                                | 合計 (税込) ¥4,414  |
+---------------------+---------------------+--------------------+---------------------+
| 注文履歴            | 店員呼出            | お会計 (補助色)    | 注文を確定する      |  操作 80dp (主色は確定だけ)
+---------------------+---------------------+--------------------+---------------------+
```

- ヘッダ: チェーンの名前、テーブルと人数、言語 (今の言語を出し、押すと言語を選ぶポップアップを開く)
- カテゴリのタブ: 横にスクロールし、続きがある向きの端に送りのボタン (‹ ›) を重ねて、まだタブがあることを示す
- カード: 写真、料理名 (2 行まで)、価格 (税込)、印 (おすすめ、人気、NEW、期間限定)、品切れの幕、すぐ入れる + (オプションのない商品だけ。写真の右下に重ねる)
- カードの文字は 2 行の高さで揃える。  
  料理名の 1 行目は価格の上まで使い、2 行目に入ったときだけ価格の分を空けて、価格は最後の行の右に置く。  
  行の高さは固定し、英語でも価格を料理名の 2 行目にそろえる
- カードを押すと商品の詳細 (プレビュー) を開く
- 注文リストの行: 上の段に料理名と数量の増減 (0 で削除)、下の段に食後の印、選んだオプション、金額。  
  オプションは省略せずに折り返して全部見せる。  
  行を押すと詳細を開いて直せる
- 注文の確定は、リストが空のときは押せない

## 🧱 構成

### プロジェクト

今あるプロジェクトと名前の付け方は [architecture.md](architecture.md#-1-プロジェクト) に書いた。

```
shared/                 共有 (サーバ・端末・Web アプリ)
  src/    TableOrder.Domain、TableOrder.Contract、TableOrder.Client
  tests/  TableOrder.Domain.Tests、TableOrder.Client.Tests
server/                 注文サーバと、サーバが配る Web アプリ (TableOrder.Server.slnx)
  src/    TableOrder.Server.Core、TableOrder.Server.Web、TableOrder.Server.AppHost、TableOrder.Web.Kitchen
  tests/  TableOrder.Server.Core.Tests、TableOrder.Server.Web.Tests

  src/    TableOrder.Terminal.Shared、TableOrder.Terminal.Table、TableOrder.Terminal.Hall、TableOrder.Terminal.Reception
```

これから足すプロジェクト:

| プロジェクト | 種類 | 内容 |
| --- | --- | --- |
| `TableOrder.Server.Core` | .NET | 業務の処理 (来店、注文、調理、提供、呼び出し、会計、ルールの確認) とデータの保存。入口に依存しない。骨組み (端末の登録、店舗、メニュー、品切れ) はある |
| `TableOrder.Server.Web` | ASP.NET Core | 入口 (REST、SignalR、OTLP の受け口、外部の Webhook)、管理画面 (Blazor Server)、Web アプリの配信。受けた要求を `Server.Core` に渡すだけにする。骨組みはある |
| `TableOrder.Server.AppHost` | Aspire | 開発で動かす構成 (サーバ、データベース、テレメトリの受け口)。サーバを動かすだけのものはある |
| `TableOrder.Web.Kitchen` | Blazor WebAssembly | キッチン端末 (KDS。チケット、作り始め、できあがり)。サーバが `/kitchen` で配る。枠はある |
| `TableOrder.Terminal.Shared` | .NET MAUI のライブラリ | 端末に共通の部品 (専用端末、EMM の設定、端末の情報、電卓、色とスタイルの土台)。2 つ目の端末アプリを作るときに、テーブル端末から移す |
| `TableOrder.Terminal.Hall` | .NET MAUI (Android のスマートフォン) | ホール端末 (スタッフのハンディ。来店の開始、呼び出しの対応、提供、品切れ)。枠 (起動して仮の画面を出す) はある |

| `TableOrder.Server.Core.Tests` / `TableOrder.Server.Web.Tests` | xunit | 業務の処理のテストと、API・通知のテスト |

### キッチン端末

キッチン端末は、表示とサーバへの操作だけなので、Web の画面を全画面で出せば足りる。  
ただし、ブラウザの全画面 (操作が要り、戻るや通知で外れる) には頼らず、次のようにする。

| 課題 | 対応 |
| --- | --- |
| 全画面 | EMM のキオスクのブラウザで URL を固定して開く |
| 通信が切れたとき | 表示を保ち、つながったら `seq` で抜けた通知を取り直す。Blazor Server は切れると操作できないので、WebAssembly にする |
| 音の知らせ | キオスクのブラウザで自動再生を許す (許せない端末は、起動したあとに 1 回触れてもらう) |
| 画面を消さない | 画面の Wake Lock か、端末の設定 |
| 端末の登録 | ペアリングコードを 1 回入れ、鍵はブラウザから取り出せない形で持つ |
| バンプバー | USB のキーの入力として受ける (なくても触って操作できるようにする) |
| 伝票のプリンタ | 扱わない (KDS を前提にする) |

- EMM のキオスクのブラウザがない店や、自前の Device Owner の店のために、Web の画面を全画面で開くだけの端末アプリ (`TableOrder.Terminal.Kitchen`、WebView) を作る余地を残す
- 端末の窓口 (`TableOrder.Client`) は WebAssembly でも動くので、テーブル端末と同じ窓口 (`IKitchenApi`、`IOrderEvents`) を使う

### ほかのアプリ

| アプリ | 判断 |
| --- | --- |
| 管理画面 (店舗と端末) | 作る。端末のペアリングとテーブルの割り当て、登録トークン、店舗の設定 (注文の一時停止、ラストオーダー、色)、端末の状態。`Server.Web` の中に置く |
| 受付機 | 任意。予約・順番待ちのシステムを使わない店のために、テーブル端末と同じ専用端末の仕組みで作る (枠は先に用意した) |
| お客様のスマートフォンからの注文 | 作らない (API の想定の範囲の外)。作るなら `TableOrder.Web` の下に置き、読み込みの軽さを優先した作りを別に考える |
| 店舗のエッジ | 検討。サーバ (`Server.Core`、`Server.Web`) を店に置き、クラウドとの同期を足す形にする |
| 本部の管理システム、POS、決済サービス、配膳ロボット | 外部のシステム。サーバの入口 (API、Webhook) でつなぎ、このリポジトリにアプリは作らない |

### 決めたこと (サーバ)

- 要求は REST (Minimal API)、通知は SignalR で作る。  
  gRPC は必要になってから足す (業務の処理は入口によらず同じにしてある)
- 接続先はクラウドに直接つなぐ (店舗のエッジは後で考える)
- 端末の認証は、端末の鍵で署名した短命の JWT にする (流れは [api-design.md](api-design.md#15-認証認可)、決めるときに調べたことは [端末の認証](#-端末の認証))
- 複数の会社 (テナント) が契約して使う形にする。  
  テナントと店舗はアクセストークンのクレームで決めて認証のあとは信用し、要求の中の `id` はテナントと店舗の中で引く (決まりは [api-design.md](api-design.md#16-テナント)、決めるときに調べたことは [マルチテナント](#-マルチテナント))
- 外部のシステムは、テナントごと (POS は店舗ごと) のクライアントで OAuth 2.0 の client credentials のアクセストークンを受け取る
- ホール端末は .NET MAUI、キッチン端末は Web (Blazor WebAssembly) で作る
- データベースは template-maui-server と同じ SQLite で始め、本番は Amazon RDS にする (エンジンと移し方は [本番の環境](#-本番の環境))
- 本番は AWS で、サーバはコンテナにして Amazon ECS (AWS Fargate) で動かし、インフラは C# の IaC (AWS CDK) で定義する ([本番の環境](#-本番の環境))
- データベースの表は [database.md](database.md) の設計に合わせる
- データベースは 1 つにして、すべての表に `TenantId` を持たせる (主キー・索引・外部キーの先頭にも置く。[database.md](database.md#テナントの持ち方))
- API の URL はリソースごとに 1 つにし、端末の種類ごとに使える範囲を認可で絞る (端末ごとの一覧は [api-design.md](api-design.md#-4-端末ごとの-api))

### 通信 (想定)

| 入口 | 内容 |
| --- | --- |
| REST (Minimal API) | 要求 (`/api/v1`。[api-design.md](api-design.md))。端末の状態 (電池、アプリの版) の報告も含む |
| gRPC | 同じ要求を gRPC のサービスでも出す (必要になってから) |
| SignalR | 通知 (店舗の出来事)。`seq` の順に送り、つなぎ直したら抜けた分を `GET /events` で取り直す。端末がつながっているかも接続で見る |
| OTLP | テレメトリ (ログ、メトリクス、トレース)。送れない間は端末にためて送り直す |

- REST と gRPC は同じ業務の処理を呼び、違いは入口の形だけにする (例外と結果の分類は `ApiResult` の `ApiStatus` に揃える)
- ポートは template-maui-server に合わせ、8080 (REST と SignalR)、9090 (gRPC、h2c)、4317 / 4318 (OTLP) にする
- 端末は接続先 (要求、gRPC、テレメトリ) を端末の設定 (QR かペアリング) で受ける

## 📡 通信の枠とモック

テーブル端末が使う API ([api-design.md](api-design.md)) を、すべての端末に共通の `IDeviceApi` とテーブル端末の `ITableApi` (`TableOrder.Client`) にまとめた。  
REST の窓口を作ったら、DI の登録を替えるだけで実際の通信に移る (端末の登録、トークンの取り直し、無効化とテナントの停止への対応は、モックで動かして端末の側を作り終えている)。

| メソッド | API |
| --- | --- |
| `IDeviceApi` の `PairAsync` / `AuthenticateAsync` / `ReportStatusAsync` / `GetConfigAsync` | `POST /devices/pair` / `POST /devices/token` / `POST /devices/me/heartbeat` / `GET /devices/me/config` |
| `GetStoreAsync` / `GetMenuAsync` / `GetStockAsync` | `GET /store` / `GET /menu` / `GET /stock` |
| `GetCurrentVisitAsync` / `StartVisitAsync` / `ConfirmAsync` | `GET /devices/me/visit` / `POST /visits` / `POST /visits/{id}/confirmations` |
| `CreateOrderAsync` / `GetOrdersAsync` / `ReleaseAsync` | `POST /visits/{id}/orders` / `GET /visits/{id}/orders` / `POST /visits/{id}/orders/release` |
| `CreateCallAsync` / `GetCallsAsync` | `POST /visits/{id}/calls` / `GET /visits/{id}/calls` |
| `GetBillAsync` / `StartCheckoutAsync` / `CancelCheckoutAsync` | `GET /visits/{id}/bill` / `POST /visits/{id}/checkout` / `POST /visits/{id}/checkout/cancel` |
| `CreatePaymentAsync` / `GetPaymentAsync` / `CancelPaymentAsync` / `GetReceiptAsync` | `POST /visits/{id}/payments` / `GET /payments/{id}` / `POST /payments/{id}/cancel` / `GET /visits/{id}/receipt` |

- 通知 (`IOrderEvents`) は、来店の開始・終了と店舗の変更 (注文の一時停止、ラストオーダー) を受ける (今はモックが出す)。  
  注文履歴・呼び出し・支払の状態は、まだ開いている間に読み直して出している
- サーバの通知を作るときに、端末の受け口に足す通知: 品切れ (`stock.updated`。売り切れの表示)、メニューの公開 (`menu.published`。メニューの読み直し)、来店の変更と移動 (`visit.updated` / `visit.moved`。人数の表示、待受と注文の画面の切り替え)、ホールの代わりの注文 (`order.created`。上限のルールの数え方)、追いつけない抜け (`EVENTS_EXPIRED`。今の状態の読み直し)
- モックの動き (時間で進む調理と提供、呼び出し、支払) は [architecture.md](architecture.md#-6-モックの動き) に書いた
- スタッフメニューから、通信できない・支払の失敗・売り切れ・注文の進みを起こせる (モックの操作は [architecture.md](architecture.md#-6-モックの動き) に書いた)

## 🔒 専用端末化 (MDM)

アプリ自身を Device Owner にする方式と、外部の EMM からロックタスクを許してもらう方式の 2 つに対応した (作りは [architecture.md](architecture.md#-7-専用端末) に書いた)。  
本番は外部の EMM で配ることにし、接続先とスタッフの PIN を管理対象の構成で配れるようにした (配り方は [device-management.md](device-management.md))。  
USB デバッグは EMM のポリシーで止め、自前の Device Owner では止めない。  
残りは次のとおり。

- 自前の Device Owner を QR コードで登録する作り (Android 12 以降の、登録の方式を返す画面とポリシーに従う画面) は作らない。  
  OS の保護の仕組みが許可されていない管理アプリを登録の途中で止めるので、使うなら許可の申請が要る

## 🔑 端末の認証

端末ごとの鍵で署名して、短命のアクセストークン (JWT) を受け取る形に決めた。  
流れは [api-design.md](api-design.md#15-認証認可) に書き、ここには決めるときに調べたことと残っていることを置く。

### 調べたこと

- クラウドの POS やテーブルオーダーが公開している API の認証は、連携する他社のサーバやアプリ向けの OAuth 2.0 / OIDC で、自社の端末が持つ資格情報 (形式・期限・保存場所) は公開されていない
- 自社の端末の登録には、管理画面で短いコードを出して端末で入れる型と、管理者が端末ごとに 1 回サインインして従業員は PIN で使う型がある (今の想定のペアリングコードは前の型)
- 毎回送る短命のアクセストークンは JWT が多い (期限は 25 分から 1 日)。  
  端末が長く持つ資格情報は JWT ではなく、リフレッシュトークンか端末の中の鍵・証明書にしている
- 期限の長い JWT をそのまま送る形は、期限まで取り消せないので避ける。  
  長く使う資格情報に JWT を使うのは、端末の秘密鍵で署名して数分で使い捨てる形 (クライアントの認証の JWT) だけ

### 方式の比較

| 方式 | 良い点 | 弱い点 |
| --- | --- | --- |
| 期限のない端末のトークン (元の想定) | 作りが簡単で、すぐ取り消せる | 盗まれると取り消すまで使える。要求ごとに照会が要る |
| リフレッシュトークンと短命の JWT | 一般的で、盗用を交換のときに見つけられる | 盗めば使える秘密が端末に残る。交換の行き違いで端末が外れることがある |
| 端末の鍵と短命の JWT (採用) | 秘密を端末から取り出せない (複製できない)。交換の状態を持たない。店舗のエッジでも公開鍵だけで確かめられる | 鍵の生成と署名を作り込む |
| 端末の証明書 (mTLS) | 強い | 証明書の発行・更新と、ロードバランサでの扱いが重い |

### 残っていること

- ペアリングの向きを逆にし、端末が出した QR をサインイン済みの管理画面で承認する形も考える (誰でも呼べる端点で推測できるコードを受けずに済む)
- サーバは JwtBearer で確かめ、トークンは小さな自作の端点 (`POST /devices/token`) で出す
- スタッフは端末の認証と分け、今のとおり PIN で識別する

## 🏢 マルチテナント

複数の会社 (テナント) が契約して使う形にし、テナントと店舗はアクセストークンのクレームで決めることにした。  
端末は 1 つの店舗に、外部のクライアントは 1 つのテナントに属するので、要求でテナントを選ぶ値は要らない。  
データベースは 1 つにして、すべての表に `TenantId` を持たせる ([database.md](database.md#テナントの持ち方))。  
決まりは [api-design.md](api-design.md#16-テナント) に書き、ここには決めるときに調べたことと残っていることを置く。

### 調べたこと

- 飲食の POS と注文のクラウドのサービスは、契約・加盟店・店舗の `id` をパスかヘッダで指す型が多い。  
  ただし、使えるテナントと店舗はトークンで限っていて、指す値は選ぶためのもの (使えるかはトークンで確かめる)
- パスやヘッダで指すのは、1 つの資格情報で複数の店舗やテナントを扱う連携 (他社のアプリ、複数の店舗をまとめて管理するグループ) のため。  
  店の端末は 1 つの店舗に属し、ほかの店舗に移すときは登録し直す
- クラウドのマルチテナントの設計の指針は、テナントを確かめたトークンのクレームから取り、要求の中の値 (パス、ヘッダ、本文) から取らないこととしている。  
  あわせて、トークンのテナントが知っているテナントかを確かめ、データの読み書きをテナントで絞ること、テナントの文脈をすべての層で引けるようにして開発者がテナントを意識しなくて済む作りにすることを求めている
- API の脆弱性の一覧の 1 番目は、要求の中の `id` でほかの利用者のデータを読めること (オブジェクト単位の認可の漏れ)。  
  推測できない `id` にするだけでは足りず、`id` ごとにトークンの範囲のものかを確かめる
- テナントごとに要求の数を限り (1 つのテナントの負荷でほかを遅くしない)、ログとメトリクスにテナントを付けて、テナントごとに見られるようにするのが一般的

### 方式の比較

| 方式 | 良い点 | 弱い点 |
| --- | --- | --- |
| パスにテナント (`/{テナント}/...`) | どのテナントの要求か URL でわかる。テナントごとの振り分けがしやすい | トークンとパスの食い違いを毎回確かめる。端末の設定の URL がテナントごとに変わる |
| ヘッダにテナント・店舗 | 1 つの資格情報で複数の店舗を扱える | 食い違いを毎回確かめる。付け忘れと取り違えが起きやすい |
| サブドメイン (`{テナント}.example.com`) | Web の画面でテナントがわかり、サインインの振り分けに使える | 証明書と DNS の管理が要る。端末の接続先がテナントごとに変わる |
| トークンのクレーム (採用) | 要求に選ぶ値がなく、取り違えが起きない。接続先がすべてのテナントで同じ | 1 つの資格情報で複数のテナントを扱えない (テナントごとにクライアントを持つ) |

### 残っていること

- 大きなテナントを別のデータベースに移す手順 (同じスキーマのデータベースに、そのテナントの行を移す)
- テナントの中のまとまり (ブランド、地域) が要るか。  
  要るなら店舗の属性にして、管理画面の絞り込みと外部のクライアントの範囲に使う
- テナントごとのサインイン (組織の ID 基盤とつなぐ) を作るなら、サインインの画面でテナントを選ぶ方法 (サブドメイン、メールのドメイン) を決める

## 🚀 本番の環境

本番は AWS で動かす。  
サーバ (`TableOrder.Server.Web`) はコンテナにして Amazon ECS (AWS Fargate) で動かし、データベースは Amazon RDS にする。  
インフラはコード (IaC) で定義し、IaC のプロジェクトも C# で作る (AWS CDK の C# 版)。  
ここには決めることと直すことを置き、作ったら構成 ([architecture.md](architecture.md)) に移す。

### 構成 (想定)

| 部分 | AWS のサービス | 内容 |
| --- | --- | --- |
| サーバ | Amazon ECS (AWS Fargate)。台数を負荷で増減する | REST、SignalR、管理画面、キッチン端末の配信 |
| ロードバランサ | Application Load Balancer | TLS を終える。WebSocket (SignalR) を通し、管理画面 (Blazor Server) は同じタスクに寄せる |
| データベース | Amazon RDS (エンジンは PostgreSQL が候補。複数の AZ に置く) | 今の SQLite の表を移す ([database.md](database.md)) |
| 共有のキャッシュ | Amazon ElastiCache (Valkey / Redis 互換) | トークンの要求の `jti`、要求の数の上限、SignalR のバックプレーン |
| 秘密の値 | AWS Secrets Manager | データベースの接続、トークンの署名の鍵、Webhook の鍵 |
| テレメトリ | タスクの隣の AWS Distro for OpenTelemetry Collector から Amazon CloudWatch と AWS X-Ray へ | ログ、メトリクス、トレース (テナントと店舗を付ける) |
| 前で絞る | AWS WAF | 要求の数の上限、登録の試行の上限 |
| イメージ | Amazon ECR | サーバのコンテナのイメージ |
| IaC | AWS CDK (C#) | ネットワーク、コンテナ、データベース、秘密、監視を、環境 (開発、検証、本番、大きなテナントの専用の環境) ごとに作る |

### コンテナで複数台を動かすために直すこと

- トークンの要求の使い捨ての確かめ (`jti`) を、サーバの中のキャッシュから ElastiCache (かデータベース) に移す
- すぐに止める一覧 (無効にした端末、止めたテナント) を、どのタスクも同じに持つ (データベースから読み直すか、変わったことを全台に知らせる)
- 要求の数の上限を、タスクごとではなく全体で数える (AWS WAF で絞るか、ElastiCache で数える)
- SignalR の通知を全台に配る (ElastiCache のバックプレーン)。  
  通知の `seq` はデータベースで採番するので、台数が増えても順は崩れない
- 管理画面 (Blazor Server) は接続をつなぎ続けるので、ALB のスティッキーセッションで同じタスクに寄せ、データ保護の鍵を共有する
- 裏の処理 (通知の送り手、Webhook の送り直し、古いデータの消去) は、1 台だけで動かすか、ロックで重ならないようにする
- 起動のたびにスキーマを作る今の形をやめ、デプロイの前にマイグレーションを 1 回だけ流す (ECS の 1 回だけのタスク)
- ALB で TLS を終え、サーバは転送ヘッダ (元の方式と送り元) を受ける。  
  ヘルスチェックの経路を、ALB のターゲットグループと ECS に見せる
- 設定は環境変数と Secrets Manager から受け取り、秘密 (署名の鍵、接続文字列) を設定のファイルに置かない

### データベースを移すために直すこと

- RDS のエンジンは、部分索引、遅延の外部キー、`RETURNING`、行のセキュリティを持つ PostgreSQL を候補にする (Aurora PostgreSQL とも比べる)
- 型を直す (guid は uuid、datetime はタイムゾーン付きの時刻、json は jsonb、bool は boolean)。  
  型の変換 (TypeHandler) とサンプルのデータも合わせる
- SQLite に固有の書き方 (`PRAGMA`、日付の関数、`INSERT OR`) を直し、SQL のテスト (テナントの条件の確かめ) を移した先のデータベースでも流す
- テナントの条件をデータベースの行のセキュリティ (RLS) でも掛ける (要求ごとにテナントを接続の変数に入れる)
- 接続の数を限る (接続のプール。台数を増やすときは RDS Proxy を置く)
- RDS の自動バックアップと時点の復元、読み取りの複製 (集計は複製から読む) を決める

### IaC

- プロジェクトは新しい区分 `infra/` に置く案 (`infra/src/TableOrder.Infra`、ソリューションは `infra/TableOrder.Infra.slnx`)。  
  サーバのソリューションに入れないのは、AWS CDK のライブラリが大きく、サーバのビルドと検証を重くしないため
- 環境 (開発、検証、本番) は同じコードから作り、値 (タスクの数、データベースの大きさ、ドメイン) だけを替える
- 大きなテナントの専用の環境 ([api-design.md](api-design.md#16-テナント)) も同じコードで作る (端末の接続先は EMM で配り替える)
- 開発の構成 (Aspire の AppHost) と、設定のキーと名前 (接続文字列、OTLP の送り先) を揃える。  
  Aspire の AWS の統合で、AppHost から CDK のスタックを扱う方法もある
- CI でコンテナのイメージを作って ECR に置き、CDK の適用、マイグレーション、ECS のサービスの入れ替えの順でデプロイする
- IaC のテストは、作る資源の定義を確かめる (タスクの数、AZ、暗号化、外に開くポート)
